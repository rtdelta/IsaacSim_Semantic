## 上一轮回答完整记录

核心思路是：**建立“执行时间线、同步依赖、资源生命周期”三份相互关联的证据，再通过独立实验验证复用和流水线是否有效。**

我已重新核对单卡实例：现有 Nsight Systems 2025.1.1 能识别 L40，并列出 `ad10x` 通用指标集和 `ad10x-gfxt` 图形吞吐指标集，CPU 采样环境检查通过。**首轮可以使用现有工具开展，无需先安装或升级。**这只是能力查询结果，实际计数器读取仍需短测确认。

**1．先建立独立实验项目**

建议新增 `single06_lab`，保留 single06 正式代码和配置，实验前保存源码、配置及资产引用清单。

实验项目按职责组织：

| 模块 | 作用 |
|---|---|
| 环境与基线核验 | 保存工具版本、设备、源码哈希、渲染配置和轨迹 |
| 实验运行器 | 按配置启动实验，记录变量及进程归属 |
| 阶段与生命周期记录 | 补充 NVTX、请求、缓冲及资源状态事件 |
| 原生追踪启动器 | 控制 Nsight 的采样内容和窗口 |
| 时间线分析器 | 用 Python、SQLite 关联项目日志和原生追踪 |
| 正确性与收益验证器 | 检查数据归属、输出质量、停顿和采集耗时 |

实验采用同一场景、传感器、分辨率、轨迹和渲染设置，分别测量**仅交互、仅采集、两者并发**。

**2．还原执行与等待关系**

重点围绕实际代码中的以下位置记录：

| 位置 | 需要拆解的行为 |
|---|---|
| `SceneStepper.advance_clock/apply_snapshot` | 时钟推进、运动、PhysX/USD 同步 |
| `warm_cameras/_step` | 预热、渲染提交、完成等待 |
| `SensorDrivers._native` | 原生操作互斥、等待及取消排空 |
| `_receive/_copy_host` | 回调、数据物化、独立复制 |
| `RecordPipeline.reserve/submit` | 缓冲背压、打包、IPC |
| `finish_generation/close` | 停止生成、资源释放、进程退出 |

每个主要等待都记录：

**谁在等待 → 等待哪个生产方 → 涉及哪个资源 → 用什么信号确认完成 → 哪些条件下可以解除。**

特别注意：当前 `persistent_gated` 正常路径已将 stop/drain 放到暂停或结束。需要分别验证**更新开关、显式停止、SDK 内部重建**，不能预设它们是同一种操作。

关联标识使用采集组、请求、传感器、进程/线程、GPU、队列/Stream，以及缓冲槽代数。性能时间使用统一校准的单调时钟；仿真时间用于数据对应关系。

**3．用现有工具分层追踪**

| 层次 | 使用工具 | 获取的信息 |
|---|---|---|
| 常态记录 | 项目日志、`/proc`、`nvidia-smi`，必要时直接调用现有 NVML | 操作延迟、更新间隔、CPU、内存、时钟、PCIe 流量 |
| 因果时间线 | Nsight Systems＋现有 NVTX | CPU 调度、调用栈、Vulkan/CUDA 提交与执行、复制及同步 |
| GPU 活动 | Nsight Systems 的 `ad10x` 指标集 | 实际可用的 SM、指令发射、Tensor、显存及 PCIe 指标 |
| CUDA 热点 | 已安装的 Nsight Compute | 选定 kernel 的访存、缓存、Warp 停顿和资源限制 |

先录制**初始化、稳态采集、结束清理**三个短窗口。通用 GPU 指标先尝试 1 kHz；图形指标集需要更高频率，另做更短窗口，检查缺失样本及额外开销。

NVTX 标记要与实际 API、提交和完成事件关联，不能把一个跨 `await` 的范围全部归为该函数的独占执行时间。硬件计数器也不能直接归属于某一个进程。[Nsight Systems 官方说明](https://docs.nvidia.com/nsight-systems/UserGuide/index.html#gpu-metrics)

**4．按顺序进行机制实验**

| 实验 | 单独改变的因素 | 要验证的机制 |
|---|---|---|
| 资源启停 | `gated` 与 `keepalive` | 开关是否伴随资源重建、分配释放和重复准备 |
| 姿态变化 | 固定姿态与规定的姿态变化 | 哪些成本来自场景更新或渲染历史失效 |
| 任务生命周期 | 新建采集进程与保留采集进程 | 初始化、上下文建立和退出是否造成长停顿 |
| 缓冲复用 | 已确认可控的分配改为池化 | 是否减少分配释放及同步成本 |
| 流水线 | 安全条件成立后增加工作重叠 | 回读 N 能否与准备、渲染 N+1 重叠 |

前几项保持现有预热子帧数量，先查清预热中的工作构成。随后才能针对“哪些准备工作可以复用”做实验，并检查画质、残影和数据新鲜度。

对 CPU 长停顿，追踪 PhysX→USD 调用及原生调用栈；对大量 `cudaHostAlloc/cudaFreeHost`，关联阶段、调用来源和可观测资源。**API 调用时间可能包含同步等待，不能直接当作纯分配成本。**

初筛采用交错的 A/B 对照和重复运行；有收益的候选再进行长测，验证 P95/P99 和长尾，而不是靠单组结果判断。

**5．流水线实验的进入条件**

只有确认以下契约后，才实现跨组回读重叠：

- 渲染生产完成信号可靠。
- N 组源缓冲能安全持有，N+1 不会覆盖它。
- 姿态、时间戳、标定与场景版本已经独立保存。
- Vulkan/RTX 与 CUDA 的交接具有明确同步依据。

随后才设计锁页主机缓冲、复制 Stream、完成 Event，以及“空闲—复制中—可消费—消费中”的所有权状态。

先使用已有 Warp/CUDA 能力做小原型，验证实际 GPU 重叠，再衡量端到端收益。异步复制和不同 Stream 只是实现条件，不能单独证明重叠成立。[CUDA 异步传输说明](https://docs.nvidia.com/cuda/cuda-c-best-practices-guide/index.html#asynchronous-and-overlapping-transfers-with-computation)

正确性同时覆盖时间戳、位姿、组归属、缓冲复用、重复启停和异常排空。跨实验图像如存在随机渲染差异，应进行受控质量比较，不能一律要求逐字节相同。
