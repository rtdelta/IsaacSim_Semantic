# NC-002：原生采集画质与耗时对照实现方案

编号：NC-002。保存日期：2026-10-12（北京时间）。以下完整保留上一轮回答；这是批准的实验方案，不是测试结果。实现、失败和实际验证另行记录。

下一轮的核心目标是：**在数据完整、位姿正确和画质可接受的前提下，测出原生链路真正需要多少渲染工作，以及这些工作为什么耗时。**保留旧代码，建立独立实验配置，使用现有工具，不新增或更新依赖。

**需要回答四个问题：**

1. 切换到 `PathTracing` 后，当前3DGS、鱼眼相机和LiDAR能否正常协同采集？
2. `RealTimePathTracing` 的16子帧是否必要，能否减少而不产生拖影、模糊或旧位姿数据？
3. 相同姿态、采样预算和输出内容下，原生与自制链路的耗时相差多少？
4. 剩余瓶颈主要来自图像渲染、LiDAR处理、固定页内存分配释放，还是发布与写盘？

**实验思路是逐项改变条件，先保证结果有效，再比较速度。**

不能同时更换渲染器、减少子帧、改变输出频率和图像编码，否则无法判断收益来自哪里。下一轮按以下顺序开展：

| 阶段 | 实验内容 | 要解决的问题 |
|---|---|---|
| ① 统一条件 | 对齐灯光、有效管线、姿态、曝光及传感器配置 | 排除上一轮遗漏的差异 |
| ② 验证冻结采集 | 保持姿态和仿真时间，使用官方接口生成并录到新数据 | 打通公平比较的前提 |
| ③ 实时模式子帧实验 | 对比1／2／4／8／16子帧，正式采集配置保持一致 | 判断固定16子帧的必要性 |
| ④ Path Tracing实验 | 对比64／256／512／1024目标SPP | 建立画质与耗时关系 |
| ⑤ 等条件链路对照 | 用相同姿态和渲染预算比较两条链路 | 测出调度、传输与存储的额外成本 |
| ⑥ 底层追踪 | 选代表性配置采集Nsight时间线 | 定位剩余CPU/GPU瓶颈 |

**首先补齐对照条件。**

除了同一USD、13路LiDAR、4路1920×1080鱼眼，还要明确：

- 使用同一盏DomeLight、相机曝光和背景。
- 核实场景自带管线与新建管线，保证每路传感器只有预期的有效生成管线。
- 使用完全相同的目标姿态序列和采集时刻。
- 记录实际生效设置，而不只记录请求的配置值。
- 固定GPU数量、渲染分辨率和传感器参数。

图像编码单独比较。渲染阶段可以直接对照；端到端若仍是旧PNG与原生RGB，就必须标明编码差异，不能把结果全部归因于采集架构。

**冻结采集是必须先通过的一项验证。**

上一轮冻结实验只录到了预热阶段的数据，尚未得到可辨识的新冻结采集结果。下一轮应验证官方Writer和发布触发能否在冻结条件下正常工作。

通过标准包括：所有传感器输出新数据、输出对应当前姿态、时间含义正确、MCAP中能解码得到完整组。**不能只检查话题存在，也不能通过改写时间戳把旧数据包装成新组。**如果这一项仍失败，就暂时只报告连续模式结果，不计算“同条件完整组”的加速倍数。

**子帧实验要同时覆盖静止和姿态突变。**

选择三类场景：

- 长时间保持同一姿态。
- 大臂、小臂或铲斗突然跳到另一目标角度。
- 整机或传感器位姿发生较大变化。

同一个姿态分别请求1／2／4／8／16子帧，检查轮廓拖影、细节稳定性、天空和曝光变化，以及实际采集位姿。子帧用于重复渲染同一逻辑帧，能够帮助历史缓存与新资源稳定，但合理数量取决于变化情况。[官方说明](https://docs.isaacsim.omniverse.nvidia.com/6.0.0/replicator_tutorials/tutorial_replicator_sdg_workflows.html)

这一阶段应得到一个明确结论：**固定16是否必要，还是不同变化程度可以使用不同预算。**

**Path Tracing阶段使用明确的采样预算。**

建议先固定反弹次数、降噪设置和分辨率，只改变目标SPP：

| 配置 | 用途 |
|---|---|
| 64 SPP | 检查功能和低预算表现 |
| 256 SPP | 中间质量对照 |
| 512 SPP | 高质量候选 |
| 1024 SPP | 检查继续增加采样的收益 |

先关闭自适应采样，使各组工作量更容易比较；记录实际累积与重置情况，不能把子帧数直接当成SPP。`AA＝3`、`DLSS Quality＝2`也不能代替Path Tracing的采样预算。[参数说明](https://docs.omniverse.nvidia.com/materials-and-rendering/latest/rtx-renderer_pt.html)

用1024 SPP结果作内部图像参考，比较较低预算的噪声和细节；它不是现实真值，也不证明3DGS与点云已经严格配准。

**耗时使用两种口径，避免重复上一轮的比较问题。**

- **单组数据就绪耗时：**应用目标姿态开始，到所有传感器产生本组有效新数据。
- **整轮有效吞吐：**采集、尾帧排空和MCAP收尾总耗时，除以有效组数。

启动、初始化预热、首组、稳态、验包和Profiler导出分别列出。关键配置做至少3轮重复，报告中位数、范围和异常组，不只给一个平均值。

日志继续记录分阶段墙钟、CPU线程时间、GPU活动、内存和显存；代表性配置再用现有Nsight查看 `cudaHostAlloc/free`、CUDA模块生命周期、数据复制、同步等待和Vulkan渲染区间。普通测速与Profiler测速分开。

最终应交付三项结果：**子帧是否能减少、Path Tracing高质量一组到底需要多久、两条链路在相同有效工作量下的差距与具体瓶颈。**
