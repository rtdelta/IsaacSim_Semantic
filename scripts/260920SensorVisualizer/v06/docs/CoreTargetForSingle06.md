读完两份文档后，我理解你的意图是：**深入查明引擎怎样调度 CPU/GPU、怎样交接资源、为什么必须等待，再通过机制级实验验证哪些串行关系可以解除。**

因此，下一轮核心目标应调整为：

**以 single06 为基线，建立可验证的执行、依赖和资源生命周期模型，找出造成间歇性负载及卡顿的机制，并验证可控的改造方向。**

具体分成四个目标。

**1．还原实际执行机制**

沿一组采集追踪：

`姿态更新 → PhysX/USD 同步 → 预热 → 渲染提交 → GPU 执行 → 输出交接 → 回读 → 编码保存 → 资源回收`

每一步都要明确：

- 哪个进程、线程负责？
- 工作提交到哪个 Vulkan 队列或 CUDA Stream？
- CPU 提交何时结束，GPU 工作何时完成？
- 回调发生时，数据是否已经完成、位于哪里、还能有效多久？

最终形成**执行图和实际时间线**，区分 CPU 计算、提交、轮询、阻塞与 GPU 执行。

**2．逐项证明“为什么串行、为什么等待”**

为每个主要等待建立一条记录：**等待方、生产方、资源、完成信号、解除条件、证据**。

然后判断它属于哪一种：

| 限制来源 | 要验证的问题 |
|---|---|
| 真实数据依赖 | 后续工作确实需要前面的结果吗？ |
| 共享状态冲突 | 下一组会修改场景或覆盖上一组缓冲吗？ |
| 引擎接口契约 | 是否支持多请求在途、可靠完成信号和缓冲持有？ |
| 项目实现选择 | 单一请求状态或粗粒度等待是否扩大了同步范围？ |
| 硬件竞争 | 并发后是否争用运算单元、缓存、显存或复制资源？ |

第二份文档中的 v07 `inflight` 等限制是研究线索；本轮必须检查 **single06 的实际实现**，才能形成结论。

**3．深入验证预热、缓存和资源重建**

这是当前证据最强、应优先研究的部分：

- **引擎缓存：**姿态变化、传感器启停分别使哪些场景资源或渲染历史失效？重复预热承担了什么必要工作？
- **数据缓冲：**谁分配、谁持有、谁复用、谁释放？大量 `cudaHostAlloc/cudaFreeHost` 与哪些生命周期事件对应？
- **硬件缓存：**在可观测范围内检查 L1/L2、显存流量和运算活动，判断访存及并发竞争。

要通过单变量实验建立因果关系，例如比较资源保持与重新创建，而不是仅根据 API 次数推断原因。

**4．验证可以落地的机制改造**

优先验证两类候选：

- **复用机制：**保留必要资源和缓冲，减少重复准备、分配与释放。
- **流水线机制：**在 N 组输出已完成且可以安全持有后，让回读 N 与准备或渲染 N+1 重叠。

第二类必须先确认源缓冲有效期、生产完成信号及跨 Vulkan/CUDA 同步契约，再验证重叠。实验同时检查场景版本、时间戳、数据归属，以及停止、取消和异常排空。

**本轮验收要求也应更深入**

交付每个重点问题的完整证据链：

**机制假设 → 原生追踪证据 → 单变量实验 → 正确性验证 → 性能收益。**

结果应明确哪些关系必须有序、哪些可以重叠、哪些受接口限制，以及尚缺什么证据。性能仍以**交互 P95/P99、最长停顿和完整采集耗时**衡量，并分别报告冷启动与稳态表现；保持现有画质、传感器和数据对应关系，保留正式代码，用独立入口进行实验。
