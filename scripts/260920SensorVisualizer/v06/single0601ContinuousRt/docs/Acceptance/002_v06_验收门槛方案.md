# 原v06冻结快照采集版本验收门槛方案

记录日期：2026-10-14。文档版本：1。性质：记录原v06的实际契约，并制定后续复验和严格比较门槛，不是新的验收通过报告。

原v06指`v06/sensor_visualizer_v06`，不含其下独立项目`single0601ContinuousRt`。两份方案均归档在当前项目`docs/Acceptance`，原v06源码、配置和既有文档保持原样。当前连续版本另见[001连续版验收门槛方案](001_single0601ContinuousRt_验收门槛方案.md)。

## 1 三种模式与两类验收

原v06为网页/交互Isaac进程、独立正式采集Isaac进程及CPU记录进程。交互侧使用自己的规定运动时钟，原生Timeline保持暂停；正式采集侧推进原生物理时间、应用源快照、冻结，然后预热、渲染并保存。这不是当前版单GUI实际场景连续采样的架构。

| 模式 | 正确的完成定义 | 不能宣称 |
|---|---|---|
| offline | 实际源轨迹覆盖范围内的约定完整网格全部采完并回读 | 轨迹外原始请求数也已完成，或交互当时原生实时采样 |
| live_complete | 轨迹中约定范围的网格完整回放，允许积压和延迟；先确认轨迹录制终止/范围边界 | 墙钟实时10Hz、没有重放延迟 |
| live_latest | 每次所取新快照形成合格完整组，跳过网格准确记账 | 完整记录所有10Hz计划网格 |

原v06的`finished`、writer结束和任务锁释放分别检查；Stop后的有效前缀不能称原请求完整完成。offline入口会按轨迹时长裁剪组数，验收同时保存用户请求数、有效约定数、轨迹覆盖及裁剪原因。

门槛分两类：**V类为原代码/原文档的实际基础契约；Q类为本次新增的严格复验/两版公平比较要求。** V类通过不自动表示Q类通过；Q类不能反向改写2026-10-10历史报告。

## 2 V类：原有基础数据门槛

以下阈值来自当前保留的v06源码，采用其原有比较运算符；不是从连续版复制的等价阈值。

| 编号 | 原有检查 | 门槛及来源 |
|---|---|---|
| V0 | 配置和资产 | schema3；非空合法选择集；频率为物理频率的合法整数分频；实际scene、依赖、渲染和传感器清单保存 |
| V1 | 原生源时间 | 每路源simulationTime相对当前冻结目标stamp差≤2ns；`CaptureTicket.validate`及`sensors.py` |
| V2 | 冻结时钟 | 组内原生仿真时间和Timeline时间各自变化≤1e-9s；`assert_frozen` |
| V3 | 冻结场景 | Stage/generation、安装revision和拓扑不变；传感器世界矩阵分量变化≤2e-6，rtol=0；`SceneStepper.capture` |
| V4 | 原生渲染变换 | 渲染/author矩阵最大分量差≤2e-3；`CaptureTicket.validate` |
| V5 | 轨迹到原生时间映射 | `abs((native_stamp-native_epoch)/1e9-trajectory_time)≤0.5/physics_hz+1e-6s`；60Hz时约8.334ms；`replay_capture.py` |
| V6 | 回调归属和新鲜性 | 正确request、Stage generation、选择集、完成窗口和attempt；原有证据方法为serialized manual Writer或completed-render poll；可用原生帧号不重复 |
| V7 | 输出与独立回读 | MCAP可解码，PNG/XYZ/标定/TF/header/组号及writer摘要一致；缺一路不得提交完整组 |

V4是含平移和旋转分量的矩阵最大差，不能直接称“2mm位置误差”，也不等于连续版的1mm/1e-4rad双门槛。V1的2ns约束正式采集原生时钟；V5描述另一层源轨迹时间映射，两者不能混为同一个误差界限。

原SDK没有暴露的source frameId保留null。项目request/callback计数不伪造为原生frameId。静止同字节和合法无返回不能仅凭内容判为旧帧。

原路径允许`max_retries=3`的有界整组重试，即最多初次加3次；仅对代码允许的源时间、渲染位姿或旧帧错误重试，冻结目标不变，attempt/request重新隔离。缺失回调不能借重试挂到下一组。保存每次失败原因与重试耗时，最后合格不删除此前错误。

## 3 V类：原输出回读与控制生命周期

独立读取`bag_unified`中的实际ROS/CDR、PNG与XYZ，不能仅复述`writer_report.state=finished`。

| 检查 | 保留的v06验证口径 |
|---|---|
| 消息时间 | 有header的消息、Clock及每条TF的stamp与对应bag时间一致；另检查原生源时间及轨迹映射 |
| 图像 | 与注册表的1920×1080和RGB/PNG一致；equidistant鱼眼模型、内参及畸变一致，数值校验atol=1e-12 |
| 点云 | x/y/z float32小端；point_step=12，row_step=width*12，字节长度、单位及有限值规则正确 |
| TF与传感器矩阵 | 独立重建矩阵最大分量差<2e-5；检查父子关系、无环、无重复child和光学坐标转换 |
| 源轨迹姿态 | 已支持的offline/live_complete检查root位置分量差<2e-5m、关节角差<2e-5rad、四元数符号等价向量差<2e-5 |
| 写入摘要 | 实际读取消息的topic/time/CDR序列摘要与writer记录一致；它不是新版本逐组commit格式 |
| 计数 | 按选择集、实际模式、有效源范围和每组输出结构核算；完整模式无无解释缺口，latest模式保留跳过网格 |

以上为[现有回读工具](../../../tools/validate_capture_data.py)的口径。该工具依赖原v06输出、源轨迹及目标场景假设，不能直接当作任意选择集、无返回场景或连续版验证器；例如场景相关的非均匀图像检查不等同原生新鲜性检查。

原v06不要求新版本的`group_commit`或READY格式。缺少新格式不代表原格式自动失败，但也不能仅将旧文件改名为新格式来通过比较；需要独立外部验证报告、真实文件清单和hash。

控制复验覆盖网页与原生按键、失焦/文本输入/F8、Direct/Target/Periodic关节、整机平移与Yaw/Pitch/Roll、安装调整/保存/恢复、轨迹导入导出、Pause/Resume/Stop+Drain、Exit/Reinitialize、重复任务拒绝、任务恢复、资源锁释放及非法GPU请求拒绝。

keys回执代表输入状态已处理，motion/mount回执代表对应操作已处理；两者均与实际按键到姿态应用、浏览器到屏幕延迟分开计量。原v06交互RTF上限0.1是原设计，不因未到墙钟10Hz判基础数据失败。

## 4 Q类：新增严格正确性与几何门槛

这部分用于后续高可信采集复验及作为当前连续版的合格性能基线。原有矩阵一致、相同header、配置保持和逐消息hash均不足以单独证明真实图像/点云对应目标状态。

| 编号 | 新增门槛 | 判定 |
|---|---|---|
| Q0 | 版本和输出范围冻结 | 源码/资产/配置/有效渲染/GPU/驱动、模式、轨迹覆盖、初始epoch、安装标定和进程拓扑明确 |
| Q1 | 原生变换的物理误差 | 从同事件原生变换独立复算平移≤1mm、旋转测地角≤1e-4rad，不能把V4分量差直接代入 |
| Q2 | 理想独立几何 | 已知非对称标记重投影P95≤1px；无噪声已知平面每组点到面P95≤5mm；可观测旋转估计沿用1e-4rad上限 |
| Q3 | 故意错步负对照 | 用真实前一物理步及已知源状态错配，确保测试对半步/一步问题具有足够观察能力 |
| Q4 | 完整模式与正式质量 | 参考数据采用offline或live_complete；原参数/PNG/4相机+13LiDAR保持；source/header/状态/几何分别通过 |
| Q5 | 原生证据不足处理 | 若旧输出没有保留所需原生矩阵、时间或buffer证据，标unknown并用独立诊断入口补取；不补造字段 |

低速3°/s、较快10°/s、纯平移、混合、反转/非匀速、关节、遮挡及暂停恢复首帧均需覆盖。诊断可明确使用理想噪声参数，但正式质量保持原噪声。几何拟合只用于诊断；不能事后改header、转点云或用历史状态替代错误原生矩阵再宣称通过。

独立指标证明的是输出与目标状态的对应关系；没有射线方向/发射器及原生转换证据时，点云几何错误不直接等于已确认GPU追踪函数有错。

## 5 最低执行规模与工具能力边界

| 层次 | 规模 | 性质 |
|---|---|---|
| 原有功能smoke | offline/live_latest/live_complete各至少3组，加安全停止、恢复和原生控制用例 | 与现有acceptance_suite规模一致；只放行后续复验 |
| 本次补充数据复验 | 单相机静止/运动各200组、单LiDAR200组、1+1至少200组、全组合至少100组 | 新增复验计划，不能称历史v06已做完 |
| 本次补充机制诊断 | 四类运动各40有效事件、各3次独立初始化；不同模型/安装及恢复首帧另覆盖 | 独立诊断；冻结采样按所取源快照解释，不强制连续播放 |
| 本次补充重复生命周期 | 同GUI至少20轮，每轮至少10组 | 逐轮订阅、产品、worker、IPC、槽位及锁状态检查 |
| 性能资格轮 | 各轮20组预热+至少200组测量；至少3轮 | 必须有足够轨迹覆盖，不能被入口自动裁剪后仍称200组 |
| 原v06已有长测脚本 | 30分钟交互soak，期间一次100组offline采集 | 其行为不是30分钟连续全组合采集 |
| 本次补充严格采集长测 | 至少30分钟墙钟持续全组合完整模式采集并全部回读 | 新增门槛；需要明确运行驱动，不能只沿用前一行脚本结论 |

工具入口包括`acceptance_suite.py`、`validate_capture_data.py`、`validate_performance.py`、`long_validation_runner.py`。它们各自证明范围不同：旧性能验证器主要针对v05/v06的既有轮次和原格式；旧长测脚本不是当前连续版C6驱动。新规模、严格几何、原生证据和长测资源门槛需要补充独立工具，现有脚本一次pass不足以放行全部Q类要求。

所有长期/重复试验先冻结Kit、记录进程、RAM、VRAM、FD、线程、槽位和日志预算，持续增长或超限即失败。3×64MiB是原raw槽配置，不包含全部encoded/mmap/进程占用，不能当作总内存上限。

## 6 默认产品与吞吐基线分别验收

| 用途 | 固定采集策略 | 验收重点 |
|---|---|---|
| 原v06默认产品 | persistent_gated+gated，16相机冻结预热+2正式子帧；安装变化/初始化预热按原设置 | 数据V/Q门槛、交互、长尾、清理；原默认不变 |
| 当前版速度比较基线 | 未改原v06、scene18、persistent_gated+keepalive、16+2 | 先证明同条件合格输出，再作为当前版≥2倍比较分母 |

v06默认scene16的2026-10-10历史数据不能直接作为scene18连续版基线。比较配置及轨迹保存在独立验收目录，不覆盖原`config/capture_policy.json`。不要求v06消除16+2、改为单Owner或取得≥2倍自身速度；这些属于当前连续版目标。

基线资格要求Q0–Q5及完整回读成立；v06速度慢或没有达到当前版扩展RTF目标，不会单独使其失去参考资格。只有v06数据与参数满足共同条件，才能将候选/基线比值解释为合格产能提升。

## 7 性能、交互及长尾的记录方案

同条件分别测仅交互、仅采集及含交互/预览的采集。默认gated与keepalive分别列结果，CPU/GPU利用率只作资源诊断，不以GPU占用更高认定吞吐更好。

原v06机制研究目标来自[CoreTargetForSingle06](../../../docs/CoreTargetForSingle06.md)和[ImplementationPlanForSingle06](../../../docs/ImplementationPlanForSingle06.md)：建立执行、等待、资源生命周期证据，比较P95/P99、最长停顿及完整采集耗时。原文件没有统一“2倍”或固定绝对吞吐通过值，不能将本次新增指标冒充原历史门槛。

| 指标 | 记录及本次补充规则 |
|---|---|
| 数据产能 | written且最终回读合格组/稳态采集墙钟；另列合格组/全操作墙钟；不使用仅提交数量 |
| 冷启动与清理 | 启动、加载、初始化、采集、排空、验证和退出分别记录，不把旧wall_s解释为全操作时间 |
| 控制延迟 | 原回执accepted-to-completed、按键event-to-actual-pose、端到端显示分开；实际应用P95≤50ms/P99≤200ms作为本次补充产品目标，不是旧报告已证明的门槛 |
| 长尾 | 更新间隔、owner回调各自P50/P95/P99/最大；>100ms和>500ms次数；startup/steady/drain/exit阶段拆开 |
| 质量 | 预先固定重点ROI和几何规则，保留无损样本；没有统一旧PSNR/SSIM门槛，不凭单帧分数宣称等同 |
| 机制改造收益 | 提前指定主指标及允许退化界限，至少3轮交错对照；主指标改善且数据/质量/资源约束通过才认定候选有效 |

无profiler普通测量与有界Nsight/NVTX诊断分开。多个并行/嵌套span不可直接求和。分位数算法预先固定，历史工具的取整算法与新增nearest-rank报告不得混为同一口径。

两版正式速度比较采用各3轮交错、每轮20+200，使用同一L40、SDK、scene18依赖、完整传感器、PNG、标定、轨迹及实际状态。保持相同可见GUI/视口、控制输入和网页/RViz预览负载，记录baseline交互GUI+headless采集进程与candidate单GUI的真实拓扑。不能以仅v06采集对照带交互的候选，或将v06固定0.1x源运动与另一种源负载悄悄混用；不能满足时比较资格为unknown。

需要只读适配旧格式产生外部比较报告；不修改旧MCAP，不捏造新格式commit/READY。基线不成立或质量不通过，候选的2倍速度结论保持未验收。

## 8 当前历史证据及判定方式

依据[2026-10-10性能证据](../../../docs/performance_evidence.md)：scene16同条件对照112组、1456份PointCloud2、448张PNG已做逐消息解码及原格式摘要/时间/TF检查；三模式各3组和原生控制等功能有通过记录。

历史默认复测的引擎回执P95约28.05ms、P99约33.39ms，但最大约816.31ms，更新间隔最大约861.33ms。它们不能等同实际按键到姿态或屏幕延迟，也不能证明长尾已消除。历史keepalive仅采集8组约43.18秒、约0.1853组/墙钟秒，属于scene16单轮小样本观察，不作为scene18验收阈值或保证。

该轮没有重做100组/30分钟长测，也未以独立几何证明全部图像/点云严格对齐；本次Q类门槛尚未新执行。历史V类证据、后续Q类资格及新配置通过范围分开写。

最终v06报告建议列`source_event_ok/frozen_state_ok/basic_readback_ok/complete_grid_ok/strict_pose_ok/geometry_ok/quality_ok/interaction_ok/lifecycle_ok/baseline_qualified`。每项给模式、场景、轮次、参数、证据路径及true/false/null；latest的完整网格项明确false或不适用，不以finished替代。只有声明范围的必需项全部通过，才给该范围合格结论。
