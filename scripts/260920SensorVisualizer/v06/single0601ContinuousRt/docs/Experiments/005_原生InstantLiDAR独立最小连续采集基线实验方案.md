# 原生 Instant LiDAR 独立最小连续采集基线实验方案

日期：2026-10-15，Asia/Shanghai。版本：1.0。本文保留执行前设计和门槛；用户已授权开始实现，实际实现、资格修订及执行状态见 [006 实现与执行记录](006_原生InstantLiDAR独立基线_实现与执行记录_20261015.md)。后文“尚未实施”描述原方案编写时状态，不代替执行记录。

依据：[003 时序与状态历史分层测试方案](003_物理传感器时序与状态历史一致性_分层测试方案.md)、[004 已有实现与执行记录](004_时序状态一致性分层测试_实现与执行记录_20261014.md)，以及本次关于“原生 Instant 模式＋最简脚本＋连续调度”的讨论。

本方案交付一组独立的诊断基线：先用最小脚本和当前有效配置，检验相同问题是否仍然出现；再用文档约束下的简化配置，区分配置因素。角增量、绝对朝向、点云与源时刻姿态的一致性分别验收。任何诊断组通过，均不自动改变正式连续采集验收状态。

## 1. 实验目标与适用范围

### 1.1 核心问题

1. 不继承现有采集框架时，原生 Instant LiDAR 在持续旋转过程中，是否仍出现半步或一步有效旋转偏差？
2. 在资产、运动、采样相位、渲染设置及输出拓扑匹配时，最小脚本与现有框架的结果是否一致？
3. 若最小脚本在不同配置下结果不同，哪些配置或配置交互足以改变异常？
4. 是否能够得到一份可独立运行、可由解析几何验证的连续采集样本，作为后续逐项接回生产模块的起点？

这里的“角增量”主要指传感器世界姿态 yaw 的物理步增量和相邻扫描增量。发射器扫描方位角、角分辨率和扫描覆盖是另一组参数，需要固定并保存，不能与传感器自身转动混用。

### 1.2 三个专业视角对应的交付

| 视角 | 主要问题 | 本轮交付 |
|---|---|---|
| 训练数据生成 | 点云与姿态真值能否正确配对，是否存在稳定的标签偏差 | 逐目标源时间、实际姿态、原始点云与独立几何判定 |
| 仿真 | 持续运动下，采样使用的有效朝向是否符合瞬时扫描约定 | 原生元数据与解析几何的分开比较，以及历史姿态候选 |
| 程序架构 | 异常复现是否需要现有调度、状态账本或配置组合 | 独立最小入口、匹配配置对照及后续模块接回路径 |

本轮主要使用静态房间和纯旋转，验证规定运动下的采集一致性。机器人关节、接触动力学、IMU、全量多传感器、真实扫描畸变、长期性能均不在首轮范围。

## 2. 已有证据与新增实验的必要性

以下内容来自 004，属于已有证据，不能充作本轮新结果。

| 已有事实 | 对本轮设计的约束 |
|---|---|
| 已使用单个原生 Instant LiDAR `MyAiry_front`、非对称解析房间和零距离噪声 | 新增价值主要在独立实现，不能把 Instant 模式本身描述成首次测试 |
| 诊断入口是 `TableOwner → NativeProbeOwner → EngineOwner`，并使用 `ContinuousBackend` 等模块 | 最小入口不能继续继承这些类，否则无法覆盖同源实现风险 |
| 60 Hz、3°/s 旋转主轮每轮几何方向 100/100 失败，有效旋转符合前一步或半步候选 | 原生时间和当前状态一致，不足以证明射线使用的历史旋转正确 |
| 60 Hz、6°/s 条件原生 pose 全通过，几何全失败，符合半步旋转候选 | 不能以原生 pose 头通过替代点云几何通过 |
| Writer 交付通常晚于源物理步，既有分析已按源步比较 | 不能再次仅用回调晚到解释已有几何偏差 |
| 保持窗口可规避几何异常，但改变运动，载荷重算新鲜度仍未知 | 新基线在采样期间必须持续旋转，不采用保持窗口 |

现有结果支持继续检查共同的原生状态消费路径，但尚未证明异常与应用框架无关。独立最小基线用于补齐这一证据缺口。

## 3. 术语与避免误判的基本规则

### 3.1 Instant 语义及实际输出节奏

NVIDIA Schema 将 `instantLidar=true` 描述为在帧末时刻生成完整扫描、忽略实际扫描时序和扫描速率。这为排除扫描内运动效应提供了适合的诊断语义，但不能据此推断原生内部不使用历史变换。[来源：Omni Sensors Schema](https://docs.omniverse.nvidia.com/kit/docs/omni.usd.schema.omni_sensors/latest/omni_sensors_schema.html)

实际输出节奏由安装版本、渲染调度及有效设置共同核验。本方案要求显式设置 10 Hz tick，并验证实际源事件间隔。若实测为每渲染帧输出，不能抽取每六帧后将其登记为“原生 10 Hz 已成立”。

### 3.2 角增量与绝对朝向必须分别验收

设物理频率为 `h`，传感器采样频率为 `f`，规定 yaw 速度为 `ω`：

```text
物理步角增量：Δθ_phys = ω / h
相邻扫描角增量：Δθ_scan = ω / f
目标绝对朝向：θ(n) = θ0 + n × ω / h
```

例如 `h=60 Hz`、`f=10 Hz`、`ω=3°/s` 时，每物理步为 0.05°，相邻扫描为 0.3°。如果每份点云始终使用前一步朝向，相邻扫描仍可相差 0.3°，但绝对朝向持续落后 0.05°。

因此，“帧间增量正确”与“点云属于该源时刻的姿态”是两个独立命题。首帧偏差也不能通过逐序列减去初始误差而被消除。

### 3.3 时间与状态分开保存

| 字段 | 用途与边界 |
|---|---|
| `physics_step`、实际 `t_phys`、回调 `dt` | 建立真实推进序列 |
| 写入目标、PRE/POST 实际 USD 世界矩阵 | 区分命令值与实际输入 |
| `IsaacReadSimulationTime`、原始 `ReferenceTime` 及原生映射结果 | 关联同一原生事件与物理步；保留各接口的来源 |
| GMO 原始 timestamp、帧首/帧末时间及位姿 | 按各字段定义解释，不默认与物理时间同域 |
| 回调单调时间、回调时最新物理步 | 观察交付延迟，不替代源时间 |
| 解析几何有效朝向 | 独立检查载荷与目标姿态是否一致 |

同源时间服务的两个一致读值不计为两份独立几何证据。物理步和纳秒值使用整数或十进制字符串保存；同时保留 API 原始值与单位。

## 4. 实验组：先比较架构，再比较配置

### 4.1 分组定义

| 组别 | 入口 | 配置 | 优先级与用途 |
|---|---|---|---|
| `M_E` | 新建独立最小脚本 | 匹配现有诊断链的有效配置 E | 必做；回答脱离框架是否仍复现 |
| `P_E` | 现有 `tools/clock_state` 连续诊断入口 | 同一份配置 E | 必做；与 M_E 在本轮重新交错比较 |
| `M_D` | 与 M_E 相同的最小脚本及原生输出拓扑 | 文档约束下的简化配置 D | 推荐第二阶段；检查配置组差异 |
| `O_D` | 安装版本所支持的官方示例/`LidarSensor` 路径 | 对应的已记录配置 | 可选；检查另一条受支持的 API 路径 |

E 指开跑前从现有实现和有效运行设置整理、读回并冻结的配置，不指根据历史报告猜测的一组值。D 指明确记录每一项请求值与有效值的配置，不使用含糊的“全部默认”。

`O_D` 若更换了资产、API 封装、产品拓扑或输出字段，只能说明另一条路径的行为；不能将其与 P_E 的差异全部归因于配置。官方文档当前推荐通过 `LidarSensor` 管理 RTX LiDAR 的运行时采集，但实际安装构建是否支持该 API，应在实现时核验。[来源：RTX Lidar Sensor](https://docs.isaacsim.omniverse.nvidia.com/6.0.1/sensors/isaacsim_sensors_rtx_lidar.html#how-to-collect-data-from-an-rtx-lidar)

### 4.2 M_E/P_E 配对条件

两组必须匹配以下内容，匹配结果另存为 `pair_equivalence.json`：

- 同一 Isaac Sim/Kit/传感器扩展构建、GPU、启动模式、渲染器及驱动。
- 同一传感器源资产及依赖哈希、有效 schema 参数、房间几何、单位和坐标约定。
- 同一规定运动表、初始世界姿态、物理与渲染推进频率、首目标运动步数和原生 tick 相位。
- 同一产品数量、分辨率、原生 annotator 集合、GMO 通道级别、CPU/GPU 输出位置及附着顺序。
- 同一完整 XYZ/GMO 保存要求、有界异步落盘方式和已声明的压缩策略。
- 初始化中产品创建时点、固定暖机长度、开始运动前的 Timeline 生命周期和初始化物理步数。

配对按运动开始后的局部步号与实际位姿进行，跨进程绝对时间、epoch 和 prim 路径单独保存，不强行设为相同。语义无关的名称可以不同；可能影响行为的差异必须列出。

如果某项无法匹配，保留该轮并标为“架构与该项差异的组合对照”。不能继续声称仅改变了采集框架。历史 004 仅作参考，本轮 P_E 新采结果才是主要配对基线。

### 4.3 配置 E/D 的冻结要求

| 项目 | E 的要求 | D 的要求 |
|---|---|---|
| 物理/渲染/loop | 60/60/60 Hz，并核验真实推进 | 同 E |
| Instant、tick、scanRate | `true`、10 Hz、10 Hz | 同 E |
| 发射器模式、坐标系、补偿输出、累积输出 | 保存实际值并锁定 | 首轮保持同 E，避免改变输出语义 |
| Motion BVH | 与 E 实际值匹配 | 按输出补偿需求和安装版本文档明确选择；不能为了简化关闭必要功能 |
| Multi-Tick | 保存全部相关有效设置 | 保持显式 10 Hz 所需的受支持设置，不能用 autotrigger 偷换条件 |
| per-sensor TLAS、历史长度及其他项目覆盖项 | 全部列明 | 明确哪些恢复为该构建默认、哪些保留及理由 |
| 异步渲染、AA、DLSS、渲染模式 | 与 E 匹配 | 与 E 相同，除非另列为配置干预 |

官方文档要求 OmniLidar 的 tick rate 与 scanRateBaseHz 相等，以保证扫描累积及 Multi-Tick 行为。本轮将两者同时固定为 10 Hz，仍以实测输出验证 Instant 模式下的行为。[来源：Tick Rate](https://docs.isaacsim.omniverse.nvidia.com/6.0.1/sensors/isaacsim_sensors_rtx_lidar.html#tick-rate)

Motion BVH 在官方文档中的默认状态为关闭，运动补偿需要开启。因此 D 不等于机械地关闭 Motion BVH；只有先确认输出语义与该构建支持方式，才允许将其作为单独干预。[来源：Motion BVH](https://docs.isaacsim.omniverse.nvidia.com/6.0.1/sensors/isaacsim_sensors_rtx.html#motion-bvh)

如 D 与 E 改动多项，首轮只能归因于“配置组”。需要解释具体开关时，以 M_E 为起点一次改变一个设置，预登记后再运行。D/E 有效值全部相同时，记录条件重合，不重复运行并冒称有配置差异。

## 5. 独立最小脚本的边界

### 5.1 允许保留的组成

```text
安装版本支持的 SimulationApp / Kit 启动入口
  → 创建六面房间与一个 OmniLidar
  → 设置固定 dt 与已冻结配置
  → 一个 PRE 写入回调、一个 POST 实际读回回调
  → 一个常规仿真推进循环
  → 一个原生输出接收入口
  → 取得自有 CPU 副本并交给有界后台保存
```

单一推进循环是指只有一个所有者推进仿真，不能同时调用两套自动推进机制。官方入口若内部管理渲染，应使用其正常流程，不再叠加第二次渲染。

最小性以依赖边界和职责判断，不设置任意代码行数目标。为获得证据所需的有限元数据和安全自有拷贝保留，复杂分析放在离线完成。

### 5.2 不进入最小采集进程的项目模块

- 不继承或导入 `EngineOwner`、`NativeProbeOwner`、`TableOwner`、`ContinuousBackend`。
- 不导入生产状态账本、正式门禁、Barrier/Hold 调度、自动后端回退及在线姿态修正模块。
- 不引入机器人、UI 控制、ROS、MCAP、网络发送或多传感器同步管理。
- 不在原生接收入口运行几何拟合、候选选择、历史账本查询或按质量筛帧。

允许使用同一安装版本的原生 USD、SimulationManager、Replicator、annotator 和时间映射 API。这些原生服务是待检链路的一部分，不属于应用框架复用。

M_E 独立建立最小原生 Writer，仅复制所需原始字段和数据。其原生 annotator 集合与 P_E 相同；不要为了缩短脚本去掉完整 GMO，从而改变图结构和保存负担。

### 5.3 离线模块的复用边界

可以用现有离线分析器对新数据复算，但主要结论还需要独立实现或交叉核验的坐标转换、射线交点与 yaw 残差计算。不能让采集和唯一分析都依赖同一套存在疑问的姿态转换。

所有共享模块、独立模块和算法来源写入 `source_manifest.json`。两种分析不一致时保存双方结果，不选择误差较小的一种作为唯一报告。

## 6. 场景、传感器与规定运动

### 6.1 房间与传感器

沿用六面非对称房间，世界单位为米，Z 向上；内表面为：

```text
x = -7、+10
y = -11、+8
z = -4、+6
```

墙体厚度、尺寸和变换与现有诊断房间一致，并保存几何 manifest。传感器位于世界原点，无运动父节点，首轮只绕世界 Z 轴旋转。材质、碰撞和可见性配置固定。

主组继续使用原 `MyAiry_front` 传感器 prim 的有效配置，可直接引用同一源 prim；无需加载完整机器人场景。记录源 prim、资产及依赖哈希，避免重新手写扫描阵列造成隐含变化。

将诊断实例 `rangeAccuracyM` 显式设为 0，并保存覆盖前后值。其他发射器误差、偏置、`fireTimeNs`、回波和模式参数全部读回。只有当前零发射器偏置、零修正、模型变换等解析前提实际成立时，才能使用简化射线模型；不成立则先扩展并验证模型，不能忽略非零值。

不能把“设置了一个距离噪声参数”为零直接称作所有噪声均为零。静态资格轮需验证剩余数值误差是否满足第 10 节门槛。

### 6.2 主轮运动条件

| 条件 | 平移速度 | yaw 速度 | 每物理步角增量 | 相邻 10 Hz 扫描角增量 |
|---|---:|---:|---:|---:|
| `S0` | 0 | 0 | 0 | 0 |
| `R3P` | 0 | +3°/s | +0.05° | +0.3° |
| `R3N` | 0 | -3°/s | -0.05° | -0.3° |
| `R6P` | 0 | +6°/s | +0.10° | +0.6° |

主轮初始 yaw 为 0°。以局部整数运动步 `n` 计算绝对目标 `θ(n)`，生成 float64 位姿表；不要使用墙钟积分。保存四元数顺序、矩阵布局、乘法方向和角度单位，离线统一为明确的规范。

纯旋转中位置历史延迟不可辨识；静止条件中旋转历史延迟也不可辨识。不可辨识项填写 `unknown`，不能赋零或填写“无延迟”。

R3P 与 R6P 的完整 100 目标覆盖的朝向范围不同。比较速度/角增量效应时，另在两组已有数据中使用预登记的共同朝向 `0.6°、1.2°、…、30.0°`，并核验对应实际矩阵；完整结果继续保留，不按共同朝向子集替代总分母。

## 7. 连续调度与目标时间网格

### 7.1 初始化、计数器与暖机

1. 初始化前冻结配置、目标规则、输出拓扑、源码及运行次序。
2. 用固定初始化流程验证 PRE/POST 步号语义。记录实际 offset 和原始观测，不预设 PRE 计数器已代表本次完成步。
3. 产品附着后正常推进 24 次静态 app update；保存全部事件、实际物理步和时间。稳态请求为一次 update 对应一个物理步。
4. 从这段固定窗口验证至少两个可唯一关联的原生源 tick，其步间隔为 6。不得通过无限延长暖机等到“凑够通过数据”。
5. 若时间冲突或推进条件不成立，保留资格失败结果，修正入口后用新 run_id 重新资格。不能依靠几何误差推定时间偏移。

M_E/P_E 的初始化物理步数、产品附着时点和暖机条件应匹配。采样期间不 pause/resume、不重置 Timeline、不重新附着产品。

### 7.2 首目标及运动起点

令 `s=6`，暖机结束时当前物理步为 `k_cur`，暖机窗口内最后一个已唯一关联的源 tick 步为 `a`。在正式运动开始前固定：

```text
first = a + (floor((k_cur - a) / s) + 2) × s
motion_start = first - s + 1
target(i) = first + i × s，i = 0…N-1
last = first + (N-1) × s
```

`motion_start` 之前保持初始姿态；从该步起，每个物理步按表持续旋转。首目标已经历六个运动步，因此 R3P 首目标为 +0.3°，R3N 为 -0.3°，R6P 为 +0.6°。目标表应在进入运动前完整生成并保存。

跨 M_E/P_E 比较局部运动步、相对 tick 相位和实际目标矩阵，不直接相减不同进程的绝对源时间。若首次 tick 相位、首目标运动步数或实际输入不同，配对资格不成立。

### 7.3 固定运行终点与交付排空

主轮 `N=100`，首末目标间隔 9.9 个模拟秒。按固定物理步终点运行至 `last + 2 × s`，额外两周期仅用于有界交付排空；期间仍按相同角速度旋转，目标之外事件全部另存。

这一排空窗口是预登记的正常推进，不能按“尚未收到成功样本”动态加步。到固定终点后再结束采集并退出；如果最后目标仍未交付，登记缺失。

以下行为均另设干预组，不进入基线：采样前保持、重复渲染同一姿态、每个目标调用额外 orchestrator step、主动 fence/刷新 Fabric、按文件完成情况暂停物理、根据误差自动换后端。

M_E 与 P_E 使用相同原生 annotator 集合：`IsaacExtractRTXSensorPointCloud`、`GenericModelOutput`、`IsaacReadSimulationTime`、`ReferenceTime`。实际名称和同事件组织方式须以安装版本核验。

### 8.2 先保存再判断

原生输出入口先取得同事件元数据和合法载荷的自有 CPU 副本，交给有界后台保存，再记录可用的原生时间映射结果。时间关联和几何检查在离线进行。

不依赖异步任务继续访问已可能失效的原生数组；GMO 的完整字节取得方式要遵循安装版本的缓冲区契约，不解引用未经验证的指针。XYZ 与 GMO 分支分别保存，单个头字段解码失败不能抹掉另一份合法载荷。

布局非法、非有限值或无法安全复制的载荷保留错误记录，不通过过滤点、重排点或重新生成数据“修好”。GMO 有效标志用于官方定义的有效点提取，并同时报告原始数量、无效数量与有效数量。

### 8.3 离线唯一关联

关联范围为同一 run/epoch、同一产品和传感器。使用原始 source time、原生 ReferenceTime 映射与实际物理时间表交叉检查：容差 2 ns 内必须各自只有一个候选，且两个时间来源落到同一步。

容差只用于比较浮点 API 到整数时间的表示误差；不吸附到最近的 0.1 秒网格，不按回调顺序或点云最接近姿态配对。冲突、缺失和多解保留为 `unassigned/ambiguous`，不得择优。

读取当前原生映射 API 可在回调内、完成自有拷贝之后进行，以保留映射服务仍有样本时的结果；这不允许引入应用状态账本或以映射结果决定是否保存载荷。

目标分母固定为 N。重复事件不挑其中最好的一份，缺失和不合格目标不从分母删除。原生事件身份与本地 `receipt_seq` 分开记录；后者只是文件索引。

## 9. 独立几何分析与测量链资格

### 9.1 三条证据分别报告

1. 输入：目标表与实际 USD 世界姿态是否一致，物理步和扫描步角增量是否符合规定。
2. 原生元数据：有明确字段语义的原生 transform/pose 是否符合对应源时刻实际姿态。
3. 载荷：点云按源时刻实际姿态转换后，是否符合已知房间；原始距离是否符合该姿态下的解析射线交点。

解析几何使用源时刻的实际读回姿态，命令目标只用于输入资格。不得用原生 pose 头作为几何真值，否则可能使两个相同的错误相互抵消。

### 9.2 解析射线与坐标资格

从已保存的发射器参数和原生 emitter/channel/tick/echo 标识建立射线对应。XYZ 行号不能直接视为发射器编号，不以两帧点数相等推定逐行可比。

按已核验的方位角正方向、仰角、模型变换和矩阵约定构造世界射线，对六面房间计算最近合法正交点。保留 near/far、有效点和回波语义；有非零发射器偏置时必须显式建模。

测量链资格包括：

- 独立已知几何的轴向/斜向射线算例，以及正反转符号检查。
- 独立生成的 0、半步、一步、两步旋转控制，验证绝对误差与增量误差可分开识别。
- 在初始 yaw 为 0°、5°的静止资格轮分别核验解析模型，不用运动数据拟合扫描角定义。
- 全部目标完整 GMO 独立解码后，与 Extractor 的有效 XYZ 按原生标识和有效标志比对；不把位姿重新配准后的相似度当成字节一致。

原生头和提取器一致只能定位差异边界，不能单独证明场景几何正确。解析前提或解码布局不成立时，该分析记为 `unknown`，不强行套用既有公式。

### 9.3 绝对 yaw 与扫描角增量

用固定规则从有足够观测性的竖直墙点估计一个局部 yaw 残差，得到 `θ_geom`。在源时刻实际姿态下，按最近房间面分配点，最近面与次近面的距离差须至少为 0.05 m，且最近面必须是竖直墙；这份选择在拟合前固定，不随迭代重新筛点。保留各墙覆盖、参与点数和 yaw 雅可比信息量，规则不能随组别或误差大小变化。

本版要求至少 100 个参与点，其中至少两个法向不平行的竖直墙各有 32 个点，且 `ΣJ² ≥ 1 m²`。以零残差为初值，使用 float64、最多四次固定 Gauss–Newton 更新；拟合范围为 ±0.2°。观测数、信息量不够或求解失败记为 unknown；若拟合越界，标明超出测量范围，不能截断到边界值充作通过。合成控制和 S0/S5 必须先验证这些规则对本传感器成立；若需修改，发布新规则版本并重新资格。

局部拟合仅作误差测量，不能改写原始点云、时间戳或保存姿态。不得通过 ICP、逐帧配准或平移补偿使数据满足验收。

```text
输入物理步增量误差 = wrap(θ_actual[n] - θ_actual[n-1]) - ω/h
输入扫描增量误差 = wrap(θ_actual[i] - θ_actual[i-1]) - ω/f
几何绝对朝向误差 = wrap(θ_geom[i] - θ_actual[i])
几何扫描增量误差 = wrap(θ_geom[i] - θ_geom[i-1]) - ω/f
```

N 个目标产生 N 个绝对误差和 N-1 个相邻增量。首帧绝对误差单列。若其中一帧不可观测，相邻两对增量应标 unknown，不跨过该帧计算并冒称相邻扫描正常。

### 9.4 历史姿态候选

纯旋转主组预登记旋转候选为当前、前半步、前一步、前两步。半步为相邻实际姿态之间的最短弧中点，属于诊断合成候选，不代表已经取得内部插值权重。

各候选对同一份原始距离计算 P95 解析残差，先按姿态等价归组，再检查分离程度。静态候选等价时标 `unobservable`。最佳残差 ≤10 μm，且次佳组残差至少为最佳组的 10 倍、差值至少为 20 μm，才报告候选可区分；否则为 `ambiguous`。缺历史样本单列，不补造历史。

同时提供由几何 yaw 误差换算的描述性等效步延迟。符号使用已核验的运动方向解释，不把它直接命名为 SDK 实际延迟。候选只用于解释，不能用“存在一个旧姿态可拟合”替代当前目标的通过条件。

## 10. 预登记判据与三值结论

### 10.1 输入、测量资格与诊断质量

| 类别 | 判据 | 结果含义 |
|---|---|---|
| 推进资格 | 运动及固定排空阶段每 update 一个物理步；实际 dt 与 1/60 s 差 ≤2 ns；原生目标 tick 间隔 6 步 | 请求的 60/10 Hz 条件实际成立 |
| 输入资格 | 实际位置与表差 ≤10 μm；旋转差 ≤1e-6 rad；每物理步 yaw 增量误差 ≤2e-6 rad | 目标运动确已施加 |
| 时间关联 | 同事件 source/ref 差 ≤2 ns，且唯一关联到同一实际物理步 | 具备按源时刻解释的条件 |
| 配对资格 | M_E/P_E 全部目标实际位置差 ≤10 μm、旋转差 ≤1e-6 rad；首目标运动步数和相位匹配 | 可开展主要架构对照 |
| 静态解析资格 | S0/S5 短轮每目标解析射线距离 P95 ≤10 μm；坐标与解码控制通过 | 分析模型具备本轮适用性 |
| 原生姿态诊断 | 有语义资格的原生 pose 与源时刻实际姿态：位置差 ≤1 mm、旋转差 ≤1e-4 rad | 元数据一致性，单独统计 |
| 几何绝对一致性 | 每目标当前实际姿态下射线距离 P95 ≤10 μm、点到房间表面 P95 ≤5 mm，且可观测 yaw 误差 ≤1e-4 rad | 检查绝对载荷姿态；10 μm 是无噪声诊断门槛 |
| 几何增量一致性 | N-1 对相邻扫描几何 yaw 增量误差绝对值 ≤1e-4 rad | 检查帧间变化，不能替代绝对判据 |
| 数据完整性 | 所有 N 个目标各唯一事件；原始保存与回读 SHA/布局正确；GMO/Extractor 对应一致 | 排除缺失、择优与保存损坏 |

上述 yaw 门槛约为 0.00573°，可区分 3°/s、60 Hz 下的半步偏差 0.025°。阈值在运行前冻结，不能看到结果后抬高。输入扫描增量另按两端各 1e-6 rad 输入误差检查，容差为 2e-6 rad。

静态与纯旋转中不可辨识的时间延迟不进入通过声明。微米级门槛只适用于本轮解析无噪声诊断，不是现实 LiDAR 精度要求，也不覆盖原始生产场景。

### 10.2 分开保存终态

```text
capture_complete: true / false
measurement_qualified: true / false / null
pair_equivalence_qualified: true / false / null
clock_ok: true / false / null
native_pose_ok: true / false / null
geometry_absolute_ok: true / false / null
geometry_increment_ok: true / false / null
payload_generation_freshness: true / false / null
cleanup_ok: true / false / null
diagnostic_pass: true / false / null
formal_continuous_acceptance: false
```

`measurement_qualified` 检查输入、推进、数据布局/坐标解析资格和源时刻可解释性，不要求旋转几何先通过。旋转几何失败是待测结果，不能导致资格轮被当作“无效数据”丢弃或停止整个对照。

`diagnostic_pass` 需要采集完整、测量与数据完整性合格，且所有目标时间、原生姿态、绝对几何和全部相邻增量通过，退出清理通过。任一明确失败为 false；必要项缺证据为 null。配对资格是跨组归因条件，独立于单组质量。

载荷重算新鲜度另作三值报告：新时间戳、新回调、静态字节相同均不足以单独证明或否定原生重算。运动几何随目标正确变化可约束旧载荷复用假说，但不能补造不可观察的内部生产证据。该项未知时保留未知，本轮诊断通过仍不等于正式生产通过。

### 10.3 统计要求

每个重复分别报告 N 个目标的缺失、重复、关联冲突、原生姿态失败、绝对几何失败、unknown；角增量分母为 N-1。列出时间/原生姿态/几何的 pass-fail-unknown 交叉表。

残差报告 P50、P95、P99、最大值及带符号序列。分位数固定使用 nearest-rank。不能只报告平均角增量、平均绝对误差或合并三轮后的单一百分比。

## 11. 运行矩阵、次序与分支

### 11.1 第一阶段：实现及资格轮

M_E、P_E 各运行三个独立短轮：`S0`、初始 yaw=5°的静态 `S5`、`R3P`，每轮 12 个计划目标。合计 6 轮、72 个目标，单独计数。

先检查静态解析、所有权、实际推进和事件可解释性。R3P 即使复现几何失败，只要测量资格成立，仍允许进入主轮。资格失败修复后使用新规则/入口版本和新 run_id，保留原结果。

M_E/P_E 在首轮正式运行前锁定代码和配置；主轮期间不热更新。

### 11.2 第二阶段：必做主轮

M_E、P_E 分别完成 S0、R3P、R3N、R6P，每条件 100 目标×3 次独立初始化。合计 24 轮、2,400 个目标。

条件顺序固定为 S0→R3P→R3N→R6P。每个条件内部顺序固定为：

```text
M_E-r01 → P_E-r01 → P_E-r02 → M_E-r02 → M_E-r03 → P_E-r03
```

三轮既检验重复性，也用于降低简单运行先后次序的混杂；不因此宣称统计上排除了所有机器状态因素。不得同 GPU 并行运行多个 Kit。不同重复使用独立 Kit 进程和场景，保存启动/缓存状态，不在条件间随意清缓存。

### 11.3 第三阶段：推荐配置对照

M_D 先完成 S0/S5/R3P 三个 12 目标资格轮，再完成 S0、R3P 各 100×3。若与 M_E 存在差异，按预登记追加 R3N/R6P 或单开关干预；不能在看过结果后只保留较好的条件。

如果配置 D 无法维持相同 10 Hz 输出语义、补偿模式或测量字段，应标为条件不成立，转为另一个明确命名的实验；不能将其作为 M_E 的严格配置对照。

### 11.4 按证据追加的范围

| 触发证据 | 后续实验 | 目的 |
|---|---|---|
| M_E 通过而 P_E 失败，配对资格成立 | 从 M_E 逐项接回状态账本、目标筛选、产品管理和原调度封装，每次一项 | 定位引入异常的最早应用边界 |
| M_E/M_D 差异稳定 | 以 M_E 为底一次改变一个配置；必要时再做交互组合 | 从配置组收敛到具体因素 |
| 两者相同角度/角增量出现相同历史候选 | 120 Hz 的同角速度/同每步角增量及相同绝对朝向控制 | 区分秒延迟、步延迟和角度依赖 |
| 只在特定初始姿态或采样相位出现差异 | 初始 yaw 与相位控制，先冻结网格 | 检查初始化和相位因素 |
| 纯旋转最小路径通过，需要恢复原混合任务 | 0.3 m/s＋3°/s 匹配混合运动 | 检查结论能否延伸到移动采集 |

扩展条件另存运行清单和规则版本。首轮不展开全部可选矩阵，以保持最小复现的可解释性。

## 12. 结果解释边界

| 观察 | 可以支持的结论 | 仍不能声称 |
|---|---|---|
| M_E 与 P_E 均失败，配对合格且模式一致 | 异常复现不需要现有复杂框架，优先检查共同原生路径、配置及使用方式 | 已证明 NVIDIA SDK 某个函数存在缺陷 |
| M_E 通过、P_E 失败，配对合格 | 存在最小正确路径；应用架构差异值得优先定位 | 已定位某个具体模块，或生产链已修复 |
| M_E 失败、M_D 通过 | 配置组或配置交互改变了行为 | 组内某一个开关已被证明是根因 |
| 原生 pose 通过、几何失败 | 元数据不能证明实际载荷正确 | 原生头可用来修正点云并宣布原始数据通过 |
| 增量通过、绝对几何失败 | 存在固定偏差或其他绝对姿态不一致的可能 | 训练数据姿态配对合格 |
| 两组都通过而历史失败未复现 | 本轮条件下未观察到旧异常，应比较版本、初始化和配置差异 | 已解释历史故障或完成根因修复 |
| M_E 失败、P_E 通过 | 最小入口的使用方式或两组未控制差异需复查 | 最小入口代表原生必然行为 |
| 静态通过 | 坐标与静态几何可用，可观察时钟正常推进 | 已证明动态历史或重算新鲜度正确 |

只有测量和配对资格成立时，才作主要架构归因；条件不成立时继续报告真实观测，但降低结论范围。

实施顺序为：核验安装构建与原生 API→冻结 E/D 和依赖边界→独立实现最小采集/分析→完成测量控制→资格轮→锁定主轮→全量离线回读→结果报告。文档中的后续命令应在工具实际存在并验证后填写，不提供看似可运行的虚构命令。

### 13.2 有界资源

初始预算：每轮初始化 180 s，总墙钟 600 s，后台队列 256 MiB，XYZ/GMO 单份载荷各不超过 64 MiB，原始未压缩证据预算每轮 2 GiB，轻量 trace 预算 128 MiB。RSS 上限取 `max(4 GiB, 2 × 初始化完成时 RSS)`，实际值在运动前保存。总墙钟从进程启动计，覆盖初始化、采集和退出；退出仍必须尝试执行有界清理。

每批最多 4 轮，开始前根据资格轮实测每事件大小计算预计用量，并额外保留至少 8 GiB 空闲空间。若不够，减少后续批次规模；不删除历史结果、不通过丢点/降分辨率维持预算。完整矩阵需要多批容量规划，不能用单轮预算代表全矩阵预算。

所有 M_E/P_E 采用相同保存策略，压缩在后台进行，预算按原始字节保守计。队列满、保存失败、磁盘/RSS/时间超限时终止该轮并保留前缀；不暂停物理等待队列排空，不悄悄丢帧。

### 13.3 退出与生命周期

在固定采集终点结束后，关闭本轮回调、Writer、产品与自有进程，并有界完成自有保存。记录异常、完成物理步、最后源事件和清理结果；清理失败与采集质量分开报告。

本方案默认独立进程；若使用共享 GUI，必须另列设置恢复验证，不能直接套用独立进程生命周期结论。不会为本实验改变旧 v06、原始 USD 或已有 READY 数据。部署和远端执行属于后续实施阶段，当前文档编写不表示已经连接或启动实例。

## 14. 实验交付与完成定义

必须交付：

1. 独立最小入口、运行依赖说明、源码哈希和真实命令。
2. 预登记 spec、E/D 有效设置、分析规则、全部运行次序及资格结果。
3. 全部原始合法载荷、完整 GMO、物理姿态、源事件和 SHA/布局回读报告。
4. 每目标的输入、时间、原生 pose、绝对几何、相邻增量与候选结果，包括缺失、重复和 unknown。
5. M_E/P_E 配对资格、三次重复对比及 M_D 的实际执行范围。
6. 源时间—物理步图、目标/几何绝对 yaw 与带符号误差图、扫描增量误差图、历史候选分布图。图不能只画去除初始偏差后的轨迹。
7. 单独的新执行报告，清楚分列已证实事实、受支持解释、仍未观察的内部状态和下一步。

本轮完成定义：必做 M_E/P_E 矩阵完成或因明确资格/资源问题留下可解释的终态；全部已采证据回读完毕；明确回答独立最小链路是否复现、架构对照是否成立、角增量与绝对几何是否分别通过。若必做矩阵因阻断未完成，状态填写“部分完成”，不以方案交付代替实验完成。

单个条件的通过仅证明所测构建、资产、配置、轨迹与时长下的诊断一致性。后续训练数据生产还需验证混合运动、原场景、多传感器、载荷新鲜度及长期运行。
