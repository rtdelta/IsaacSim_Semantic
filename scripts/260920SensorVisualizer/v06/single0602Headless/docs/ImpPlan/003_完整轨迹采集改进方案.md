# single0602Headless 完整轨迹采集改进方案

更新日期：2026-10-19（北京时间）。方案版本：003。状态：已实施，运行包版本 0.3.0；短程全传感器采集、尾端、指定范围和 Pause/Stop 回读已通过。具体证据和范围见 [验证记录](../Testing.md)，以下保留设计及验收契约。

本方案补充 [001 实现方案](001_single0602Headless_实现方案.md) 和 [002 连续交互改进方案](002_连续交互改进方案.md) 中的正式离线采集参数、计划和结果展示。002 的连续交互、逐步位置设置、零物理速度及 Stop 结束轨迹规则继续有效。

## 背景与核心目标

改进前网页必须填写“最多组数”，默认值为 100。后端在启动时将其限制到轨迹可采集组数以内，但没有“完整采集所选轨迹”的入口。用户必须先知道轨迹时长，再根据采样频率计算组数，容易只采到轨迹前段。

本轮目标：

1. 在传感器采集区新增“采集范围”下拉框，提供“完整轨迹”和“指定最多组数”，网页默认选择“完整轨迹”。
2. 完整模式由后端自动生成覆盖全部有效采样网格的有限采集计划，用户只需选择轨迹和采样频率。
3. 启动前显示时长、计划组数和最后采样时间；启动后按最终任务计划显示实际进度。
4. 区分按计划完成、用户提前停止和失败，单独显示数据排空及进程资源释放状态。
5. 保留指定组数方式及旧接口、旧任务配置、已有完整轨迹的使用能力。

## 采样范围与尾端规则

“完整轨迹”定义为：按所选仿真采样频率，从轨迹相对起点开始，采集轨迹时间范围内的全部有效网格点。

- 轨迹时长 `T = last_state_time - first_state_time`，执行时使用任务私有轨迹快照的实际时长。
- 采样频率为 `f`，采样时刻为 `t_k = k / f`，从 `k=0` 开始。
- 可用组数 `N_available = floor((T + epsilon_s) * f) + 1`，每个计划时刻还需满足同一终点判定。
- 统一使用 `epsilon_s = 1e-8` 秒处理网格边界的浮点误差，计划计算与执行源终点检查共用此规则。它只容纳数值表示误差，不增加正常网格以外的尾帧。
- 完整模式：`N_planned = N_available`。
- 指定模式：`N_planned = min(N_requested, N_available)`，超过轨迹长度时显示实际可采集组数。
- 最后计划采样时间为 `(N_planned - 1) / f`，不能用页面四舍五入后的时长反推组数。

| 轨迹时长 | 采样频率 | 完整模式组数 | 最后采样时间 |
| --- | --- | --- | --- |
| 26.5 s | 10 Hz | 266 | 26.5 s |
| 26.53 s | 10 Hz | 266 | 26.5 s |
| 0.05 s | 10 Hz | 1 | 0 s |
| 0 s，包含有效状态 | 10 Hz | 1 | 0 s |

26.53 s 的例子中，末尾 0.03 s 不足一个采样周期，页面应说明“末尾不足一个采样周期，未追加非等间隔尾帧”。若后续要求最终姿态无论是否对齐网格都单独采集，应另增明确的尾帧策略；本轮保持等间隔采样。

完整模式仍使用现有完整状态重放、插值和 Direct/安装 revision 跳变规则。它按采样网格产生传感器组，不把每条轨迹状态或控制事件分别变成一组传感器数据。例如最近核验的轨迹有 1592 条状态、时长约 26.5 s，10 Hz 下应计划 266 组。

采样频率沿用现有任务契约：有限、正数，不超过 `physics_hz`，且能整除物理频率；默认 `physics_hz=60`、`sample_hz=10`。不在本轮开放任意频率或逐条状态采集模式。

## 页面与用户流程

传感器采集区调整为：

```text
采集范围        [完整轨迹 ▼]
仿真采样 Hz     [10]
采集计划        26.5 s · 10 Hz · 预计 266 组 · 最后采样 26.5 s
                [Start Recording]
```

切换为“指定最多组数”后显示组数输入，初始保留 100。切回完整模式时隐藏并禁用该输入；再次切回指定模式可保留本页草稿，但完整模式提交时不携带草稿组数。

交互规则：

1. 选择已完成轨迹，或修改采集范围、采样频率、指定组数后，重新请求计划预览。
2. 预览只在相关参数变化时请求，输入采用短防抖；不在现有 200 ms 状态轮询中重复全量加载轨迹。
3. 新预览返回前标记“计算采集计划”；使用请求序号或取消机制丢弃过期响应，防止切换轨迹后显示旧计划。
4. 无有效轨迹、轨迹未完成、校验失败、参数无效、预览未就绪或已有采集任务/清理占用时，禁用 Start Recording 并给出具体原因。
5. 正式采集可在交互控制器退出后启动；计划预览和启动条件不依赖 GUI owner 连接。
6. 启动响应返回最终计划；页面使用它替换预估，任务卡显示所选范围、已采集/计划组数、已写入组数和源轨迹时间。
7. 页面的范围或频率修改只影响下一次任务，已启动任务继续执行自己的快照计划。

网页默认完整模式是本轮产品行为变化。旧接口未提供范围字段时仍按旧的指定组数规则处理，不能因页面默认值而改变旧调用的含义。

## 请求、预览与兼容

新增请求字段 `capture_scope`，其取值为 `full_trajectory` 或 `group_limit`；现有 `mode=offline` 继续表示运行方式，不能复用该字段表达采集范围。

完整模式请求示例：

```json
{
  "mode": "offline",
  "trajectory": "/项目输出目录/trajectories/已完成轨迹",
  "capture_scope": "full_trajectory",
  "sample_hz": 10
}
```

指定组数请求增加 `"capture_scope": "group_limit"` 和 `"groups": 100`。

兼容和校验规则：

- 未提供 `capture_scope`：按 `group_limit` 处理，未提供 `groups` 时保留 100 的历史默认值。
- 显式 `full_trajectory`：`groups` 应省略或为 null；同时传入非空组数时拒绝，提示参数冲突。
- 显式 `group_limit`：要求合法的正整数组数；拒绝布尔值、零、负数、小数和非数值。旧调用中的合法正整数继续有效。
- 拒绝未知范围、无效频率、空轨迹、不完整轨迹、非有限或负时长，以及现有路径/资产/坐标/文件完整性校验失败。
- 自动计算发生在调用最终 `load_job` 前，最终执行配置中的 `groups` 始终是确定的正整数；不将 0、-1、null 或无限循环传给采集运行器。

增加只读预览入口 `GET /api/capture_plan`，接收所选轨迹路径、`capture_scope`、`sample_hz` 及指定模式的 `groups`。预览返回时长、可用组数、计划组数、起止采样时间和尾端说明；不得创建任务目录、启动进程或申请采集锁。

预览与启动复用同一套计划计算和参数校验。预览可以复用按文件身份校验的轨迹摘要以减少重复读取；启动时必须重新校验轨迹并基于任务快照生成最终计划，不能把浏览器预览当作权威结果。

命令行同步增加 `--all-trajectory`，与显式 `--groups N` 互斥：

```bash
/usr/bin/python3 run_capture.py --trajectory /完整轨迹目录 --all-trajectory --sample-hz 10
```

原有命令行调用未提供两者时继续按 100 组处理。参数解析使用“是否显式提供组数”判断互斥，不能因历史默认 100 导致完整模式始终冲突。任务子进程读取已生成的 `--job`，无需重新解释网页选择。

## 后端计划与执行

建议新增纯标准库模块 `single0602_headless/capture_plan.py`，集中负责范围解析、采样频率和请求组数校验、可用/计划组数计算及终点判定；避免网页、CLI、supervisor 和执行源各自复制公式。

启动流程：

```text
校验请求、资源占用和完整轨迹
→ 保存并重新加载任务私有轨迹快照
→ 从快照计算最终采集计划
→ 写入确定的 job、计划和任务信息
→ 启动独立 Headless
→ 执行各采样网格点并保存
→ 核对计划、采集和写入数量
→ 排空文件、退出进程、释放资源
```

保持现有路径边界、资产哈希、原点、关节、swing 零位与时间版本检查。请求和预览参数错误应尽量在创建任务目录前返回；快照或启动阶段失败时保留明确的失败记录，不发布虚假的运行中任务。

在 `job.json` 中增加独立的 `capture_plan` 信息，至少包含：

| 字段 | 含义 |
| --- | --- |
| `schema_version` | 计划格式版本，首版为 1 |
| `scope` | `full_trajectory` / `group_limit` |
| `requested_groups` | 用户指定组数；完整模式为 null |
| `sample_hz` | 已验证的采样频率 |
| `trajectory_duration_s` | 快照实际时长 |
| `available_groups` | 轨迹的全部有效网格数 |
| `planned_groups` | 本次实际计划组数，与 `job.groups` 一致 |
| `first_sample_time_s` / `last_sample_time_s` | 本次计划采样范围，相对于轨迹起点 |
| `time_tolerance_s` | 统一的浮点边界容差 |

来源路径、快照及文件哈希继续由现有任务快照元数据提供，不重复伪造来源。计划摘要同时保存到 `task.json`，使网页重启后、子进程尚未生成状态时，也能恢复范围和计划组数。

新运行器读取包含计划的任务时，应核验快照时长、频率、组数和计划相符；执行源若在计划完成前意外耗尽，应报告失败并保存已采集结果，不能静默当作完整完成。

已有无 `capture_plan` 的任务配置继续执行原来的确定组数语义；展示为“历史任务”，不补写或宣称其拥有新计划验证结果。

## 完成、停止与结果展示

保持 `capture_complete` 表示计划组是否全部生成，`record_drain_complete` 表示保存管线完成排空；进程退出和资源锁释放仍分别观察。新增结果字段区分 `completion_reason`：`completed_plan`、`stopped_by_user`、`failed`。

| 情况 | 结果展示与判定 |
| --- | --- |
| 完整模式，所有计划组成功生成且写入/排空通过 | 显示“完整轨迹采集完成”，实际组数和写入组数均等于计划；计划本身等于可用网格总数 |
| 指定模式，所有计划组保存完成 | 显示“指定范围采集完成”，同时展示实际采样终点；组数上限截短轨迹时明确显示 |
| Stop 导致计划未完成，已成功排空 | 显示“提前停止，已保存 X / N 组”，`capture_complete=false`，保留有效数据 |
| 计划已完成后才收到 Stop | 以实际完整结果为准，不因晚到的停止请求改成“提前停止” |
| 采集、来源、数量核对或写入失败 | 显示失败及原因，已生成/已写入/排空状态分别保留，不能宣称完整完成 |
| 排空完成但进程尚未退出或锁尚未释放 | 显示“数据保存完成，正在释放资源”，继续禁止下一任务 |

任务状态、最终 `session.json` 和页面使用同一结果语义。页面的任务更新判断应包含计划、完成原因、写入、排空和资源状态，避免只按 `state/groups/running` 判断而漏刷新。

不根据采样频率承诺墙钟采集耗时；10 Hz 描述轨迹时间网格。长轨迹会产生更多数据和更长运行时间，继续使用既有有界管线和 MCAP 分段，不自动降频或跳过组。

## 验收标准

### 计划与接口

- 覆盖 26.5 s / 10 Hz → 266 组，非网格尾端 26.53 s → 266 组，短于一周期和有效零时长轨迹 → 1 组。
- 覆盖网格边界浮点误差以及容差两侧，保证计划最后时刻与执行源终点判断一致，无多一组、少一组或超出来源。
- 指定组数小于、等于、大于可用组数均正确；频率更改同步改变计划，非法频率及组数明确拒绝。
- 旧 API 无范围字段、旧 CLI 默认 100、旧无计划 job 继续按原有合法语义工作；新 CLI 互斥参数正确报错。
- 预览不创建任务、启动进程或取得锁；损坏、不完整轨迹和路径越界被拒绝。
- 启动最终计划来自快照，用户之后切换页面参数不会改变正在运行的任务。

### 页面与生命周期

- 默认完整模式，切换后正确显示/隐藏组数；完整模式请求不携带残留组数。
- 快速切换轨迹/频率时不显示旧请求的计划，不误启旧选择；无 GUI owner 时完整离线任务仍可预览和启动。
- 完整/指定计划、写入进度、排空与资源释放能正确刷新；刷新网页或重启网页服务后恢复已有任务状态，不重新启动任务。
- Pause/Resume 不改变计划且不重复组；中途 Stop 只保存已完成组并准确显示部分结果；计划完成后晚到的 Stop 不误报提前终止。
- 来源提前耗尽或保存失败时不显示完整完成，失败原因和已保存范围可追踪。

### 实际 Headless 与独立回读

- 使用短完整轨迹及带非网格尾端的短轨迹验证完整模式，确认自动结束、排空、进程退出和锁释放。
- 用指定组数模式执行短程回归，并至少一次验证完整模式 Pause/Resume/Stop + Drain。
- MCAP 回读核对实际组数、首末源时间、无重复/缺失网格、既有 topic/TF/传感器/关节和载荷规则；只生成计划不能代替真实数据验收。
- 对最近的 26.5 s 轨迹验证预览与最终计划均为 266 组；短程验收不冒充这条长轨迹的全量实采结果。实际全量任务按用户后续采集安排执行。

2026-10-16 首次制定方案时未运行上述功能测试；2026-10-19 已实施并验证，结果记录于 Testing、OperationRecord 和 reports。短程验证不代表长轨迹全量采集或长期性能验证。

## 可行性、边界与后续事项

可行性高：现有 supervisor 已有时长限幅、任务快照和独立进程，运行器已有有限组数循环及排空流程。本轮重点是统一计划规则、明确范围和结果语义、完善页面入口与兼容测试。

当前实现采用以下决策：网页默认完整轨迹；按所选频率覆盖全部有效网格；不足一周期的尾段不追加不等间隔尾帧；旧调用保留指定组数默认值。

后续另行讨论的需求包括：最终姿态额外尾帧、逐条轨迹状态采集、指定起止区间和中断后断点续采。002 中其他运动对象记录/重放的 TODO 继续保留；本轮“完整轨迹”不扩大其场景复现承诺。

## 实施落点

- `capture_plan.py` 使用 Fraction 计算网格数，计划及执行源共享 1e-8 秒边界规则；预览在参数变化时请求，无 200 ms 全轨迹重复加载。
- `capture_supervisor.py` 在任务私有快照形成后重新生成计划并校验 job，写入 job/task；启动失败保存原因并释放租约。
- `replay_capture.py` 核验新计划和快照、核对最终写入数量，明确完整、部分停止和失败；历史无计划 job 保留兼容入口。
- 实际短测均使用从既有完整轨迹派生、明确标识的独立测试轨迹，不改写用户轨迹；完整网格和尾端各 3 组，指定范围 2 组，Pause/Resume/Stop 保存 4/21 组，均完成全传感器 MCAP 回读。
