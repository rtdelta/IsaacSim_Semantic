# 单参数场景加载与自动绑定实现方案

日期：2026-10-22（北京时间）。状态：0.5.0 已实现，test 单卡原生验收结果见文末执行记录。

本次修订：标准挖掘机结构只约束机械接口，不要求任何传感器。传感器改为全场景自动发现，
允许车载、固定于环境以及独立安装的设备；取消固定名称、固定数量和必须同时存在相机/雷达的要求。
补充预留 IMU 类型、物理步驱动及数据接口，先用 Isaac Sim 官方原生 IMU 资产/示例做独立验证；
通过正式同步验收前不将 IMU 自动加入相机/雷达采集任务，不改变现有机械运动模型。

适用项目：single0602Headless。实现前基线：0.4.0；本轮交付版本：0.5.0。

本文件保留设计时的目标与用例矩阵；实际执行范围以文末记录及验收摘要为准。
既有场景编辑与跨环境采集能力继续遵循 [004 方案](004_场景编辑与跨环境轨迹采集_实现方案.md)。

## 1 核心目标

用户通过一个 `--scene` 参数指定新的完整 USD 场景。程序加载场景、发现唯一标准挖掘机、
绑定机械关节，并独立扫描整个 Stage 的传感器、分类和检查能力，成功后进入可录制状态。

常规换场景不修改 Python，不复制或编辑 job JSON，不登记场景文件哈希，不逐项运行人工绑定脚本。
网页与交互 GUI 仍按原流程分别启动；本轮不增加进程编排服务或一键启动全部服务。

必须达到以下结果：

1. 新场景路径成为交互入口的一等参数，兼容 `--job` 高级配置和现有默认启动方式。
2. 机械绑定与传感器配置解耦；挖掘机资产可以不带任何传感器，不要求相机或雷达位于机器人子树。
3. 检查自动执行，成功显示绑定摘要，失败定位到具体节点或字段，并给出可执行的修复提示。
4. 本次最终配置、实际资产绑定与轨迹保持一致，正式采集继续使用任务自己的不可变快照。
5. 延续 1× 交互目标、逐帧离散位置结算、物理速度清零、Stop 结束当前文件的既定行为。
6. 参照 v04 的 Stage 索引与类型适配机制，全场景发现相机和雷达，形成候选清单、能力状态和可选采集清单。
7. 根据实际承载关系处理传感器位姿：车载设备随对应刚体运动，环境固定设备保持世界位姿，不因挖机摆放而移动。
8. 支持零传感器交互录制、仅相机、仅雷达和混合采集；正式采集至少选择一个可采集设备，不生成占位传感器。
9. 预留 IMU 的发现、配置、承载参考、原始读数和导出契约；首阶段验收官方资产的接口读通，正式多传感器同步另设能力门槛。

以下为方案编写时的源码事实；修改前应再次核对实际工作区。

| [交互运行器](../../single0602_headless/interactive_runtime.py) | 轨迹记录实际根层、机器人绑定、运动与传感器接口 | 引用本次配置与绑定报告，确保网页和录制元数据一致 |
| [采集监督器](../../single0602_headless/capture_supervisor.py) | 根据轨迹元数据选场景、创建私有任务与轨迹快照 | 将所选 profile 和可移植绑定信息传入正式采集，避免重新使用不匹配的默认值 |
| [传感器接口描述](../../single0602_headless/scene_replay.py) | 目前要求传感器属于挖掘机刚体，路径相对机器人 | 区分机械接口、车载传感器和世界固定传感器，分别处理重放 |
| [消息输出](../../single0602_headless/messages.py) | 相机信息目前固定为鱼眼表达；传感器 TF 统一挂在 swing 参考下 | 按真实镜头模型编码，环境固定设备使用 world 参考，按实际清单生成通道 |

目前 `run_capture.py` 使用 `parse_known_args()` 向 Kit 转发部分参数；新增参数必须由本项目显式解析，
不得把 `--scene` 交给 Kit 后误认为本项目已经选择了场景。
当前 `--output` 和 `--asset-profile-id` 主要在轨迹采集分支使用，交互分支需一并贯通。

参考 semantic world module v04 的两条流程：场景路径进入配置快照后加载；全 Stage 索引经过传感器适配器匹配后形成候选。
v04 的候选发现不局限于挖掘机，Camera 的普通和鱼眼匹配可能重叠，需要合并并优先选择专用适配器。
v04 将发现和选择分开。本项目为保持常规接入简单，新增“自动选择全部可采集候选”的默认策略，仍允许取消或显式选择。
本轮参考其模块边界，不直接引入 v04 完整项目系统、插件加载系统或运行依赖。

## 3 功能边界

| 情况 | 本轮承诺 |
| --- | --- |
| 更换静态地形、建筑、材质、背景及灯光 | 支持，目标机能够解析必要资源 |
| 同一标准挖掘机改变初始摆放 | 支持，从目标场景读取，不套用 scene18 的摆放位置 |
| 替换挖机外观，保持标准运动接口 | 支持，不要求外观资源或传感器布置与旧文件一致 |
| 挖机外部命名空间变化，例如根节点变为 `/Site/Machine` | 支持；内部相对层级和节点名保持标准约定 |
| 挖机没有传感器，场景其他位置有传感器 | 支持，传感器从整个 Stage 发现 |
| 整个场景没有可采集传感器 | 允许机械交互和轨迹录制；正式采集入口说明原因并拒绝空任务 |
| 相机/雷达名称、数量、所属父节点变化 | 自动发现；不要求 13 路雷达、4 路相机或固定 Fisheye 名称 |
| 普通透视相机、原生鱼眼和 RTX LiDAR | 按类型与属性识别；正式采集是否可用由具体镜头模型和运行后端能力检查决定 |
| 官方原生 IMU | 预留全场景发现与物理步读数接口，用官方资产/示例独立验证；正式任务默认不选入，后续同步验收通过再启用 |
| 仅相机、仅雷达，或车载与车外设备混合 | 支持；按实际选择清单初始化、采集、写入和验收 |
| 新场景录制完成后沿该轨迹采集 | 支持；默认使用轨迹记录的实际场景 |
| 旧轨迹在新环境采集 | 使用既有 `environment` 流程，不隐式改变采集目标 |
| 名称与层级相同，但关节枢轴、轴向、机构尺寸或零位改变 | 属于新的运动接口适配，不因同名而自动放行 |
| 多台挖机、额外运动自由度、闭链机构 | 不纳入首版 |
| 未适配的传感器、扫描时序或镜头模型 | 能识别的候选展示类型和不可用原因；不声称自动获得采集能力，不冒充已支持类型 |
| 安装在其他运动设备上的传感器 | 可识别并报告承载关系；该设备的运动重放不在本轮范围，不能作为固定设备悄然放行 |
| 运行中切换 Stage、热换资产、跨 Stop 续写轨迹 | 不实现；切换前结束旧流程，再重新启动 |
| 地形贴合、自动避障、自动选择作业区域 | 不实现；旧轨迹摆放继续使用显式平移和绕 Z 旋转 |
| 其他对象的运动记录与重放 | 保留 TODO，验收以静态环境为范围 |

1× 是交互目标，不承诺任意复杂场景都能达到实时速度；继续显示实际播放倍率。
不新增碰撞、受力、接触响应验收，不新增机械轨迹的速度、角速度和加速度求解或采集字段，也不引入逆运动学求解。
IMU 自身的原始加速度、角速度和姿态属于新预留的传感器数据契约，不能据此推导或改写机械运动状态。
SDK 所需的刚体与 Articulation 接口仍必须有效。

## 4 对资产的要求

### 4.1 必须满足的约定

| 编号 | 要求 | 核验方式 |
| --- | --- | --- |
| A1 | 入口是目标 Linux 实例可读的完整 `.usd`、`.usda` 或 `.usdc` 场景文件 | 启动器检查路径、可读性和扩展名，Isaac 检查实际加载结果 |
| A2 | `metersPerUnit=1`，Z 向上 | 自动读取 Stage 元数据 |
| A3 | 必要 USD 引用、payload、纹理和传感器资源能够解析 | 组合错误、必要资源解析检查及首次短采确认 |
| A4 | 恰好一台符合标准接口的挖掘机，公共根节点不混入其他设备 | 机器人发现及唯一性检查 |
| A5 | 标准五刚体、四转动关节，机械连接正确，没有额外待控制自由度 | 关节关系和实际 Articulation 检查 |
| A6 | 关节轴、两侧局部关节框架、零位声明与已选标准 profile 一致，限位有效 | 组合 Stage 接口核对、初始化读回；旧轨迹重放再核对角度范围 |
| A7 | 控制骨架不含镜像、剪切、退化或意外尺度变化 | 初始变换和运动接口检查；外观的既有缩放保留在 Visuals 等外观层 |
| A8 | 传感器无固定名称、数量和车载要求；有设备时通过真实类型、schema 和属性识别 | 全 Stage 扫描；每个候选分别报告可发现、可采集、已选择和不可用原因 |
| A9 | 被选设备的配置、真实镜头/扫描模型及位姿参考有效；正式采集至少一个设备 | 按适配器逐项验证；安装编辑能力单独检查，不能编辑不等于不能读取采集 |
| A10 | 多个可见 DomeLight 时明确选择目标；零个或一个可见时允许自动规则 | 自动列出候选，必要时提示 `--background-dome` |
| A11 | 环境在录制及采集中保持静态，不依赖未记录的动画或外部运动脚本 | 场景提供方确认，首次接入观察；不宣称自动识别全部动态行为 |
| A12 | 源文件没有保存上轮控制器的保留运行节点或临时控制层 | 检查保留命名空间；运行修改仅写入可移除会话层 |

“初始资产”包括根 USD 实际组合使用的资产及必要资源。根文件存在不足以证明完整场景可用。
已有 Isaac 内置资源使用当前安装提供的解析路径，不要求复制一份到场景目录。
纹理、HDRI 不做每次启动的全量内容哈希审计，首次接入仍需检查图像表现和缺失资源警告。

### 4.2 标准内部结构：仅机械接口

下图的 `<robot_root>` 由程序发现，不要求场景中一定存在 `/World/Excavator`。
五个刚体按现有标准保持平级，机械连接由 joint 的 `body0/body1` 表达。
此结构不包含必需传感器节点，传感器可以位于该树内部或场景其他位置。

```text
<robot_root>
├── track_link
├── swing_link
├── boom_link
├── arm_link
├── bucket_link
└── Joints
    ├── swing     track_link → swing_link
    ├── boom      swing_link → boom_link
    ├── arm       boom_link → arm_link
    └── bucket    arm_link → bucket_link
```

机械角色仍按已支持的关节命名与拓扑识别，不通过宽泛字符串替换推断未知机械资产。
已有整套 legacy 关节名的兼容分支保留，但仍要求有对应的已核验运动 profile，首版新增资产推荐标准短名称。

传感器的以下布置均合法，示例节点名没有接口含义：

```text
/Site
├── Machine                     单台标准挖掘机，可不带传感器
│   └── boom_link
│       └── AnyCamera           可选车载相机
├── Tripod
│   └── AnyCamera               环境固定相机，同名也应有不同 ID
└── Gantry
    └── AnyLidar                环境固定雷达
```

相机无需叫 FisheyeFront，雷达无需用 sensor 作为叶节点名；类型判定以组合后的 USD 定义为准。
13 雷达和 4 相机只是 scene18 的回归样例，不是接入门槛。

### 4.3 零位与传感器配置分别管理

标准 profile 是运动接口约定，不能因换了场景就用目标资产反向生成一份“检查必过”的 profile。
保持当前原生角度约定，不自动引入旧 URDF、历史 bag 或其他项目的角度偏移。
swing 工程假定零位及其原生读回检查继续保留；工作关节的零位由标准资产的原生装配定义表达。

新场景录制读取该场景实际传感器清单，允许与 scene18 完全不同，也允许清单为空。
不把传感器数量、命名或车载关系放进机械 profile 的准入条件。

传感器的“可识别”“可采集”“可编辑安装”分别记录。参数缺失、模型不支持或不可编辑均应显示具体原因，
未被选入采集的故障设备不阻断机械录制；显式选入后不得静默跳过。
相机内参、成像尺寸和镜头模型取自资产有效值及有来源的渲染配置，不虚构统一标定或把所有相机写成鱼眼。
普通 USD Camera 未携带输出分辨率时采用有明确来源的项目渲染默认值，允许覆盖并保存到快照；
该分辨率是本次采集配置，不能标记为资产自身的标定值。镜头内参按实际模型和最终输出尺寸计算或读取。
当前正式 LiDAR 仍要求经过验证的 Instant 后端；其他 RTX 扫描方式可以被发现，但支持其时序需要另行适配。
IMU 需要所选官方后端支持的有效刚体承载；在全场景中可以发现一个没有有效承载的 IMU，
但必须报告不可读原因。不能把相机可挂任意静态 Xform 的条件直接套用到 IMU。

新轨迹的原场景复现使用录制时保存的传感器配置。旧轨迹跨环境若要使用目标场景自己的新传感器，
必须选择第 7.6 节的目标场景传感器策略；保留旧策略时仍按原有传感器一致性规则检查。

## 5 命令行接口及配置语义

### 5.1 常规启动

以下为实施后的目标用法。当前基线尚不支持交互 `--scene`，实施完成前仍使用既有操作指南。
在目标实例桌面终端执行：

```bash
export PROJECT=/root/gpufree-data/semantic/scripts/260920SensorVisualizer/v06/single0602Headless
/usr/bin/python3 "$PROJECT/run_web.py"
```

另一终端执行：

```bash
export PROJECT=/root/gpufree-data/semantic/scripts/260920SensorVisualizer/v06/single0602Headless
/usr/bin/python3 "$PROJECT/run_capture.py" --interactive \
  --scene /root/gpufree-data/IsaacSim_Asset/combine_stage/new_scene.usda
```

默认输出目录和 IPC 地址沿用当前项目默认值，网页无需新增场景参数。
如需独立输出根，两个终端均显式传入同一个 `--output`；启动时打印最终输出根和 socket，便于核对。
不自动按场景名改输出根，避免网页连接到另一套 IPC，也不通过改变输出根绕过同一卡的资源约束。

### 5.2 参数适用范围

| 参数 | 交互录制入口 | 完成轨迹的采集入口 |
| --- | --- | --- |
| `--scene` | 新增；选择本次加载的完整场景 | 首版拒绝，提示使用 `--scene-policy environment --target-scene` |
| `--job` | 可选高级配置；未指定时使用交互默认配置 | 保留已有私有任务快照用法 |
| `--output` | 统一控制录制输出根与默认 IPC 位置 | 保留现有任务与采集输出语义 |
| `--background-dome` | 扩展为可用；显式指定目标 DomeLight | 保留已有策略检查 |
| `--asset-profile-id` | 扩展为可用；选择已声明接口 | 保留，并在新轨迹后续采集时正确继承 |
| 传感器选择配置 | 默认全场景自动发现并选择全部可采集设备；可在网页/显式 job 中调整 | 固化本次选中设备及配置，不在采集中重新扫描切换 |
| `--target-scene`、`--scene-policy`、`--placement` | 不用于选择新录制场景，误用时明确报错 | 保持 004 方案定义 |
| `--all-trajectory`、`--groups` | 不改变交互录制时长 | 保持现有采样计划与互斥规则 |

`--scene` 首版只接收 Linux 本地绝对路径；含空格时使用 shell 引号。
URI/Nucleus 地址、USDZ、相对场景路径和在线资源下载不在本轮入口承诺内。
不能将 `--scene` 与 `--trajectory` 同时传入后静默选择其中一个。
`--headless-owner` 的测试入口复用相同解析器；纯 `--gui` 和高级 `--entry` 不因新增参数暗中启动控制器。

### 5.3 配置优先级

最终配置按“显式命令行参数 > 显式 job 字段 > 通用默认”生成。

- 解析阶段保留“未提供”状态，不能用 argparse 的默认 `--output` 等值覆盖用户 job 中的显式字段。
- 没有 `--scene` 和显式 job 时，默认交互配置继续选择现有 scene18，保持原启动体验。
- 有 `--scene`、没有显式 job 灯光字段和灯光参数时，`background_dome=null`，使用通用自动规则。
- 用户 job 显式写了灯光路径时保留该选择；路径失效则提示修正，不自动换成另一盏灯。
- 通用默认采用自动灯光规则；scene18 既有特定灯光选择放在其显式配置中，保留正式重放的历史配置。
- 只有一个已声明 profile 时自动选择；有多个时优先使用明确声明的标准默认 profile，缺少唯一默认则要求指定 ID。
- profile 默认选择使用稳定 ID，不使用列表第一项，也不按场景文件名猜测。
- 自动发现为新入口默认策略，不将旧 `robot_sensors.json` 的四相机路径当作全场景白名单。
- 显式设备选择或参数覆盖优先于自动选择；未提供选择项表示自动，不等于用户显式选择空列表。
- 无可采集设备时仍可初始化机械录制；正式采集预检单独拒绝空选择，不靠补造设备满足旧检查。

## 6 完整运行流程

```text
解析交互参数和显式 job
  → 检查目标文件，合并并验证最终 job
  → 创建本次启动快照，输出目录及 IPC 摘要
  → 启动 Kit，打开用户指定的完整 Stage，等待加载完成
  → 检查 Stage 基础约定，发现唯一标准挖掘机，验证运动接口
  → 独立构建全 Stage 索引，匹配传感器适配器，去重并读取参数
  → 判断各传感器实际承载与位姿参考，形成候选及默认选择清单
  → 按通用规则选择灯光，初始化必要运动与安装状态
  → 完成实际读回，保存绑定报告，发布 interactive_ready
  → 用户录制，Stop/End 后排空，形成完整轨迹
  → 正式采集从该轨迹和任务快照读取实际场景及绑定
```

初始化仍可按现有机制短暂 Play/Pause 建立 Articulation；不把初始化帧记入用户轨迹，
也不将“读取初始摆放”解释为禁止现有标准零位初始化。
成功后沿用等待用户操作的初始状态，不自动开启键控或开始录制。

场景或机械检查失败必须结束本轮初始化，释放已取得的资源，发布失败阶段；不能留下看似 ready 的网页状态。
设备级问题在候选清单中报告，机械 ready 与 capture ready 分开；已选设备验证失败或选择为空时不启动正式采集。
交互期间没有正式相机/雷达采集产品；正式 Headless 的兼容性检查仍在创建采集产品和 writer 之前完成。

## 7 模块实施设计

### 7.1 启动参数与配置快照

在独立的纯配置模块（建议 `single0602_headless/launch_config.py`）集中实现参数覆盖、默认选择和配置来源记录，
`run_capture.py` 调用它，不在多个 Kit 入口中复制合并逻辑。

建议在输出根下使用 `runtime/launches/<launch_id>/` 保存：

- `job.json`：验证后的最终 job，供 `S0602_JOB` 和 Kit 读取。
- `launch.json`：启动 ID、时间、显式输入与来源、最终 scene/output/socket/profile、阶段及错误。
- `binding.json`：初始化成功或失败的资产绑定结果与检查摘要。

启动目录独立创建，禁止覆盖上一轮快照。运行数据不进入源码交付清单。
snapshot 在启动前写入，绑定报告在实际 Stage 检查后补充；两个阶段使用同一启动 ID。
场景路径检查在启动器切换到 Isaac 安装目录之前完成；JSON/argv 传递不使用 shell 字符串拼接。

### 7.2 全场景发现、能力适配与独立位姿参考

将机械绑定和传感器发现拆为两个入口：`discover_robots(stage)` 与 `discover_sensor_candidates(stage)`。
后者不接收必须的 robot_path，不以机器人子树或预设相机路径为发现边界。
建议使用纯数据 Stage 索引和轻量类型适配器，分别承担“匹配、参数读取、能力校验、运行配置生成”，
不要求复制 v04 的整套插件发布系统。

#### 7.2.1 发现与去重

1. Stage 及必要 payload 加载完成后遍历整个已加载组合树，记录类型、applied schemas、关键属性、父子关系和有效变换。
2. 普通相机、鱼眼相机、RTX LiDAR 适配器按真实属性匹配。名称不参与类型判断，也不要求固定安装位置。
3. 同一 Prim 只生成一个候选；鱼眼专用匹配优先于通用 Camera，保留全部匹配信息便于诊断。
4. 鱼眼参数无效时仍报告“鱼眼不可采集”，不能回退成普通相机后输出错误标定。
5. 排除本程序生成的运行设备和临时视口设备，避免重复发现；不能凭节点名称隐藏合法业务传感器。
6. inactive 或 unloaded 的子树不伪造设备清单；报告可见的未加载资源边界，必要资源加载失败按实际错误处理。
7. 自动发现范围覆盖全场景；未知类型仅在有 schema/属性证据时标记为待适配候选，不承诺识别所有第三方私有格式。

初始正式适配目标为普通透视 Camera、原生鱼眼 Camera 和 RTX LiDAR；增加 IMU 预留适配器及官方资产独立验证分支。
原生鱼眼优先支持当前已验收的 OpenCV fisheye；其他镜头模型先发现并读取原生模型，
完成图像、位姿和标定输出适配后才能标记为可采集。非 Instant 扫描雷达同样不能因能发现就直接进入现有冻结采集后端。
本轮不顺带增加深度、语义、法线等输出模态。

#### 7.2.2 候选、选择和 ID

候选记录至少包括 `id/prim_path/sensor_type/adapter/model/parameters/parameter_sources`，以及
`discoverable/capturable/selected/mount_editable/issues`。具体字段可在实现时统一命名。
默认选择所有能力校验通过的业务设备，网页允许取消或调整；不额外要求用户逐个填写路径。
启动摘要明确列出发现数、可采集数、已选数及不可用设备原因，正式采集预览展示准确清单。

同名 Camera 或 sensor 节点使用完整身份消歧，ID、topic 和 frame 必须唯一，不能按发现顺序分配可漂移编号。
优先保留经过验证的已有绑定/持久 ID；新生成 ID 采用类型和规范路径，冲突时使用确定性路径摘要。
车载设备可使用机器人内相对路径作为身份部分，环境设备使用场景内路径；明确记录 ID 算法版本和实际映射。
相同场景重复启动结果稳定；任意改名、重挂载或外部路径变化不承诺自动识别为同一物理设备。
旧轨迹从已保存 registry 恢复既有 ID 和 ROS 通道，不能用新算法悄然改写旧身份。

#### 7.2.3 承载关系与坐标

| 类别 | 位姿语义 | 处理 |
| --- | --- | --- |
| 挖掘机刚体附属 `robot_body` | 相对实际承载部件安装，随该部件运动 | 保存刚体角色及局部安装参考，从实际 Stage 计算世界姿态 |
| 挖机根附属 `robot_root` | 相对整机根固定，不一定附属某一刚体 | 保存根参考；机械摆放作用于该设备，不能错误随某个工作关节运动 |
| 环境固定 `world_static` | 安装在静态三脚架、建筑或独立支架上 | 保存实际世界位姿和安装参考；挖机运动及轨迹 placement 不移动它 |
| 其他动态承载 `unsupported_dynamic` | 依赖另一运动物体或未记录动画 | 保留候选和原因，首版不用于可复现正式采集 |

承载分类依据有效变换依赖，结合 `resetXformStack`、刚体/关节控制和动画信息，不能只看路径是否位于机器人下面。
无已知动画也不能证明没有外部脚本驱动，静态承载仍需场景提供方确认；检测到未支持的运动时不能继续冒充静态。

`SensorPoses` 改为独立安装管理，不再要求每个设备的祖先都是挖掘机刚体。
默认只读取已有变换。需要安装编辑时，仅修改安全且专属的节点；共享支架、复杂变换栈和 instance proxy 可只读采集，
编辑功能显示不可用原因，不能为了编辑而移动建筑、整台设备或拆改原资产。

TF 按真实参考输出：机器人参考链保持既有契约，车载设备使用相应已发布的机器人参考帧，
环境固定设备直接以 world 为父参考；相机 optical 轴变换保留。每个 child frame 只有一个父节点。
ROS 导出按真实镜头模型写入 CameraInfo；不能表示的原生模型需要明确元数据和能力处理，不能统一伪装成 equidistant。
离线图像/点云、位姿、TF 和元数据必须使用同一份 registry 与同一时间戳。

#### 7.2.4 运行清单与零设备

交互启动不要求设备存在；候选和选择清单可为空。轨迹仍可记录机械状态，安装状态为空集合。
正式采集允许 `cameras=[]` 或 `lidars=[]`，不要求相机和雷达同时存在。
空任务判断应实现为“所有已启用正式采集驱动的设备总数为零”，避免将未来物理传感器锁死在相机/雷达的两列表中。
预留 `imus=[]`，旧 registry 缺少该字段按空列表读取。IMU 在独立验证阶段不计入正式可采集数，
只有预留 IMU 的场景可录制机械轨迹，但启动正式任务时应明确提示“IMU 正式同步采集尚未启用”。
驱动、门控、内存估算、PNG/点云编码、ROS 通道、网页、验证工具都按实际选中清单迭代，移除固定数量假设。
机械运动接口检查、候选发现和正式采集能力检查各自报告，防止某个未选设备故障导致整套机械初始化失败。

#### 7.2.5 IMU 预留接口与官方资产验证

本节采用“接口预留 → 官方原生资产读通 → 正式时序验收”的顺序。
保存方案不代表已经创建、下载资产或运行测试。当前挖机仍逐帧设置离散位置并清零物理速度，
IMU 不能被承诺为该位置轨迹对应的真实惯性测量，也不从轨迹差分生成伪 IMU。

**验证资产与版本基线。** 首选目标实例已有的官方 IMU 示例或原生传感器资产。
没有独立 USD 文件时，使用该安装版官方 Create Sensors 菜单或官方创建 API，在隔离验证场景中生成标准 IMU Prim，
保存为验证副本；记录其“官方原生创建器生成”的来源，不虚构一个未经核对的官方 USD 路径。
传感器外壳几何不作为识别依据。官方硬件目录中的厂商型号和扩展属于另一个验证范围，本阶段不以安装它们为前置条件。
来源说明见 [官方 IMU 资产目录](https://docs.isaacsim.omniverse.nvidia.com/latest/assets/usd_assets_imu_sensors.html)。

现有 [交付记录](../handoff/DeliveryHandoff.md) 的安装基线为 Isaac Sim `6.0.1-rc.7`。
实施前核对实际安装及扩展版本，优先按该安装版官方原生接口读数，不能为了匹配网上最新版示例而升级 Isaac。
6.0 文档指向 `isaacsim.sensors.experimental.physics` 的 `IMU` / `IMUSensor`，旧 API 已进入迁移流程；
若当前 rc 仍提供不同接口，适配器明确记录所用 API 和能力，不假定跨版本参数、返回字段完全相同。
参见 [官方 6.0 迁移说明](https://docs.isaacsim.omniverse.nvidia.com/6.0.0/migration_guides/isaac_sim_6_0/sensors_physics_to_experimental_physics.html)。

**发现与生命周期接口。** 增加 `sensor_type=imu` 适配器，基于实际官方 schema/type 和属性匹配，
可发现挖机内及车外的原生 IMU；只包含名为 IMU 的普通 Xform 或外壳 Mesh 不能据此认定可读。
验证需要有效物理场景和后端支持的刚体承载。相机/雷达的 RenderProduct 驱动与 IMU 的物理步驱动分开。
IMU 适配器至少提供匹配、读取配置、能力检查、初始化、读取原始样本、Stop 后失效处理、关闭和释放接口。
运行元数据记录 API/扩展版本、承载刚体、安装参考、物理频率、实际读数频率、滤波、重力开关及采样语义。

候选状态增加 `sampling_domain=physics`、`validation_status` 和 `formal_capture_supported`；
独立验证成功只能标记接口验证通过，`formal_capture_supported` 在完整时序验收前仍为 false。
安装修改、重挂父节点或 Stop 后需按所用后端重新初始化；首阶段不开放 IMU 播放中安装编辑。
这些约束参考 [官方原生 IMU 使用说明](https://docs.isaacsim.omniverse.nvidia.com/6.0.0/sensors/isaacsim_sensors_physics_imu.html)，
实际有效性、坐标和刷新时机以安装版读回证据确认。

**预留读数与导出契约。** 内部统一样本结构至少保存以下字段，外层 registry 与已有稳定 ID 规则一致：

| 字段 | 约定 |
| --- | --- |
| `sensor_id`、`frame_id` | 唯一设备和实际 IMU 轴参考，不借用 camera optical frame |
| `sensor_time_s`、`physics_step` | 后端原始测量时间与步号；不能由墙钟或渲染帧号冒充 |
| `is_valid`、`status` | 区分预热、有效、重复步、过期、停止和后端错误 |
| `linear_acceleration_m_s2` | 原始三轴加速度，明确传感器轴及是否包含重力 |
| `angular_velocity_rad_s` | 原始三轴角速度，不从挖机位姿差分生成 |
| `orientation_xyzw` | 统一顺序；保留原 API 四元数顺序和姿态参考说明，未提供时显式不可用 |
| `read_gravity`、`source_model` | 记录重力设置及 `native_physics_imu` 来源，防止将模拟读数标为硬件实测 |
| 协方差及参数来源 | 区分未知、不可用和已知，不伪造精度或滤波结果 |

预留 `/imu/<sensor_id>/data` 与 `sensor_msgs/Imu` 的 ROS2/MCAP 导出映射；
首阶段可在隔离探针中验证该映射，未通过前不向正式 bag 添加空通道或全零占位消息。
消息单位、缺失估计和未知协方差遵循 [ROS2 Jazzy 官方消息定义](https://github.com/ros2/common_interfaces/blob/jazzy/sensor_msgs/msg/Imu.msg)。
原始结构化样本与参数、源时间一并保留，原 API 到统一结构的轴和四元数转换须有独立用例。

**物理时钟与冻结采集边界。** IMU 按实际物理步读数，不要求创建 RenderProduct。
预留物理回调到有界缓冲的通路，按测量时间读取有效样本；不得仅在相机渲染后读取“最新值”并换上相机时间戳。
频率以安装版后端实际能力为准，请求频率、有效频率和物理频率分别记录，不靠重复旧样本提高有效 Hz。
在未来正式接入前，必须核对目标机械状态应用、物理步、IMU 测量、冻结渲染四者的顺序；
无满足时间要求的样本时明确报告，不补零、不改原时间，也不偷偷推进物理时间破坏已有采集契约。

现有离散位置和零物理速度下，姿态变化与 IMU 角速度/加速度读数不必满足真实运动的一致性。
静止时是否出现重力分量取决于已记录的重力选项，不要求全部 IMU 数值为零。
本阶段验收接口有效性、坐标、时间和生命周期；真实惯性数据集、噪声/偏置/漂移和 IMU 预积分不在范围内。

**分阶段验证。**

| 阶段 | 实施内容 | 完成条件 |
| --- | --- | --- |
| I0 接口预留 | 候选类型、配置/数据结构、能力状态、物理驱动入口、旧 registry 默认空列表 | 不影响无 IMU 场景；未正式支持设备不会自动加入采集 |
| I1 官方资产探针 | 官方原生 IMU + 有效承载，分别放在车载位置和独立验证刚体上，读原始样本 | 明确来源/API；预热后有有效样本，时间与步号前进，坐标和重力设置可核对 |
| I2 独立运行验证 | 静止、安装旋转、官方示例的受控运动、Stop/Play、导出映射 | 原始 API 与适配结构一致，失效后不读旧句柄，重复时间不伪造新消息 |
| I3 正式同步接入（后续门槛） | 与轨迹、冻结相机/雷达、采样计划和 MCAP 写入对齐，验证 IMU-only 任务 | 独立验收通过后才允许 `formal_capture_supported=true`；不作为本轮仅预留接口的完成声明 |

I1/I2 的受控运动在隔离官方验证场景执行，不改变生产挖机的运动设定，也不把额外验证刚体加入业务轨迹。
记录官方资产/创建器身份、实例版本、重力、频率、滤波、样本数、有效率、时间和轴转换结果，
原始日志进入忽略的实验目录，小型验收摘要才进入仓库。

### 7.3 运动接口与 profile

继续比较四关节角色、连接、轴、两侧局部坐标、零位和必要尺度信息。
将失败路径转换为明确提示，例如 `Joints/boom.axis: expected Y, actual Z`。
不因场景路径变化要求新增 profile，不因名称匹配跳过机构检查。

新轨迹中实际选用的 profile ID、零位声明和接口信息必须在正式采集时继承；
如用户显式请求另一 profile，仍须通过接口检查，不能覆盖来源身份后冒充原始录制。

### 7.4 灯光规则

复用 `select_dome()`，完善输入和报告即可：

- 零个可见 DomeLight：保留场景已有其他照明，不创建或复制 scene18 的灯光。
- 一个可见 DomeLight：自动保留，记录实际路径及属性。
- 多个可见 DomeLight：列出候选，要求提供有效 `--background-dome`，不取遍历第一盏。
- 显式目标：验证节点类型及可见性，按当前会话层策略处理其他 DomeLight。

配置快照记录“自动/显式”来源，绑定报告记录实际解析结果；轨迹和采集任务保存足以复现该选择的信息。
不保存修改到源 USD，不改变正式采集的渲染质量、预热或时钟阈值。

### 7.5 绑定报告和网页摘要

`binding.json` 至少包含：启动 ID、请求与实际加载场景、实际 USD 身份、机器人根与 Articulation、
profile ID、四关节绑定、全部候选及选择清单、每个设备的类型/模型/实际路径/ID/承载分类/能力及问题、
灯光策略、输出根、各项检查结果及错误。正式任务另存其不可变 `sensor_registry.json`。
大体量逐帧状态不写入该报告。

终端打印简短摘要；网页在现有状态区域显示实际场景、机器人根、profile，以及机械 ready 和采集 ready。
传感器列表显示模型、车载/车外归属、可采集状态和默认勾选，不增加必须填写的路径表单。
详细报告路径可作为排错信息显示。

### 7.6 轨迹与采集衔接

新增记录将机械运动接口与传感器采集配置拆开，并为带承载分类的传感器接口设置新的 schema 版本。
保留原 `scene`、机器人绑定和来源身份；旧接口通过明确的兼容读取处理，不将旧版“必须车载”字段直接套用到车外设备。
旧轨迹继续遵守已有完整性、契约和已核验 legacy baseline 规则，不从目标设备反推来源记录。

传感器重放定义两种策略，任务快照必须写明实际策略：

| 策略 | 用途 | 传感器来源和检查 |
| --- | --- | --- |
| `recorded` | 原场景复现；既有跨环境命令的兼容默认 | 使用录制时保存的设备及安装 revision，验证这些设备的接口和参考，不被新增目标设备自动替换 |
| `target_scene`（新增、显式选择） | 旧运动轨迹配合新场景自己的传感器采集 | 全场景发现目标设备，保存目标选择与配置；检查来源机械接口，不要求源和目标传感器数量/位置/标定相同 |

普通“新场景重新录制 → 在该场景采集”无需新增参数，使用该新轨迹保存的实际设备配置。
跨环境使用不同传感器时在网页或任务中显式选择 `target_scene`，具体 CLI 参数在实现时补齐；
既有 `environment` 命令未指定新策略时继续 `recorded`，不静默改变 004 已有行为。
原场景严格复现模式只接受 `recorded`；更换传感器配置属于明确的新采集用途。

`recorded` 只恢复来源中指定设备的安装状态；缺少设备或标定不兼容时明确失败，额外候选不会自动加入重放。
`target_scene` 不按同名 ID 套用来源安装 revision，设备以目标定义和任务自己的调整快照为准。
新环境传感器变化与机械轨迹复现误差分别验收，不能将新观测结果描述为原传感器视角复现。

placement 只作用于机械轨迹及实际附属该机械的设备，不作用于世界固定传感器。
初始和调整后的环境安装记录使用独立世界/静态参考，不要求记录整栋建筑或支架的运动轨迹。
另一动态物体的运动依赖仍不支持；不能借“车外设备”放宽这一边界。
根节点变化的用例必须覆盖接口比较、安装 revision、TF 和正式回读，不能只验 GUI 可操作。

Script Editor 的 `run_in_isaac.py` 首版保留“使用当前已打开 Stage”的语义；
本轮一参数换场景的主入口为独立交互启动器，不默默把 Script Editor 改成打开另一个场景。

## 9 核验标准、指标与用例

### 9.1 核心指标

| 指标 | 通过标准 |
| --- | --- |
| 用户接入动作 | 兼容场景仅替换交互命令的 `--scene`；无需改源码、复制 job 或登记哈希 |
| 选择一致性 | 请求 scene、最终 job、实际 Stage 和新轨迹记录一致；显式参数与 job 的覆盖符合第 5 节 |
| 默认兼容 | 既有 scene18、显式交互 job、轨迹采集命令保留相应行为 |
| 机械绑定完整性 | 原根及替换外层根的标准场景均绑定唯一挖机及 4 个关节；零传感器也成功 |
| 发现完整性 | 预置测试场景中全部已加载且支持的设备均发现，车内/车外、任意名称和数量均不漏识别；同一 Prim 不重复 |
| 身份与选择一致性 | ID、topic、frame 无冲突；同场景重复启动映射稳定；候选、已选设备与实际输出一致 |
| 设备独立性 | 仅相机、仅雷达可正式采集；零设备能交互录制，空正式采集在资源创建前拒绝 |
| IMU 预留与探针 | 官方原生资产可发现；预热后有效读数至少覆盖连续 5 s，时间单调不回退、四元数转换和重力设置可核对；只在新物理步上计有效样本，不宣称正式同步已完成 |
| 失败可解释性 | 每项负例指出具体路径/字段和原因；机械故障不报 ready，未选设备问题不阻断机械录制，已选故障设备不启动 writer |
| 数据一致性 | 短采实际采集/写入数量符合计划，MCAP 可独立回读，传感器和 TF 清单匹配 |
| 重放精度 | 延续 004：根位置误差 ≤1e-5 m、姿态角误差 ≤1e-5 rad、关节角误差 ≤1e-4 rad |
| 传感器参考正确性 | 车载设备随真实承载运动；世界固定设备在挖机运动和 placement 后位姿不变，位置/姿态误差分别 ≤1e-5 m / ≤1e-5 rad；保留原有驱动回读阈值 |
| 模型表达正确性 | 普通透视相机不输出伪鱼眼模型；鱼眼不重复为 pinhole，图像尺寸、内参和数据使用同一适配配置 |
| 数据与资产保护 | 源 USD、共享输入配置和旧轨迹不被运行器改写；快照互不覆盖 |
| 交互体验 | 保留 1× 目标与实际倍率显示；Pause/Play、键控开关、Stop 后新文件行为不回退 |

不新增任意场景固定加载时限或无条件 1× 保证。记录实际初始化耗时和倍率，发现明显回退再定位。

| T23 | 官方原生 IMU 在车载及车外有效承载上，含任意命名和同名设备 | 按真实 schema 发现且 ID 唯一；无承载或只含外壳的设备说明不可读原因 |
| T24 | 官方 IMU 静止、改变安装旋转，分别读取含/不含重力数据 | 对照同一原始 API，轴和四元数转换正确；静止不被强制补成全零，重力响应与实际设置一致 |
| T25 | 官方验证场景受控运动、预热、Stop/Play 和旧句柄失效 | 原始样本有效，时间语义明确；重启后重新初始化，不将旧样本伪装为新物理步 |
| T26 | 业务场景仅有预留 IMU；关闭或缺失 IMU 后端 | 机械轨迹可录制，正式采集说明尚未支持或不可用；没有占位数据、无 IMU 场景不受影响 |
| T27 | 预留 ROS2/MCAP 映射与重复采样/缺失字段 | 单位、frame、重力设置和不可用字段表达正确；不靠改时间戳或填零补齐采样 |

验证分三层：纯配置和路径解析单元用例；Linux 入口、快照和 IPC 集成用例；真实 Isaac 的加载、录制及短采。
真实用例至少对默认场景、新环境、新根命名空间、仅相机、仅雷达及车外设备组合分别完成短轨迹和 4 组采集，独立回读 MCAP。
scene18 的 13 雷达/4 相机保留为回归样例；另有零设备轨迹用例，不要求零设备生成 MCAP。
IMU 的 T23～T27 在 I0～I2 的独立官方探针执行，结果与上述正式图像/点云短采分别报告；
IMU 与冻结采集的联合验收以及 IMU-only 正式任务留给 I3，不因探针读通而声称整条链路支持 IMU。
沿用现有采样计划测试覆盖完整轨迹和指定组数，保留原生时钟、姿态和排空检查，不用扩大容差换取通过。

Windows 缺少 Isaac 的跳过用例应与 Linux 原生通过证据分别说明，不能将纯配置通过写成真实采集完成。
原始日志、逐帧数据和运行快照保存在输出或本地忽略目录；仓库只保留必要的小型验收摘要。

## 10 风险、处理与后续事项

| 风险或矛盾 | 处理 |
| --- | --- |
| 希望只填路径，但资产只有名称一致、实际机构不同 | 按标准运动接口检查，明确报差异；新的机构进入单独适配流程 |
| 显式 job 仍含旧场景灯光路径 | 尊重显式配置并报错；常规 `--scene` 采用通用默认，无需沿用该 job |
| 全场景任意命名及同名设备导致 ID、topic 或 frame 冲突 | 规范身份与确定性消歧；旧 registry 保留原身份，记录算法版本 |
| 把所有设备绑定到挖机，导致固定摄像机随车移动 | 按实际变换依赖分类，独立 world 参考，placement 只作用于机械及其附属设备 |
| 发现了模型但当前后端不能正确采集 | 区分发现与能力，报告原因，显式无效选择失败，不转换成错误模型 |
| 自动选中大量场景设备增加资源成本 | 展示实际清单和资源估算，允许取消选择，按选中设备检查预算，不暗中减少采集质量 |
| 扩展设备后仍按固定鱼眼或固定通道编码 | 驱动、消息、TF、writer、验证器共同使用版本化动态 registry |
| IMU 依赖物理步，与冻结渲染和离散零速度运动存在语义差异 | 单独物理域适配器和官方探针；原始读数不改时间、不差分伪造，联合时序通过前不正式启用 |
| 交互指定 profile，Headless 又选择默认 profile | 轨迹和任务传递实际 profile，并在 Headless 再核验接口 |
| 自动绑定成功，但重放接口或安装位姿不一致 | 首帧至正式采集贯通验证，原有接口和位姿检查保持 |
| 单张 GPU 上出现旧进程或另一输出根的任务 | 沿用现有资源约束，切换前完整结束旧流程，不通过删锁或换目录并发启动 |
| 场景渲染成本高或外部资源缺失 | 报告耗时、实际倍率与解析问题，首次短采确认；不自动降低采集质量 |
