## 1. 核心目标与实施边界

### 1.1 目标

1. 初始化完成后以及暂停、运动阶段，不执行不需要的相机和 LiDAR 渲染更新。
2. 以“本组所有传感器的数据真正就绪且通过校验”为采集完成条件，减少系统性的重复渲染。
3. 缩短主线程上的无效工作和同步阻塞，及时反馈阶段状态、暂停与停止请求。
4. 将运动、传感器、渲染、数据回读、编码、写盘连接为可查询的事件链，下一轮优化有可核实的证据。
5. 保持点云、图像、TF、关节状态与仿真时间的一致性，保留现有数据组织和使用方式。

### 1.2 本轮保持的约束

- 继续采用 Instant LiDAR；不更改雷达发射模式、视场角、采样距离或遮挡规则。
- 继续采用“运动推进 → 冻结 → 采集”的顺序。冻结期间原生仿真时间、时间轴和相关物体位姿均不得改变。
- 默认使用当前场景 `combine_scene_16_terrain_fisheye.usda`；不覆盖或修改磁盘上的场景及引用资产。
- 保持相机分辨率、镜头模型、渲染模式、DLSS 设置、PNG 参数一致。
- **保留当前相机 16 个预热子帧、正式采集 2 个子帧及初始化预热配置。** 此前第 3 项“减少预热”不纳入本轮性能收益。
- 保持交互模式不高于 0.1 倍速，离线模式不限速。两种模式分别验收。
- 保留现有独立录制进程、共享内存槽、并行 PNG 编码及顺序 MCAP 写入。
- 暂不合并到 semantic world module v04。
- 保持现有暂停、停止时的位姿行为：暂停保留当前状态；正常停止完成收尾后，依原有逻辑恢复初始关节、整机及 LiDAR 安装位姿。

下文中的新增模块、接口和配置均为拟议内容，不代表当前项目已经具备这些能力。

## 3. 总体架构

```text
UI / 离线任务
    │  控制请求、配置、状态显示
    ▼
CaptureRunner：唯一的采集阶段调度者
    ├── SceneStepper：运动、时间与位姿冻结、最终一致性检查
    ├── SensorDrivers：传感器资源、更新开关、采集触发、数据回读
    ├── CaptureTicket：本组请求、就绪集合、来源验证、超时/重试状态
    └── RecordPipeline：拥有数据的缓冲槽、顺序提交、背压和收尾
                │  不可变数据与关联编号
                ▼
         独立录制进程
         并行 PNG → 消息组装/CDR → 顺序 MCAP → ROS 预览

RunDiagnostics：贯穿上述模块的事件、区间、资源、警告与关联记录
分析工具：在采集后生成汇总和可本地查看的时间线
```

原则：场景和传感器仍由同一个 Isaac 调度上下文拥有；后台只处理已经脱离引擎生命周期的数据。允许第 N 组后台编码、保存与第 N+1 组运动、采集重叠，不允许第 N 组尚未取得稳定数据就改变场景。

## 4. 第 1 项：统一控制传感器渲染更新

### 4.1 资源生命周期

1. 每次初始化创建一套 Render Product 和 Annotator，记录 `stage_generation` 和资源拥有者。
2. 在当前 API 允许的最早时刻关闭新建产品更新，防止批量创建过程产生意外采集。
3. 初始化必须的时钟建立、挂接及预热作为显式阶段执行；完成后所有传感器更新关闭。
4. 日常阶段切换只修改更新状态，不反复创建、销毁或 attach/detach。
5. 正常关闭时先结束在途请求，再 detach、destroy，最后移除临时层并恢复设置。

资源句柄在有效生命周期内复用。缓存句柄不等于允许持有已被 Stage 切换或产品销毁失效的对象；失效后必须重建。针对重复释放警告先记录对象路径和生命周期，再修复拥有关系，不能仅屏蔽警告。

### 4.2 拟新增项目接口

```python
suspend_all(reason)
set_updates(sensor_ids, enabled, reason)
set_camera_updates(enabled, reason)
set_lidar_updates(enabled, reason)
```

底层继续使用已在本机验证过的 `render_product.hydra_texture.set_updates_enabled(...)`。

- 每个产品维护“最后一次成功发出的更新状态”，只在需要变化时调用。
- 记录期望状态、调用结果、作用的传感器和之后观察到的回调数量。
- 不把软件缓存中的 `False` 冒充为已经观察到 GPU 完全无工作；若没有底层状态查询，明确标记为“请求状态”。
- 关闭的是传感器 Render Product 更新，不隐藏传感器、挖掘机或场景几何，不改变遮挡含义，也不关闭编辑器主视口。

### 4.3 阶段表

| 阶段 | 相机更新 | LiDAR 更新 | 时间/场景行为 |
|---|---|---|---|
| `IDLE / PAUSED / PACING / WAIT_SLOT` | 关闭 | 关闭 | 时间不推进，允许安全边界上的控制操作 |
| `ADVANCE` | 关闭 | 关闭 | 按既定物理步长推进和写入运动姿态 |
| `FREEZE` | 关闭 | 关闭 | 暂停时间，记录本组目标时间与位姿 |
| `WARMUP` | 按原预热流程开启 | 仅在原有安装位姿刷新等流程确有需要时开启 | 场景与时间冻结，结果不作为正式组提交 |
| `CAPTURE / WAIT_READY / ACQUIRE` | 按请求需要开启 | 按请求需要开启 | 保持冻结，接收并取得正式数据 |
| `SUBMIT / DRAIN` | 关闭 | 关闭 | 已取得独立数据；提交或排空录制队列 |
| `ERROR / CLOSE` | 关闭或等待在途调用安全结束后关闭 | 同左 | 标记失败、保留证据、安全清理 |

不要直接把现有 `enabled(False)` 改成遍历全部产品后就结束实现：现有 `render()` 也通过这个函数开启产品，可能意外破坏“相机预热时 LiDAR 应保持关闭”的约束。所有调用点必须按阶段重新映射。

## 5. 第 2 项：建立整组数据完成条件

### 5.1 CaptureTicket 的数据结构

每个正式采集请求至少包含：

| 字段 | 含义 |
|---|---|
| `run_id / capture_id / group_id` | 所属脚本运行、录制会话、采集组 |
| `request_id / attempt_id` | 本组请求及其重试编号 |
| `stage_generation` | 防止场景重载后的旧回调被接收 |
| `expected_sim_ns / timeline_time` | 原生仿真时间网格及时间轴快照 |
| `pose_revision / expected_poses` | 安装调整版本和冻结时的相关位姿 |
| `expected_sensor_ids` | 本次实际选择的传感器集合，不硬编码为 17 路 |
| `submit_sequence / source_frame_id` | 可获得时保存真实渲染提交与源帧关联；不可获得时为 null |
| `ready / pending / errors` | 每传感器的就绪、等待及错误状态 |
| `deadline / cancelled / state` | 超时、取消和状态管理 |
| `owned_payloads` | 已经通过来源验证并取得所有权的数据 |

`request_id` 由项目分配，只能用于关联，不能证明底层返回的就是本次新数据。源时间一致也不总能证明新鲜度：冻结时间内预热与正式渲染可能拥有相同时间戳。

### 5.2 接收窗口与触发顺序

1. 预热完成，并确认或排空预热阶段的交付。预热结果与正式结果分别管理。
2. 建立 ticket，清空本 ticket 的结果，注册接收窗口。
3. 记录各产品的当前源帧/提交标识；有能力时使用真实标识区分本次和历史结果。
4. 显式触发正式采集，再调用 `step_async(delta_time=0.0, pause_timeline=True, wait_for_render=True, ...)`。
5. `step_async()` 返回只结束“渲染调用等待”区间，不立即关闭 ticket。
6. 等待本 ticket 的所有预期传感器完成来源验证和安全回读。
7. 最终检查场景仍被冻结，完成 ticket 后再关闭接收窗口与传感器更新。

相机仍使用 Writer 回调交付数据。可在独立兼容性测试中评估 `attach(..., trigger=None)` 和 `schedule_write()`，以明确区分预热与正式输出；它们仍需后续引擎渲染更新才能触发交付。不能仅凭官方新版文档假定远端构建行为完全一致。

LiDAR 当前使用 Annotator 读取，不能把它描述成已经具有与相机相同的 Writer 回调。先在经过验证的产品完成点读取；若要改成回调式交付，必须单独验证当前构建的接口、内存生命周期和时间语义。

### 5.3 就绪判定

每个传感器至少验证：

- 请求、Stage、传感器属于本次有效采集。
- 来源能够与本次渲染关联；缺少真实源帧标识时，必须采用实测验证过的串行提交/完成协议，不能仅给旧回调补上当前 request_id。
- 传感器源时间与目标时间匹配。
- 实际渲染位姿与冻结的 USD 位姿匹配。
- 图像尺寸、类型、点云字段和有限数值符合现有数据契约。
- 结果已安全复制，或拥有经过验证的缓冲区租约，不依赖下一帧可能覆盖的临时视图。

保持当前校验阈值作为首轮基线：

| 校验 | 当前阈值 |
|---|---|
| 源时间转为整数纳秒后与目标网格比较 | 绝对差不超过 2 ns |
| 原生时间、时间轴在冻结前后比较 | 现有 `assert_frozen` 默认 1e-9 s |
| 冻结前后相关 USD 位姿矩阵比较 | `rtol=0`，`atol=2e-6` |
| 传感器渲染位姿与 USD 位姿矩阵比较 | 元素最大绝对差不超过 2e-3 |

不得通过放宽阈值、重写时间戳或忽略位姿错误来消除重试。矩阵元素误差同时涉及平移与旋转部分，不能直接称为统一的“毫米误差”。以上是当前校验阈值，不代表底层测量或浮点时钟具备同等物理精度。

对应用内控制请求实行安全边界排队；若外部编辑器在冻结期间直接改变了场景，应检测并使当前组失效，不拼接新旧姿态数据。

### 5.4 异步等待与重试

- 用 Future/Event 表示“应用层完成条件”，在 Kit 所在线程创建和完成；跨线程通知只传轻量元数据并安全投递回该事件循环。
- 等待期间允许必要的 Kit 更新推进回调，但保持原生时间与时间轴冻结。
- 若当前 Replicator 构建必须再次执行 step 才能交付，就将它记录为额外渲染/图更新，而不是伪装成零成本等待。
- 未完成来源验证或安全复制前，不能为了减少工作过早关闭产品而使待接收缓冲失效。

| 情况 | 处理 |
|---|---|
| 回调尚未到达 | 保持窗口开启，有界等待，并记录 pending 传感器 |
| 窗口外迟到回调 | 记录并拒收，不写入新 ticket |
| 已确认旧时间、旧源帧或旧位姿 | 保持冻结，记录具体原因并重试 |
| 部分结果有效、部分无效 | 仅在已验证产品可独立恢复时补采缺失部分；否则执行明确记录的整组有界重试 |
| 场景时间或位姿变化 | 当前组失败，停止继续提交，保留此前完整组 |
| 超时、无效数据或原生错误 | 结束请求并报错，不用上一组结果填补 |

每次重试分配新的 attempt_id，明确哪些已取得的数据保留、哪些作废。第一阶段保留现有重试上限作为兜底，重点消除“正常路径必然重试”，不承诺绝对零重试。

## 6. 第 4 项：减少主线程阻塞与改进交互

### 6.1 调度与线程边界

- `CaptureRunner` 统一管理阶段，禁止多个任务同时推进同一 Stage。
- 第一阶段仍使用 `SceneStepper.advance()` 当前的 Kit 步进方式，传感器关闭后再测量。此前直接原生步进曾出现源时钟契约问题，不在本轮未经验证地替换。
- USD 写入、时间轴控制、Replicator 和 Annotator 调用保留在符合 Kit 要求的线程上下文。
- 普通后台线程只处理已经独立拥有的 CPU 数据、序列化、文件写入和轻量统计。
- `async` 只能让协程在等待点让出执行权，不能让内部阻塞的原生调用自动变为并行。对此必须保留分段计时与深度追踪入口。

### 6.2 UI 行为

- 进入每个阶段时立即更新状态，而不是只在整组完成后刷新。
- 显示组号、已就绪/预期传感器数、等待对象、当前阶段耗时、后台已写入组数。
- 控制回调只登记请求，不直接在正在采集的场景上改位姿。
- Pause：完成当前在途组后进入冻结且全部产品关闭的暂停状态。
- Stop：停止发起下一组；当前组按安全边界完成或明确失败，排空已经提交的数据，再恢复原有初始姿态。
- 尚未进入采集的等待阶段可以及时停止；正在执行的原生渲染不可强行跨线程打断。
- 函数内部若阻塞，UI 仍可能短暂无法响应。显示“请求已登记”和真实阶段，不承诺原生调用期间能够即时取消。
- 阶段事件即时更新，连续进度适度限频；避免为刷新 UI 高频遍历 Stage。

### 6.3 数据所有权与已有并行链路

现有缓冲槽仍采用有界容量和代次检查，拟明确如下所有权状态：

```text
FREE → RESERVED → CAPTURE_OWNED → PACKED → SENT → RELEASE_ACK → FREE
```

- 在缓冲槽不足时停在 `WAIT_SLOT`，传感器关闭、时间暂停，不额外生成随后无法保存的数据。
- 回读取得的数据必须在引擎继续更新之前完成安全复制；禁止把短生命周期 GPU/Annotator 视图交给后台。
- 当前安全复制先保留，增加独立计时。只有测量证明其成为主要瓶颈，才评估异步回读、固定页内存和 CUDA 事件等后续改造。
- 若将共享内存打包或 socket 发送移出主线程，必须先明确数组所有权、容量上限、顺序和关闭协议；不能让异步发送成为无界队列。
- 已发送的槽只能由匹配 `capture_id / group_id / slot / generation` 的释放确认回收。
- 未提交的失败组可以安全释放本地槽；已提交组不得因 Stop 提前复用。
- 保留一个顺序 MCAP 写入者；PNG 的并行结果可以乱序完成，但完整组提交顺序必须确定。

ROS 发布调用也要单独计时。若实测其阻塞保存链路，再考虑独立的有界预览队列；丢弃预览消息不得影响正式录制。

## 7. 优化后一组数据的执行顺序

1. 检查停止/暂停请求，应用安全边界上的控制命令。
2. 关闭全部传感器更新。
3. 执行交互模式的倍率等待，并申请可用缓冲槽；等待时不推进仿真。
4. 按原时间网格推进运动；首组保持当前已定义的初始采集语义。
5. 暂停时间轴，读取原生仿真时间，保存相关位姿快照。
6. 按原配置执行必要预热，区分预热输出和正式输出。
7. 创建 ticket 并注册接收窗口，触发正式采集。
8. 等待产品交付，逐传感器确认来源、时间和姿态，安全取得数据。
9. 确认全部预期传感器完成，再次验证场景时间和位姿未变。
10. 结束 ticket，关闭传感器更新，将独立数据打包提交给录制进程。
11. 后台编码、组装、写入及预览；前台在所有权允许后推进下一组。
12. Stop 时排空已提交数据，关闭 MCAP，恢复原有姿态并保留诊断结果。

简化伪代码仅表达时序，不是可直接执行的 API：

```python
await enter_safe_boundary()
drivers.suspend_all(reason="before_advance")
await wait_pacing_and_slot()
await scene.advance(group_id)
frozen = scene.freeze_snapshot()
try:
    await run_existing_warmup(frozen)
    ticket = begin_capture_request(frozen, selected_sensors)
    await trigger_formal_capture(ticket)
    owned_data = await collect_and_validate(ticket)
    scene.assert_still_frozen(frozen)
finally:
    await quiesce_request_before_releasing_resources()
    drivers.suspend_all(reason="capture_boundary")
await submit_owned_group_in_order(owned_data)
```

实际实现必须区分“尚未触发”“请求已提交”“数据已取得”和“数据已交给后端”四种清理情形。异常分支不得执行伪代码最后的正常提交。

## 9. 新版日志的统一事件模型

### 9.1 从面板启动覆盖到关闭

新增 `RunDiagnostics`，在 GUI 面板创建或离线入口开始时启动，而不是等 Start Capture 才启动。若场景在脚本启动前已打开，记录“此前加载过程未观察到”，不补造加载耗时。

一次 run 可包含多个 Initialize 和多个 capture。Stage 重载递增 `stage_generation`；每次录制生成新的 capture_id；group_id 只在该 capture 内有意义。

### 9.2 建议基础字段

```json
{
  "schema_version": 1,
  "run_id": "run-example",
  "capture_id": "capture-example",
  "group_id": 12,
  "request_id": "request-example",
  "attempt_id": 0,
  "stage_generation": 1,
  "sensor_id": "front",
  "pid": 100,
  "tid": 101,
  "process_role": "isaac",
  "event_seq": 2048,
  "span_id": "span-example",
  "parent_span_id": "capture-span-example",
  "event": "camera.callback.received",
  "phase": "WAIT_READY",
  "monotonic_ns": 123456789000,
  "utc": "2026-10-08T02:24:00.000000Z",
  "simulation_time_ns": 133333333,
  "source_simulation_time_ns": 133333333,
  "source_frame_id": null,
  "measurement_source": "writer_callback",

```

此示例为字段定义，数字不是实测结果。与某事件无关的字段可以省略；缺失能力使用 null 加原因，不能填零冒充测量。

### 9.3 时间与计量规则

- 同机进程使用明确声明的单调时钟，例如 `time.monotonic_ns()`，记录时钟实现、分辨率与主机/启动会话关联。
- UTC 用于人工对照和 Kit 日志关联，不用于计算耗时。
- 仿真时间和传感器源时间用于数据契约，绝不作为真实耗时。
- GPU 时间由对应 profiler 提供，并由其处理时钟关联；不能和 CPU 时间戳随意相减。
- ns 是存储单位，不承诺纳秒测量精度。导出浏览器时间线时使用相对起点的微秒等格式，避免 JavaScript 大整数精度问题。
- 异步区间使用显式起止及关联 ID，不用一个跨 `await` 的线程栈区间假装独占主线程。
- 线程 CPU 时间只用于可解释的线程区段；跨 `await` 的线程 CPU 增量可能包含别的协程工作，不能用“墙钟减 CPU”直接声称得到了锁等待时间。
- 嵌套区间显示包含关系；并行区间显示重叠。汇总不得把所有区间简单累加成总耗时。

## 10. 各层具体埋点

| 层 | 建议事件/区间 | 记录的关键维度 |
|---|---|---|
| 生命周期 | `ui.open`、`stage.loading_wait`、`product.create`、`annotator.attach`、`init.warmup`、`close` | 资源数量、实际配置、生命周期编号 |

## 11. 分级资源与底层追踪

### 11.1 常规模式：默认开启

- 生命周期、关键阶段、每组及每传感器的完成/失败事件。
- 约 1 Hz 的进程、选定关键线程、RSS、容器 CPU 配额与节流、整卡 GPU/显存采样。
- Kit 更新间隔统计、队列深度、槽占用、提交与写入差距。
- 控制请求响应时间、重试原因、丢日志计数。
- 优先利用已经可用的 NVML 绑定；若不可用，继续低频使用现有 nvidia-smi，不为基础日志引入安装前提。

### 11.2 诊断模式：按组或时间窗口开启

- 详细的每步、每产品和每回调事件。
- 更细的 CPU 线程采样、短时 Python 调用分析和异常前后环形记录。
- Kit `carb.profiler` 区间、计数和 flow 标记；以当前安装构建实际支持的 API 为准。
- 将请求提交、回调、缓冲传递和写入用 flow ID 连接。
- 不默认开启全函数 Python profiler；它会改变运行开销。

### 11.3 深度模式：独立短时复现

- 使用 Nsight Systems 等已确认可用工具查看 CPU 调度、同步、Vulkan API/GPU 工作与 CUDA 操作。
- RTX 渲染涉及图形接口，仅 CUDA trace 不能覆盖全部渲染链路。
- CUDA Event 只用于确实掌握流与生命周期的 CUDA 工作，不能直接包围任意 Python `render()` 就声称测到了整个 RTX GPU 时间。
- 工具、权限、驱动和符号支持不足时明确记录能力缺失；不承诺看见闭源插件的全部内部函数。
- 本次检查未找到可直接调用的 `nsys`、`perf`、`gdb`、`py-spy`、`strace`；基础实现不得依赖它们。
- 如后续需要新增下载或安装，按既有外部内容清单确认流程单独列出来源、版本、用途、落点与验证依据。本方案不授权安装、系统升级或修改内核性能权限。

## 12. 日志写入、目录与兼容性

### 12.1 建议目录

```text
output/sensor_visualizer/v02/

│   ├── manifest.json             # 版本、配置、资产标识、能力与时钟信息
│   ├── events_isaac_<pid>.jsonl   # 前端事件及区间起止
│   ├── events_writer_<pid>.jsonl  # 录制进程及编码线程事件
│   ├── resources.jsonl           # 资源采样与更新间隔摘要
│   ├── warnings.jsonl            # warning 摘要与原始日志引用
│   ├── summary.json              # 增量检查点与最终统计
│   └── trace.json                # 按需导出，兼容本地时间线查看
└── <capture_session>/
    ├── diagnostics_ref.json      # 关联 run_id、capture_id 和事件范围
    ├── performance/              # 保留旧版兼容输出
    ├── writer_report.json
    ├── capture_index.jsonl
    └── bag_unified/
```

`manifest.json` 包含代码版本/哈希、Isaac/扩展/驱动版本、实际传感器集合、关键渲染与时钟设置、GUI/离线模式、场景及配置指纹。对已有资产清单复用结果，避免每次运行重新哈希大型点云或纹理。

MCAP 保留现有话题和字段，可增加可选诊断关联字段及独立 schema_version。完整性能日志放在旁路文件中，不把每个细粒度事件都写进 MCAP。

### 12.2 写入与失效策略

- 主线程只生成小型事件并入队；后台批量序列化、写盘。
- 每个进程写自己的事件文件，避免多进程竞争一个普通文本流；采集后按单调时钟和 flow 合并。
- 事件在入队时分配序号和时间，不用后台真正写盘的时间冒充事件发生时间。
- 设置有界队列和文件轮转；超过预算时优先聚合/丢弃低优先级详细事件，显式记录缺口。
- 错误、状态转换和最终摘要预留容量。诊断写入失败要反馈为“可观测性降级”，不得递归打印日志造成更大阻塞。
- 定期落盘简短检查点，避免异常退出导致所有统计都只留在内存；异常结束标记 incomplete，不能伪称完成。
- 保留异常前的轻量环形事件，触发后输出前后窗口。已失去的事件不能事后补造。
- 不逐点/逐像素记录，不将完整图像、点云、密码、令牌、环境变量或未经筛选的命令行写入日志。
- 日志保存在本地或用户指定实例的项目目录；时间线在本地查看，不自动上传到外部分析网站。

### 12.3 拟议配置

建议增加独立 `diagnostics` 配置块，并明确验证默认值、容量与模式。示例仅表达接口设计：

```json
{
  "diagnostics": {
    "level": "basic",
    "resource_period_ms": 1000,
    "detail_group_range": null,
    "event_queue_capacity": 8192,
    "flush_interval_ms": 250,
    "ring_history_seconds": 10,
    "slow_stage_ms": 500,
    "export_trace_on_stop": false,
    "native_profiler": "off"
  }
}
```

容量与慢阶段阈值是起始候选值，需用真实事件量校准。不同阶段应支持不同阈值，不能把正常的 16 子帧预热全部判为错误。

## 14. 自动分析输出

每次运行至少生成：

1. **正确性摘要**：完整组、失败组、重试次数、源时间和位姿检查结果。
2. **耗时摘要**：冷启动与稳定阶段分开，P50/P95/最大值、样本数与采样范围明确。
3. **传感器排行**：回调等待、回读和编码最慢的传感器及对应组号。
4. **供需关系**：缓冲槽等待、编码队列、提交与写入差距、预览耗时。
5. **交互表现**：Kit 更新长间隔和控制请求响应/生效延迟。
6. **资源关联**：慢区间的主线程负载、进程 CPU、整卡 GPU 和容器节流；不把整卡指标冒充进程独占指标。
7. **warning 关联**：重复次数、活跃阶段、代表样本及原始日志位置。
8. **日志质量**：丢事件数量、时钟能力、缺失指标、profiler 模式与自身开销。

自动结论区分“直接测量事实”和“候选解释”，不因 GPU 低或 warning 多就自动断定原因。

与基准对比时，检查代码、场景、传感器集合、画质、预览、运行模式、日志等级和是否存在其他 GPU 进程。差异条件明显时给出不可直接比较提示，而不是生成误导性百分比。

## 15. 验证方案与验收条件

### 15.1 正确性验收

- 原生仿真时间与时间轴在正式采集、等待、重试期间保持冻结。
- 每组恰好包含预期传感器集合，时间、位姿和数据格式通过原有校验。
- 旧 ticket、旧 Stage、迟到回调、重复回调不能污染当前组。
- 暂停/恢复、停止、关闭、修改安装位姿、重复开始录制均有确定行为。
- 后端组号有序、槽不提前复用，写入完成与 bag 关闭状态正确区分。
- 相机数量、点云字段、TF 关系、MCAP 话题及现有解包工具保持兼容。
- 原始磁盘 USD 与未授权配置不变；异常退出不得遗留该脚本仍在工作的传感器资源。

### 15.2 有针对性的故障测试

| 测试 | 预期结果 |
|---|---|
| 一个相机回调迟到 | pending 精确指向该相机；按真实来源接收，不误用旧结果 |
| 回调落在关闭窗口之外 | 拒收并记录原因，不自动归到下一组 |
| 一个 LiDAR 返回旧时间或旧位姿 | 有界重试，记录期望/实际值；失败时不提交混合组 |
| 捕获期间修改 Stage | 当前组失败并留下场景变化证据 |
| 编码进程变慢 | 有界背压，关闭传感器等待，无界内存不增长 |
| Stop 发生在渲染或回读期间 | 在安全边界收尾，不强制销毁在用缓冲 |
| 诊断队列满或日志文件不可写 | 明确报告观测降级，避免日志反过来阻塞主链路 |
| Stage 重载或初始化失败 | 旧代次失效，资源清理幂等，允许有说明的重新初始化 |

故障注入在独立测试入口中完成，不污染生产数据。测试优先覆盖异步顺序、来源判定、所有权和错误恢复，不编写只重复实现细节的测试。

### 15.3 性能验收

1. 用同一场景、13 路 LiDAR、4 路相机和相同画质做成对测试。
2. 初始化、空闲、运动、采集、停止后空闲、关闭后分别测量。
3. 先做短程冒烟，再做足够覆盖尾延迟的稳定采集；短测只有 3 组时不宣称获得可靠的长尾 P95。
4. 原版和新版使用等价的低开销采样；记录冷启动、缓存和并发应用条件，交替复测排除运行顺序偏差。
5. 运动和空闲阶段传感器不再持续产生非预期数据；在途完成事件单独标记，不能机械要求关门后一条回调都没有。
6. 正常路径不再每组必然出现同一种缺失回调重试；剩余重试必须有明确原因。
7. 同画质下完整组耗时、更新长间隔和操作延迟有可重复改善；不能用降低预热或改变时间校验掩盖退化。
8. 常规日志开销以不超过约 3% 作为初始设计预算，通过多轮开/关日志对照测量后确认；诊断/深度模式单独报告开销，不强行适用该预算。

不把“CPU/GPU 必须满载”作为验收条件。评价重点是正确数据的产出率、交互响应和可解释的关键路径。

## 16. 实施阶段、交付与回退

| 阶段 | 工作 | 退出条件 |
|---|---|---|
| P0：冻结基准 | 保留原代码与配置，建立版本/资产清单，保存本次证据 | 基准可复现、可比较 |
| P1：日志基础 | run/capture 关联、统一时钟、阶段起止、资源与错误事件 | 不改变采集行为即可解释当前缺失回调与长更新 |
| P2：统一启停 | 修正全部调用点、空闲与运动关闭产品、完善异常清理 | 正确性通过，空闲和运动改善可重复 |
| P3：完成条件 | ticket、接收窗口、来源关联、等待与有界重试 | 旧数据不混入，系统性重复渲染得到解决或明确定位 |
| P4：交互与交接 | 阶段 UI、安全控制边界、缓冲/IPC 细分与必要的异步调整 | 交互改善，无所有权和顺序回归 |
| P5：报告与验收 | trace 导出、A/B 报告、长期采集和故障测试 | 同画质验收通过，限制和剩余瓶颈有记录 |

P1～P4 每阶段保留独立变更记录和测试结果。只有基础日志仍不能解释原生阻塞时，再进入可选深度 profiler 阶段。

未来实施时保留当前可运行版本作为回退基准，可使用独立分支或明确的候选目录，不覆盖唯一可用副本。用户尚未指定新版本目录时，不在本设计阶段创建或部署新的运行版本。

预计交付物包括：候选代码、配置说明、日志字段说明、分析工具、同条件 A/B 报告、使用说明及原版本回退入口。部署到远端需在实际实施授权下执行，先验证文件，再使用独立任务运行验收。

回退以切回原入口和配置为主；所有运行时 Stage 改动位于临时层，并恢复脚本拥有的设置。原生调用异常不能安全取消时，不跨线程强行销毁资源；标记实例状态不可继续采集，按当次授权进行后续处置。
