## 二、已有线索——需要重新验证，不能直接当作根因

历史测量显示：

- 正式 step_async() 阶段平均约 6.57 秒/组，主线程约占一个 CPU 核的 94.2%。
- 正式生成排空阶段平均约 0.86 秒/组，主线程约占一个核的 99.6%。
- 容器整体 CPU 峰值约 4.64 核，配额约 14 核，未观察到配额限流。
- GPU 利用率波动，整体没有持续吃满。
- 当前已有后台图像编码和写盘并行机制。
- 曾发现关闭传感器更新时只关闭相机，LiDAR 仍然更新。
- 曾出现缺少渲染完成快照、需要追加渲染的问题。

必须区分：
“某阶段内主线程很忙”不等于“该函数本身消耗了全部 CPU”。
await 期间可能执行其他任务、回调和引擎更新，需要线程栈和时间线证据进行归因。

## 三、先建立正确性基线

梳理实际调用链：
运动与姿态写入 → 场景同步 → 渲染提交 → GPU 执行 → 完成通知 → 数据回读 → 编码 → 发布与写盘。

明确各环节：

- 调用函数、所属线程、使用的外部接口。
- 输入输出以及缓冲区所有权。
- 哪些操作推进仿真时间。
- 哪些操作读取或修改场景。
- 哪些环节必须完成后才能进入下一组。
- 哪些耗时互相重叠，不能简单相加。

优化必须保证：

- 同一采集组的场景姿态在相关传感器采集完成前保持固定。
- 不读取上一组旧数据，不混用不同组的相机、点云或位姿。
- 时间戳、TF、相机参数与对应数据一致。
- 异步消费者使用的缓冲区在处理完成前不会被覆盖。
- 有效采集数量和录制内容完整。

不能通过丢帧、降低分辨率、减少传感器、跳过必要同步，伪装成同等条件下的性能提升。这些变化只可用于诊断实验，必须明确标注。

## 四、深入到原生线程和 GPU 时间线

优先考虑现有的 Kit/Carbonite Profiler、Tracy、Nsight Systems，以及可用的原生 CPU 采样工具。先检查版本兼容性和权限，再决定具体方案。

不要只使用 Python 函数计时或 nvidia-smi 平均利用率。

需要尽可能获得：

1. 主线程原生调用栈和热点路径。
2. 线程实际运行、休眠等待和调度情况。
3. Vulkan 图形工作及相关 CUDA 工作的提交与执行时间线；不要只采集 CUDA 而漏掉 RTX 图形路径。
4. CPU—GPU 同步、锁等待、轮询、内存复制和回调时间。
5. Kit 更新、USD/场景同步、OmniGraph、渲染准备、传感器输出之间的关系。
6. 采集组、渲染请求、完成回调与数据读取的对应关系。

为关键阶段建立 group_id、request_id、sensor_id 和跨线程关联标记。请求编号只能用于关联，不能单独证明数据属于本次渲染。

区分启动加载、着色器编译、预热与稳定采集阶段。详细追踪使用短窗口，单独评估诊断工具开销，性能验收需在关闭高开销追踪后复测。

## 五、围绕假设做受控实验

一次优先改变一个因素，并保持场景、姿态、传感器参数和采集要求一致。

重点排查：

- 空闲、运动、暂停阶段是否仍在执行不必要的传感器工作。
- 传感器数量增加时，耗时是线性增长还是存在固定同步开销。
- 相机、LiDAR 单独运行及组合运行时是否互相阻塞。
- 渲染、annotator/writer、CPU 回读、编码和写盘分别贡献多少耗时。
- 不变的姿态或参数是否仍被重复写入，导致场景反复标脏或更新。
- 排空逻辑是否等待了无关任务，或者重复执行全局等待。
- 缺少完成快照是否来自回调接收窗口、执行顺序或生命周期错误。
- 高 CPU 是否来自有效计算、忙轮询、场景同步、数据复制或其他回调。

如现有框架不能隔离某个因素，制作独立诊断程序，不要强行在生产入口堆叠临时逻辑。

## 六、根据证据实施优化

不局限于现有代码结构，但必须说明每个改动针对哪条已验证的瓶颈。

可探索：

- 统一相机与 LiDAR 的更新开关，消除阶段外渲染。
- 基于实际完成信号的采集调度，减少重复渲染和不必要的全局等待。
- 减少重复场景同步、属性写入和数据复制。
- 缓冲池、批处理、有界队列和明确的背压机制。
- 将线程安全、数据已经独立的处理工作移出主线程。
- 在接口确实支持时实现异步回读及跨组流水线重叠。
- 若原框架存在结构性限制，制作替代采集后端或最小验证原型。

不要因为函数名带 async 就认定它没有阻塞。
不要假设增加 Python 线程能并行执行 Kit、USD 或 RTX 的线程受限操作。
不要在仍有传感器读取当前场景时推进下一组姿态。
不要仅为了提高 GPU 利用率而增加无效工作。
