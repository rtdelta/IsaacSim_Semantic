## 核心判断

**最看好的激进路线，是做一套“针对这台挖掘机、这些传感器、这些运动方式进行专门优化的 GPU 采集引擎”。** 场景提前编译，运动批量计算，传感器共享计算结果，必要时用学习模型替代部分昂贵计算。

下面几条路线，比继续增加线程更有可能改变性能上限。其中有些能保留现有计算含义，有些属于需要验证误差的研究方案。

## 1. 利用刚体运动的不变性，把部分计算永久消掉

这是最适合当前项目的算法突破之一。

假设传感器和某个车体部件都安装在挖掘机上：

\[
T_{\text{sensor}}^{world}=T_{\text{root}}^{world}T_{\text{sensor}}^{root}
\]

\[
T_{\text{part}}^{world}=T_{\text{root}}^{world}T_{\text{part}}^{root}
\]

两者的相对变换为：

\[
T_{\text{part}}^{sensor}
=(T_{\text{sensor}}^{root})^{-1}T_{\text{part}}^{root}
\]

**整机的世界变换完全抵消了。**

这意味着：

- 挖掘机整体前进、转向、俯仰、横滚，不会改变固定安装的雷达与固定车体之间的几何关系。
- 对安装在固定车体上的雷达，部分车体自遮挡可以预计算。
- 大臂、小臂、铲斗只根据影响自身的关节更新。
- 环境单独根据整机与传感器的世界位姿计算。

可以把每条射线的工作拆成：

```text
固定车体：查预计算结果
运动部件：计算当前相交
外部环境：计算当前相交
                 ↓
            统一决定回波
```

这里**完整保留车体遮挡**，并没有屏蔽挖掘机。对于不透明几何的最近回波，可比较各部分命中距离；Gaussian 透射、多回波则需要保留并合并更完整的沿射线信息。

这种方法直接减少必须执行的工作量。固定射线模式、固定安装关系越多，价值越大。相机也能利用几何关系不变性，但颜色、阴影和环境光通常不能一起永久缓存。

## 2. 把多个雷达合成一个共享的几何查询系统

如果部分雷达仍然原点重合、视场重叠，可以进一步共享计算。

传统做法是：

```text
MyAiry 查询场景一次
MyNZ3 查询场景一次
其他雷达再查询一次
```

更激进的设计是：

```text
收集各传感器需要的射线
        ↓
合并重复查询、按方向和空间区域排序
        ↓
批量查询同一份几何或 Gaussian 场景
        ↓
分别应用各传感器的距离门限、噪声和回波模型
```

这里有两个层次：

- **精确共享**：原点、方向和所需几何查询一致的射线，只计算一次公共结果。
- **近似共享**：先生成高密度球面距离表示，再供各传感器采样，边缘和不确定区域补发精确射线。

第二种更激进，但遮挡边缘、细杆、铲斗边沿容易出现误差；不同发射原点也不能简单共用一张球面图。

**先共享几何查询，再分别计算传感器响应，比直接共享最终点云更合理。** 即使没有完全重复的射线，方向排序和批处理也可能改善缓存与 GPU 执行效率，收益需要实测。

## 3. 把整个采集过程编译成 GPU 批量计算

可以借鉴 **Madrona 的多世界批量执行**和 **Dr.Jit 的场景专门化编译**。

Madrona 将大量环境状态组织在 GPU 内存中，批量执行和渲染；Dr.Jit 则根据具体场景简化计算图，生成专门的并行内核。这些研究证明了这类架构的可行性，但它们的演示帧率不能直接套到我们的四路高清鱼眼和十三路雷达上。[Madrona](https://madrona-engine.github.io/)、[Dr.Jit](https://rgl.epfl.ch/publications/Jakob2022DrJit)。

对当前项目，可以这样组织：

```text
一次提交一批采样状态
        ↓
GPU 批量计算关节和传感器变换
        ↓
批量生成射线、剔除无关部件
        ↓
批量渲染图像与点云
        ↓
批量输出
```

关键改变是：

- USD 主要用于资产编辑和导入。
- 离线执行阶段使用紧凑的 GPU 数组。
- 静态几何只存一份，各采样状态保存独立的变换。
- Python 负责提交任务与管理结果。
- 避免每个传感器、每个小步骤都经过应用事件循环。

融合内核、CUDA Graphs、异步队列都可以成为实现工具。但并不是内核越大越快：过度融合可能增加寄存器压力，复杂光线也可能更适合分阶段队列。应根据实际任务选择。

## 4. 为鱼眼和雷达重新选择渲染算法

当前鱼眼图像必须经过 Isaac 的完整采集链路。激进方案可以让专用 Gaussian 渲染器直接接收姿态和鱼眼模型。

值得研究：

- **3DGUT**：用 Unscented Transform 处理 Gaussian 在畸变相机中的投影。
- **3DGRT**：通过射线追踪 Gaussian 粒子。
- **SimULi**：面向相机和 LiDAR 的 Gaussian 仿真，包括跨传感器一致性设计。[3DGRUT 官方项目](https://github.com/nv-tlabs/3dgrut)、[SimULi 论文](https://arxiv.org/abs/2510.12901)。

可以构建两种后端：

| 后端 | 思路 | 需要解决的问题 |
|---|---|---|
| 专用混合后端 | 鱼眼采用 Gaussian 光栅化，雷达采用射线查询 | 两者的几何、透明度和遮挡必须一致 |
| 联合传感器表示 | 场景同时学习相机和雷达响应 | 可能需要重新训练资产和补充数据 |

这里最有价值的变化是：**直接计算最终需要的传感器输出，减少为通用应用服务的中间过程。**

但 SimULi 并不是给当前 RGB 3DGS 换一个渲染函数就能使用；其传感器模型与我们的 Instant 射线模式也需要对接验证。

## 5. 更前沿：让小型神经网络回答部分射线查询

这是改变算法性质的一条路线。

传统计算：

```text
射线 → 遍历 BVH → 几何相交 → 距离和属性
```

学习型计算：

```text
射线、局部状态 → 小型网络 → 预测命中、距离或外观
```

**N-BVH** 已经研究了用神经表示回答射线查询，并与传统几何混合使用；Instant-NGP／tiny-cuda-nn 则提供了多分辨率哈希编码和高效小型网络实现的技术基础。它们提供的是近似表示，压缩率或单项加速不能直接等同于本项目的端到端提升。[N-BVH](https://www.iliyan.com/publications/NeuralBVH/)、[Instant-NGP](https://nvlabs.github.io/instant-ngp/)。

针对挖掘机，更倾向于**按刚性部件建立局部模型**：

- 车体一个模型。
- 大臂、小臂、铲斗分别一个模型。
- 环境使用另一种表示。
- 射线先转换到各部件局部坐标，再查询。

这样移动部件时无需重新训练整个世界。

实际可采用混合策略：关键几何和遮挡边缘保留精确计算，部分外观或复杂远景使用学习模型。不过网络置信度不能自动构成误差保证；若点云用于几何对齐或测量，必须单独验证深度和遮挡误差。

**这条路线潜力大，但研究成本和数据风险也最高。**

## 6. 从“每帧全部重算”改为“只计算变化造成的影响”

挖掘机运动通常连续，而且每一步只改变少数部件。可以维护：

- 上一状态的可见部件。
- 射线此前命中的对象。
- 动态部件影响到的图像区域和射线范围。
- 新出现、被遮挡或失效的区域。

每次姿态变化后，先计算哪些结果可能失效，再集中处理这些区域。

例如铲斗小幅移动时，理论上可以避免重新处理大量完全不受影响的区域。但必须检测新遮挡者；“上一帧命中地面”不代表这一帧铲斗不会挡在前面。

相机光照还可以研究 **ReSTIR** 等时空样本复用算法，以减少达到目标质量所需的光照采样。它主要针对光照积分，不会直接解决 Gaussian 数据加载或雷达时间戳问题，当前 RTX 后端也可能已经包含类似技术。[ReSTIR GI](https://research.nvidia.com/publication/2021-06_restir-gi-path-resampling-real-time-path-tracing)。

对于当前场景，优先研究**严格有效的几何缓存和失效判定**，再研究有误差的图像重投影。

## 7. 方向选择与推荐组合

| 方向 | 对当前项目的判断 |
|---|---|
| 刚体局部坐标分解、固定车体相交缓存 | **最值得优先做算法原型** |
| 多传感器共享查询、射线批处理 | **与 Instant、多雷达非常匹配** |
| GPU 批量状态与专用执行管线 | **决定长期性能上限** |
| 独立鱼眼 Gaussian 渲染 | **值得做小规模替代验证** |
| 增量可见性、时空缓存 | **运动连续时有潜力，正确失效是难点** |
| N-BVH、学习型传感器模型 | **作为研究分支，明确接受近似后再扩大使用** |

最想验证的组合是：

> **刚体不变性消除重复计算 → 多传感器共享查询 → GPU 批量执行 → 专用鱼眼渲染 → 异步输出。**

它能够同时减少计算量和调度开销，并尽量保留已有数据含义。神经网络代理则作为更激进的一层，在明确哪些输出允许近似后加入。

本方案讨论阶段仅做资料研究和分析，没有安装、下载运行程序或修改远端；本次归档仅新增本文档，没有实施上述优化。
