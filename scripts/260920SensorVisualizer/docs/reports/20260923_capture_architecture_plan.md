# 顺序采集、并行处理与渲染质量方案

2026-09-23。本轮仅分析：只读检查远端文件、下载并校验八张已有 PNG，未修改远端场景、配置、代码或运行进程。用户已确认：新增离线模式不限速，交互模式保持 RTF 不高于 0.1。

## 已核实的基线

- 数据集：20260923_102450_024594_6ccb02。337.075 秒墙钟、8.283333 秒仿真时间，RTF 0.02457。
- 83 组，每组 4 张 1920×1080 图像、13 路 Instant LiDAR；本轮回读帧数一致，无空点云或非有限 XYZ。
- 录制时平均使用约 2.51 个 CPU 核，GPU 整卡利用率 14.60%；Kit 已有约 400 个线程。
- 图像同步保存平均 2.614 秒/组，总计 216.975 秒，约占墙钟时间 64.4%。计时包含转换、编码和写文件，不能全部归因于 PNG 压缩或磁盘。
- 先前的 0.1 倍速上限也是明确的吞吐限制。离线模式应移除墙钟限速；它不改变数据的仿真时间间隔。

## 强制时序与新模块边界

采样时间使用整数帧号与整数纳秒，所有传感器和 TF 采用同一采样时刻。源数据时间与目标采样时间需要核验，不能仅给旧缓冲数据重写时间戳。

1. `TrajectoryPlanner`：按采样时间生成整机、关节和传感器位姿。手动跳转、速度到位和周期模式统一为轨迹接口。
2. `SceneStepper`：更新运动，完成 PhysX / USD / Fabric 与渲染场景同步，然后冻结仿真时间和场景状态。当前规定运动可计算目标姿态；若未来引入动力学，必须保留必要物理积分步骤。
3. `CaptureCoordinator`：固定同一场景版本，执行必要预热，再触发四相机和十三雷达。等待各传感器产生本组的新结果，快照位姿和标定；预热结果不进入数据集。
4. `FrameBufferPool`：预分配双缓冲或三缓冲。完成 GPU 输出等待并取得独立、不可变的数据副本后，才允许更新下一组场景。GPU 读回与同步接口的可用性需要针对已安装版本验证。
5. `EncoderPool`：CPU 工作池并行处理图像编码和消息序列化。先比较 2 / 4 个工作者；线程效果不足时采用独立进程与共享内存，不从 Kit fork 图形上下文。
6. `DatasetWriter`：单一写入者按帧号整理并直接写 MCAP。使用分段文件与旁路提交索引，全部传感器成功才标记整组提交；MCAP 本身不提供跨话题组事务。完整记录图像、点云、TF、CameraInfo、鱼眼原始模型参数、渲染参数和帧索引。保留 ROS 2 消息定义和元数据，验证标准回放兼容性。
7. `PreviewPublisher`：可选 ROS / RViz 输出，独立显示节拍；不再以 ROS 网络回环作为离线记录的必经路径。
8. `Telemetry`：分开测量运动提交、GPU 渲染、读回、编码、写盘、队列等待以及墙钟/仿真时间。

同组运动和采集串行；不同组的渲染、CPU 编码及写盘流水并行。队列有界，满时暂停产生下一组，不能静默丢帧或无界积压。停止时排空已接收任务、完成提交，再关闭 MCAP。

离线采用常驻无界面 Kit 进程，场景与 Render Products 只初始化一次，关闭非必要视口。先用单 GPU 单渲染进程共享场景；多 GPU / 多实例以后按采集片段分工，每个工作者产出完整多传感器组。同一 L40 上多个完整 Kit 仅作为实测候选，不保证更快。

PNG 独立文件变成可选导出，避免默认“写 PNG—再读取—合并整个 MCAP”。无损与既有消息接口优先，不默认换成 JPEG 或视频。GPU 图像编码仅在格式、精度和接口满足要求时评估，不能将 NVENC 当作无损 PNG 加速器。

## 暂停采集的技术验证点

v04 的 `rep.orchestrator.step(delta_time=0, pause_timeline=True, wait_for_render=True)` 可作为固定仿真时间的组织方式。官方文档确认 delta_time=0 不推进时间，RT subframes 可用于材料加载和减少时域伪影。

当前项目相机回调、运动图和 ROS 发布包含播放状态判断；因此不能只加 timeline.pause。先用一相机一雷达验证：暂停下产生新结果、实际渲染姿态正确、原始传感器时间与采样计划一致、重复预热不多录。通过后扩展四相机十三雷达。v04 连续扫描历史机制不直接套到 Instant LiDAR。

## 当前渲染模式与模糊分析

根场景 combine_scene_16_terrain_fisheye.usda 继承的 scene13 Render Settings 作者值为 `RealTimePathTracing`，DLSS 为 `performance`；安装配置也有 Performance 默认值。它对应 RTX Real-Time 2.0，本身采用路径追踪及重建技术，不能称为纯光栅化。与 v04 正式采集的 Interactive Path Tracing 配置不同。

现有会话没有记录运行时渲染参数快照，GUI 或运行时覆盖仍存在不确定性。当前证据可确定文件配置，不能百分之百追溯每次录制时实际 AA / DLSS / 采样值。

相机模型是 OpenCV fisheye，1920×1080，fx=fy=578.7734375。鱼眼是投影模型，不是单独的渲染引擎。源相机 lens fStop=0；记录中的 exposure:fStop=5 是曝光参数，不能拿它证明景深虚焦。

已查看四方向的首尾八张原始 PNG，并验证与远端 SHA256 一致。近地面和部分车体表面有涂抹/松散细节，围栏标记与立方体边缘相对清楚；最后一帧仍存在，因此模糊已写入原始图像，不能仅归因远程桌面。首尾姿态不同，不能作为严格加载或收敛实验。

需要分离以下因素：

1. 3DGS 源资产的 Gaussian 尺寸、训练视角和局部细节。近距离、新视角可能暴露素材不足；增加等待或采样不能恢复原素材不存在的细节。
2. DLSS Performance 与时域重建。若该设置生效，低内部渲染分辨率、重建和去噪可能影响细薄边缘/高频纹理；场景运动后历史数据也可能影响结果。
3. 加载与收敛。代码已等待 USD loading 归零，但未明确确认 GPU 资源/渲染场景准备完成及图像收敛。USD 加载、GPU 就绪、时域收敛是不同条件；整个过程不能依靠固定 sleep 证明。
4. 鱼眼角分辨率与素材投影。宽视角分摊有限像素，需要在相同投影、相同视角下比较。若提高分辨率须同步缩放相机内参。
5. 重叠背景、Gaussian 变换或可见性。原始图可见较平整浅色区域与粗糙地面交错，单凭图像无法区分素材空洞、其它地面露出或遮挡设置，需逐层隔离验证。

加载未完成有可能，但目前无证据确认它是主因。录制前已有预览，且首尾都有局部模糊，使“仅启动时未加载”的解释不充分。

## 最小对照与实施顺序

1. 先冻结一组相机/挖掘机姿态，保存运行时渲染设置；比较同姿态首帧与充分预热后图像（例如 1/4/16 个子帧）。固定灯光和曝光，预热不改变仿真时间。
2. 同姿态对比 RT2 Performance、Quality / 原生分辨率 AA、Interactive PT 合理采样；一次只改一类参数，不把全因子组合直接用于正式采集。子帧数量不等同于 PT samples-per-pixel。
3. 分别隔离 3DGS、普通几何、不同地面；用相同视角比较素材参考渲染，定位源素材与渲染器差异。
4. 实现暂停采集的一相机一雷达验证，再扩展全部传感器。
5. 实现后台流水线、直接 MCAP 和高速无界面运行；确认首尾、停止排空、失败提交和标准回放。
6. 同一轨迹与质量配置做旧/新基准：完整采集组/墙钟秒、P95 延迟、各阶段耗时、队列长度、CPU/GPU/显存、无丢组、同组时间和几何一致性。画质提升可能增加 GPU 工作量，不能把提质与纯吞吐收益混成一个数字。

验收目标以合格完整数据组吞吐为主；CPU/GPU 利用率用于判断瓶颈，不保证或追求没有有效产出的满载。当前平均约 0.246 组/墙钟秒，优化收益需要实测，不预先承诺倍数。
