## 结论

当前使用不顺畅的主要原因有三层：

1. 原生渲染及停止/排空同步耗时过长，采集时 Kit 出现数秒的更新间隔。
2. 运动与调节只能在组间推进，一组约耗时 11.5 秒，因此用户看到的是短暂移动、长时间停住，按钮命令还要排队等待。
3. 存在真实的交互缺陷：末组排队的命令没有执行或取消反馈、实时状态与编辑框不同步、整机直接定位会隐式清除速度、活动会话 JSON 不更新采集进度。

正式数据可以正常写出，但这不代表交互可用性已达到要求。后台 PNG 和 MCAP 写盘不是本轮主要瓶颈。

## 运动为什么看起来停顿

sample_hz=10、physics_hz=60，每个后续组推进 0.1 秒仿真运动，然后固定姿态采集约 11 秒。用户看到的是约 0.4 秒推进，随后长时间停住。

34 组时间戳从 0.333333333 到 3.633333333 秒，首尾采样跨度仅 3.3 秒。采集墙钟时间 392.72 秒，因此按这个跨度计算的有效比例约 0.00840，即真实时间约 119 秒对应 1 秒采样仿真跨度。该比例包含首组渲染和结束收尾，是会话总体测量，不是纯运动步骤实时因子。

Interactive 的 0.1 是上限，不是保证达到的倍率。本轮主要受采集吞吐限制，没有证据表明额外的 0.1 倍速节拍等待是主要耗时来源。

16:45:18—16:45:47，用户在空闲状态多次应用 arm/bucket Periodic 命令。日志显示命令在几毫秒内被接收应用，但空闲期间没有运动推进，直到 16:50:52 开始下一轮采集。这可以直接解释“点了 Apply 但没动，重复点仍没动”的感受。

## 额外交互/日志缺陷

源码静态核对显示：

- Actual 角度主要在采集 runner 回调中刷新，空闲直接 Apply 后没有立即同步读数。
- XYZ/Yaw 输入框是初始化时的草稿，不随整机运动刷新；Apply XYZ/Yaw 会同时应用所有字段，可能把未修改轴重新设置成旧草稿值。
- BaseController.direct 会清零平移速度和转向速度。16:53:04 启动速度，16:53:27 又提交直接位置，后者会停止持续平移；面板没有明确提示这一结果。
- 活动 session.json 的 complete_groups 仍为 0，仅收尾时更新；新会话实际已有 9 条 group_written。不能用该字段的活动值判断没有采集。
- job_spec.json 的 motion 在 GUI 采集中为空，GUI 调整主要存在诊断事件及实际状态消息中；不能仅凭 Job JSON 复现本轮交互动作。
- 控制状态文本容易被频繁的阶段更新覆盖，普通命令应用事件还缺少 control_id；影响用户反馈和后续准确延迟分析。
