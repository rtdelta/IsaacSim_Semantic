# v07 双卡实现与实测证据

日期：2026-10-10，北京时间。实现基线是保留的 v06，目标为双 L40 实例。以下区分运行验收、数据验收与尚未证明的性能收益。

## 1 本轮实际交付

- 独立 `sensor_visualizer_v07` 包，运行代码不导入旧版；保留熟悉的网页分类、关节三种模式、整机移动与姿态、安装调整、轨迹和三种采集模式。
- GPU 0 交互、GPU 1 正式采集；分别记录 renderer 编号、CUDA ordinal、UUID、PCI 以及可获得的实际数组设备。相机 Warp 数组已观察到 `cuda:1` 对应 GPU 1，原生 Kit 设备表亦显示采集使用 GPU 1。SDK 没有暴露的源设备字段不会被伪造为已核实。
- 根据可见 128 逻辑 CPU、cgroup 约 28 核时间预算设置工作池：交互 8、采集 12、PhysX 4、编码 4，数值库内部线程限制为 1。线程上限不等于独占 CPU。
- 交互异步渲染与正式同步采集分开；正式进程关闭未使用的默认 viewport 更新。
- 常驻采集引擎复用兼容场景和 RenderProduct；每轮独立 job、捕获 ID、epoch、writer、日志及输出目录。任务完成与服务存活分开判断，空闲可以显式关闭。
- 保留 13 路 Instant LiDAR、4 路 1920×1080 鱼眼、RealTimePathTracing、DLSS 2、AA 3、初始化预热 4、相机预热 16、正式子帧 2。未靠降低传感器质量换取指标。
- 关键事件与常规事件的有界队列、产生/写入计数、序号检查、完整性标记、逐进程/线程/物理 GPU 资源、原生启动日志和 Python GC 耗时记录。

## 3 交互响应

以下来自 `20261010_173141/evidence_summary.json`，持续按键与完整质量采集同时进行。

| 阶段 | 按键回执 P95/P99 | 交互更新间隔 P95/P99 | 更新最大间隔 |
| --- | --- | --- | --- |
| 第一轮 8 组 | 27.002 / 31.069 ms | 33.954 / 36.849 ms | 56.125 ms |
| 第二轮 3 组 | 24.660 / 28.356 ms | 32.494 / 35.675 ms | 45.680 ms |

回执从 socket 接收开始计时，包含主线程队列等待。它不包含浏览器、网络、云桌面和最终屏幕呈现。统计使用去重的回执和更新序号，阶段边界最多可能偏移一个发布帧。此结果支持稳定采集期间控制及时响应，但不能替用户宣布所有操作都无卡顿。

首次服务准备阶段仍出现一次 **703.261 ms 更新间隔**。对应交互回调墙钟约 665.7 ms，线程 CPU 约 660.9 ms；嵌套 `physx_root_write` 为 657.188 ms 墙钟、654.789 ms 线程 CPU，USD 同步约 2.497 ms。这说明该样本的主要耗时落在 `Articulation.set_world_poses` 的调用区间内；尚不能凭这段日志分清 Python GC 与 native 内部工作。新增 GC 开始/结束及分代总计就是为后续分解此长尾，不改变收集阈值。

补充日志后的 `20261010_174511` 又捕获到准备阶段 452.400 ms 的更新间隔：同一主线程的一次 GC 第 2 代收集耗时 **417.571 ms**，完整落在约 **427.534 ms** 的交互回调内，占约 97.7%。这次长回调的主要耗时已能归因于 GC；不能反推上一轮 703 ms 停顿也必然由 GC 导致。该短轮稳定采集两轮按键 P95 为 22.749/23.348 ms、更新间隔 P95 为 29.797/29.750 ms。没有为得到这些数字禁用 GC。

退出后 Reinitialize 的一次参数回执约 2.046 s，属于重建生命周期，不应混入日常参数输入延迟。退出期间拒绝续租按键的回执同样须按状态解释。

已证明常驻重复任务无需重新启动 Kit；首次准备仍约 56–60 s。**稳定采集吞吐尚未证明比 v06 更快**。缓存顺序、交互窗口及样本数不同，不应得出双卡加速倍数。

GUI 并发首轮的稳态 `frozen_group_capture` 平均约 10.24 s，主要包含约 9.3 s 的相机预热/渲染等待和约 0.77 s 正式渲染等待。时钟推进约 0.50 s；PNG 编码每图约 0.25 s，已在后台并行并与采集重叠。各嵌套区间不能重复相加。

该轮离散资源样本：采集进程平均约 1.63 个 CPU 核，最高约 2.7，RSS 约 12 GiB；GPU 0 平均约 60%，GPU 1 平均约 25–30%、峰值 98–100%，GPU 1 显存约 8.3–10.6 GiB。测量阶段没有新增 cgroup CPU 限流计数。这些是阶段样本，不能代表一个短函数的精确 GPU 执行或 SM occupancy。

资源采样器约一秒采样，曾测到单次墙钟约 160 ms，包含两个 `nvidia-smi` 子进程与读取等待；同时记录线程 CPU 成本，不能把它的墙钟等待直接当成交互主线程阻塞。

## 5 剩余问题和后续实验

1. 首次准备的 CPU 长尾、重建时延仍在；短轮已定位一次主线程第 2 代 GC，下一次应研究对象分配和安全的收集时机，并继续对齐 GC 与 `physx_root_write`，再决定 native/Fabric 路径的实验。
2. 相机预热和 RTX 等待仍主导单组吞吐。未提供 GPU kernel/queue 级 Nsight 追踪，也未证明可以安全减少预热。
3. hydratexture 释放、Fabric/版本、SdfPath、音频、ECC 等 SDK 原生 warning 仍有记录；没有把重复采样等同于修复。实际种类、精确计数与原文见该轮 warning 聚合及 `.kit.log`。新增 PhysX 越界错误已用范围校验防止。
4. 修复后通过两轮 GUI 验证，尚未完成 30 分钟人工交互与常驻服务资源稳定性验收；此前 100 组长测不能替代修复后的长测。
5. CUDA 池化异步回读、Fabric/USDRT 运行时变换、两卡同时离线分片尚未接入默认运行路径。它们需要 SDK 完成契约与数据一致性对照，不把能力探测当成已经取得收益。
6. 场景复用键检查根 USD 和运行配置，不能检测所有 payload 被外部修改的情况；外部资产改动后请关闭并重新准备 worker。

这版交付优先解决交互与采集相互影响、重复任务生命周期和证据不足；后续底层优化应从实测长尾和预热热点继续，而非追求利用率数字本身。
