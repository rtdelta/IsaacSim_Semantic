# Gaussian / Motion BVH 核心探究目标与执行方案

制定日期：2026-09-17。状态：计划已制定；本文所列新实验尚未启动。

依据：同目录 REPORT.md、native_evidence.txt、audit_data.json。既有证据已定位当前安装的 PreprocessedGaussians::buildTlas 拒绝非零 AccelStructMode 并提前返回；上游模式选择和各渲染路径的触发条件仍待验证。

**总目标**

解释原项目为何需要关闭 Motion BVH，建立并验证以下因果链：

活动相机/雷达与生效设置 → Hydra/RTX 调用上下文 → SceneDB 构建模式 → Gaussian 构建是否完成 → 图像或点云中的 Gaussian 是否保留。

最终结论需要分清三个层次：

| 层次 | 必须回答的问题 | 合格证据 |
|---|---|---|
| 触发条件 | 哪个输出路径、哪些设置与几何条件会触发？ | 最小对照、实际组成配置、原生错误及输出 |
| 实现机制 | 谁传入不支持模式，在哪一步停止，如何影响测量？ | 参数、调用模块/偏移或调用栈、构建前后与输出对应关系 |
| 能力边界 | 属于本构建的哪些路径；其他完整构建是否有差异？ | 同一复现包的跨构建对照，或明确的实现/厂商资料 |

“已有 guard”“已知关闭后恢复”“可能存在数学困难”分别是代码事实、现象和假设，不能互相替代。

**阶段 0：建立可信的最小实验入口**

工作内容：新增独立入口，加载已验证的最小 Gaussian 与 Mesh 参照物；支持 camera_only、lidar_only 和 conditional_both 三类活动输出；与业务 runtime.py 解耦。

固定条件：同一完整 Isaac 安装、同一 GPU、同一渲染后端和场景委托、相同靶标与姿态，关闭测量噪声。阶段 1 固定 multiTick=false、perSensorTickTlas=false，几何和传感器都静止。

必须检查：

- 列出实际组成后的 Gaussian、OmniLidar、RenderProduct 及其绑定；记录扩展加载状态，但不把它当作活动输出的证据。
- camera_only 不存在活动 LiDAR 渲染请求；lidar_only 没有活动视口或额外 RGB RenderProduct。继承的 RenderProduct、自动创建的输出也计入核查。
- 记录启动参数以及初始化后、首个渲染帧后读取的实际 Carb 设置，避免启动器或扩展覆盖设置。
- Motion OFF 下 Gaussian 必须可见/可测，Mesh 参照物必须正常。基线失败则先修复输入或采集条件，该 case 不用于归因。
- 若平台无法证明输出路径隔离或实际 Motion BVH 模式，标记证据缺口，不能凭没有报错宣布兼容。

产物：独立运行入口、监督器、配置快照、原文件哈希清单和一个通过验收的 OFF 基线。

**阶段 1：确定谁触发限制，首批 8 组**

每行分别 OFF/ON，独立冷启动。阶段 0 的成功基线满足同样条件时可以复用，不重复计为新证据。

| 组别 | 几何 | 活动输出 | Motion BVH | 主要观察 |
|---|---|---|---|---|
| A1 / A2 | Mesh | 仅相机 | OFF / ON | 基础相机路径与设置有效性 |
| A3 / A4 | Gaussian + Mesh 参照物 | 仅相机 | OFF / ON | 没有雷达时是否报相同错误、Gaussian 是否可见 |
| B1 / B2 | Mesh | 仅一个 LiDAR | OFF / ON | 基础传感器路径与 Mesh 返回 |
| B3 / B4 | Gaussian + Mesh 参照物 | 仅一个 LiDAR | OFF / ON | 是否报相同错误、Gaussian 靶区返回是否消失 |

每组先完成资产流送和渲染就绪，再按固定仿真步数采集；等待条件、采集帧区间和超时上限保存到 manifest。不同渲染路径可采用合适的就绪条件，但同一 OFF/ON 对必须一致。关键失败及其对应成功条件各复测一次以检查稳定性；只有结果不一致时才扩大重复次数。

后续分支：

| 结果 | 下一步 |
|---|---|
| 相机独立也失败 | 已证明此相机配置下不依赖 LiDAR；追踪相机侧 mode 和调用路径 |
| 相机正常，LiDAR 独立失败 | 追踪传感器上下文及模式选择；检查相机是否真正使用 Motion BVH |
| 两者独立正常，旧的共存实验失败 | 新增同场景相机 + LiDAR 的 OFF/ON 两组，检查共享上下文与 engine 配置 |
| 新实验均正常 | 对照旧 probe 的源码快照、实际属性、RenderProduct 与生效设置，定位差异 |
| 纯 Mesh 或 OFF 基线也失败 | 停止该分支归因，先解决环境或输入错误 |

阶段完成标准：得到一对仅改变必要条件即可稳定复现/消除原生错误的最小 case，并说明各活动输出的实际模式证据；不能只报告开关值。

**阶段 2：拆解原项目的必要触发条件**

只在阶段 1 确认的触发路径上增加变量，避免完整排列全部参数。

1. 设置依赖：从 Motion=1、multi=0、perSensor=0 开始，分别增加 multi、perSensor，再按需要检查共同开启。新配置先验证纯 Mesh；本身不受支持的配置单独记为配置错误。检查哪项是必要条件、哪项只改变调度或错误表现。结合原生错误与返回，判断项目同时关闭三项的保护范围。
2. Instant：复制同一传感器的配置到新层，仅切 instantLidar，保持发射数组、噪声及其他属性一致；OFF/ON Motion 配对。远端 NZ3 原数组全零，这个实验研究模式选择和兼容触发，不以扫描畸变差异作为结论。之后按需加入一个具有非零发射时间偏移的控制配置，单独解释时间调度影响。
3. 运动状态：依次比较全静态、仅传感器刚体运动、仅 Gaussian 刚体运动。运动由一种已验证且记录清楚的时间驱动提供。只有触发依赖运动状态时，才进一步拆分变换更新和生命周期；本阶段不扩展为 P95 精度评测。
4. 资产类型：先保证 Motion OFF 下合法可见/可测，再对比少量原生 ParticleField3DGaussianSplat 与真实项目 Gaussian；属性差异逐项保存。若最小原生资产也失败，支持该类型路径存在限制，但不能据有限样本断言所有 Gaussian 表达都失败。

产物：最小触发条件表，分别说明必要条件、已排除条件、仍未知条件；明确 NZ3 Instant 是否改变触发。

**阶段 3：把触发条件连接到原生函数**

在最小失败 case 和对应成功 case 中，优先使用可用的日志与诊断接口采集：

- 活动 RenderProduct、Hydra/RTX 上下文和 engine 标识（接口可取得时）。
- SceneDB 构建所收到的 AccelStructMode，及其与开关、传感器模式的关系。
- 首次错误、Gaussian 构建活动、输出缺失的时序。

若现有接口不足，为独立实验进程准备调试条件，获取 buildTlas 入参及调用栈/调用模块与偏移。当前安装未发现 gdb，不能将此项写为已有能力。只针对本任务新进程诊断，不修改磁盘上的供应商二进制。

使用 ELF Build ID、库哈希和进程映射基址定位；未知的枚举名称保留为数值，剥离符号后的邻近导出符号不作为真实函数名。不能只凭错误字符串恢复全部上游逻辑。

分析需要区分：模式选择不当；Gaussian 该构建模式未实现；上下文共用导致不支持对象进入该路径；构建失败后仍消费不完整资源。先找证据，再判断哪一种成立。

完成标准：能够把一个具体调用上下文与拒绝分支连接起来；无法取得的源代码或符号明确列入限制。厂商为何未实现属于更深的设计原因，不能仅从 early return 推断。

**阶段 4：确认版本边界，再回到原项目**

- 将最小场景、脚本、配置和输出打成固定复现包，在可取得的另一个完整 Isaac/Kit 构建中运行同一成功/失败对照，记录精确版本与依赖。保留当前安装，不单独替换 SceneDB 动态库。
- 如果没有第二个可用构建，结论限定于当前构建；不把“预计升级解决”写为已验证修复。
- 最小机制明确后，用新覆盖层回到项目场景，验证真实资产与设置是否符合相同因果链。
- Stop/Play 崩溃作为独立问题采集首错、退出阶段、调用栈和 GPU dump。未经证据连接，不把回波遗漏和崩溃合并为一个已证明的原因。

**每组统一验收与交付**

输出数据分四项判定：原生拒绝错误、Gaussian 图像可见性、Gaussian 测量返回、进程/生命周期状态。单纯“有点云”“没有崩溃”不算 Gaussian 兼容通过。

Gaussian 返回优先用可靠对象标识判断；标识不可用时，使用空间隔离的近处 Gaussian 靶标和更远 Mesh 背板，保存靶区返回与背板返回。相机用固定视角、相同采集条件和必要的可见性指标，保存原图供核验。

每组保存 manifest.json、settings.json、scene_inventory.json、日志、图像/点云原始数据、过程退出状态与简短判定。最终提供：最小复现包、触发条件表、带证据的调用链、版本结论和未解决问题清单。

所有实验新建入口、根层/会话层和输出目录。既有 USDA 及其引用层禁止编辑/保存，EditTarget 指向新层；需要 RenderVar 时在新层预先定义。每轮核验既有 USDA 哈希。每次只运行一个 GPU 实验进程，监督器只管理自己的进程组。

**执行优先级**

先完成阶段 0–1，取得独立输出路径的最小复现。随后结合结果交替推进阶段 2 的必要条件对照和阶段 3 的调用追踪；最后做阶段 4。每一轮结束只扩展能够区分剩余假设的实验，避免无差别增加场景、运动方式和精度测试。
