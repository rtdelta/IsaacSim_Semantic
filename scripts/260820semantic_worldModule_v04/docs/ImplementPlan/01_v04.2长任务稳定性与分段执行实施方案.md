# v04.2 长任务稳定性与分段执行实施方案

## 1. 文档信息

- 项目：Semantic World Module v04
- 阶段：v04.2 Long-running Stability and Segmented Execution
- 状态：已实施并完成阶段验收
- 部署模式：云电脑单机部署，Studio 与 Headless Runtime 分进程运行
- 核心运行环境：Omniverse Kit、Isaac Sim、Replicator、RTX

## 2. 阶段背景

v04.1 已经完成针孔相机采集的核心闭环：用户可以在独立 Kit Studio 中配置 USD Stage、传感器、场景变体、模态、渲染、轨迹和输出策略，再由独立 Headless Runtime 执行 Realtime 或 Path Tracing 采集。

当前 Runtime 仍然以一个 Isaac Sim 进程执行整个 Job。对于数百至数万帧 Path Tracing 任务，这种模式存在以下风险：

- Kit、RTX、Hydra 或 Replicator 状态可能长期积累。
- 显存或主机内存可能缓慢增长。
- 单个进程崩溃会中断整个长任务。
- 当前 `segment_frames` 只是配置字段，尚未真正控制独立 Worker 分段。
- 缺少长时间无进度检测、GPU telemetry 和结构化失败报告。
- Supervisor 可以控制一个 Runtime，但还不能编排多个独立 Segment Worker。

因此，v04.2 的工作重点不是增加新传感器，而是把现有采集闭环升级为可长时间运行、可诊断、可停止和可恢复的工程系统。

## 3. 阶段性核心目标

本阶段的核心目标是：

> 让 720p Path Tracing 数百至数千帧任务能够分段运行、持续监控、明确失败，并在进程崩溃或人工停止后可靠恢复，同时保证已经提交的采集文件不会被重复覆盖。

具体目标包括：

1. `segment_frames` 真正控制独立 Isaac Segment Worker。
2. 每个 Segment 完成后完全关闭 Replicator、Stage 和 SimulationApp。
3. Studio 退出后，轻量 Job Runner 继续编排剩余 Segment。
4. 任务停止、Worker 崩溃或超时后均有明确状态。
5. Resume 从首个未提交 capture group 继续。
6. 已提交文件在恢复前后保持内容和 SHA256 不变。
7. 持续记录进度、帧耗时、GPU 利用率、显存和温度。
8. 卡死或异常退出时自动生成结构化失败报告。
9. 完成 Realtime 与 720p Path Tracing 长任务验证。

## 4. 本阶段范围

### 4.1 包含内容

- Segment 数据模型和确定性规划器。
- 任务级 Job Runner。
- Segment Worker 启动与生命周期管理。
- Segment、Job 两级状态机。
- Ledger 驱动的恢复和完整性校验。
- Watchdog、heartbeat 和 no-progress timeout。

这些内容分别留到 v04.3 传感器扩展和后续产品化阶段。

## 5. 核心架构

### 5.1 总体链路

```text
Studio / CLI
    ↓
StudioController / Supervisor API
    ↓
SameHostSupervisor
    ↓
Job Runner（轻量任务级进程，不加载 Isaac Sim）
    ↓
Segment Planner
    ↓
Segment Worker 000（Headless Isaac）
    ↓ 完成并释放 GPU/Kit 资源
Segment Worker 001（Headless Isaac）
    ↓
Segment Worker 002
    ↓
Job 完成
```

### 5.2 单个 Segment 的采集链路

```text
SegmentSpec
    ↓
Host Preflight
    ↓
SimulationApp(headless=True)
    ↓
打开 USD Stage
    ↓
应用并回读 Render Profile
    ↓
Sensor Override Session Layer
    ↓
Motion 定位到 Segment 起点
    ↓
Variant Visibility Session Layer
    ↓
重置 Path Tracing History + Warmup
    ↓
Sensor Driver / Replicator Annotator
    ↓
Modality Encoder
    ↓
Atomic Frame Writer
    ↓
Ledger Commit + Status + Heartbeat
    ↓
关闭 Annotator、RenderProduct、Stage、SimulationApp
```

### 5.3 模块依赖原则

- Segment Planner 是纯 Python，不导入 `omni`、`pxr` 或 `isaacsim`。
- Job Runner 是轻量进程，不创建 GPU 或 Kit 对象。
- Segment Worker 继续通过 ABI-safe wrapper 启动 Isaac Runtime。
- Job Runner 只通过文件状态、子进程和稳定协议管理 Worker。
- Ledger 是采集是否完成的最终事实来源。
- Segment 状态不能替代文件和 Ledger 完整性检查。
- 所有新模块保持独立边界，方便未来替换 Supervisor 或扩展分布式执行。

## 7. 核心数据模型

### 7.1 SegmentSpec

```json
{
  "schema_version": 1,
  "job_id": "job-example",
  "job_content_digest": "sha256...",
  "segment_id": "segment_000003",
  "segment_index": 3,
  "start_frame": 750,
  "frame_count": 250,
  "end_frame_exclusive": 1000,
  "expected_capture_groups": 750,
  "motion_positioning": "absolute_seek",
  "variant_ids": ["full_scene", "excavator_only", "front_teeth_only"]
}
```

要求：

- 相同 JobSpec 必须生成完全相同的 Segment 计划。
- `job_content_digest` 必须与 JobSpec 一致。
- Segment 范围不能重叠或产生空洞。
- 最后一个 Segment 可以小于 `segment_frames`。
- SegmentSpec 编译后不可由 Runtime 修改。

### 7.2 SegmentStatus

建议状态：

```text
planned
queued
starting
running
stopping
completed
failed
cancelled
```

主要字段：

- `segment_id`
- `state`
- `pid`
- `process_token`
- `started_at_utc`
- `updated_at_utc`
- `completed_at_utc`
- `last_heartbeat_utc`
- `last_commit_utc`
- `capture_groups_current`
- `capture_groups_total`
- `exit_code`
- `failure_code`
- `message`

### 7.3 JobRunnerStatus

建议增加：

- 当前 Segment 和 Segment 总数。
- 当前 capture group 和总 capture group。
- 最近一次成功提交时间。
- 当前 Worker PID。
- 平均帧耗时。
- 预计剩余时间。
- 当前 GPU 显存使用量。
- 是否允许 Resume。
- failure report 路径。

## 8. Segment Planner 实现规则

### 8.1 基础分段

例如：

```text
start_frame   = 0
frame_count   = 10190
segment_frames = 250
```

生成：

```text
segment_000000 = frame 0..249
segment_000001 = frame 250..499
...
segment_000040 = frame 10000..10189
```

### 8.2 变体处理

每个 Segment 默认处理该帧范围内的所有启用变体，保持现有输出 key：

```text
(frame_index, sensor_id, variant_id)
```

这样 Segment 只是执行边界，不改变数据集目录结构和 Ledger 主键。

### 8.3 分段大小

初始默认值继续使用 Project 中的 `segment_frames`，但 UI 应给出提示：

- Segment 太小：频繁启动 Isaac、打开 Stage 和 warmup，吞吐降低。
- Segment 太大：单进程运行时间变长，异常影响范围扩大。

Path Tracing 初始建议从 100～500 帧/段验证，再根据实际单帧耗时调整。

## 9. Job Runner 实现方案

Job Runner 是本阶段最关键的新模块。

职责：

1. 加载并验证 JobSpec。
2. 读取或创建 `segment_plan.json`。
3. 使用 Ledger 判断各 Segment 的真实完成情况。
4. 选择第一个未完成 Segment。
5. 启动独立 Segment Worker。
6. 监控进程身份、状态、心跳、Ledger 和 telemetry。
7. Worker 正常退出后校验 Segment 完整性。
8. 完整则启动下一 Segment；否则停止 Job 并生成 failure report。
9. 所有 Segment 完成后将 Job 标记为 completed。

Job Runner 不能：

- 导入 Isaac Sim。
- 创建 Replicator 对象。
- 仅凭 Worker exit code 判断 Segment 完成。
- 在失败后无限自动重启。
- 覆盖已经提交的采集文件。

## 10. Segment Worker 改造

Runtime CLI 新增：

```text
--segment-spec <path>
--segment-id <id>
```

运行时只处理：

```text
[segment.start_frame, segment.end_frame_exclusive)
```

Segment Worker 启动顺序：

1. 校验 JobSpec digest 和 SegmentSpec。
2. 执行主机、磁盘、GPU 和 ABI preflight。
3. 启动 SimulationApp。
4. 打开 Stage。
5. 应用并回读 Render Profile。
6. 写入传感器 Session Layer 覆盖。
7. 定位到 Segment 起始状态。
8. 重置 RTX history 并 warmup。
9. 对每个变体和帧执行未完成 capture group。
10. 每次 commit 后更新 Ledger、状态和 heartbeat。
11. 校验本 Segment 所有 capture group。
12. 完整释放 Runtime 资源并退出。

## 11. Motion 分段策略

### 11.1 Absolute Seek

适用于 CSV 中包含绝对关节位置和绝对根位姿的任务。

```text
暂停 Timeline
→ 设置 Segment 起始时间
→ 写入目标绝对位姿
→ 执行一次同步更新
→ 冻结物理状态
→ reset render history
→ warmup
→ 正式采集
```

这是本项目现有挖掘机 RGB/语义采集的主要路径。

### 11.2 Single Worker

以下任务默认不能直接 absolute seek：

- 接触动力学结果。
- 速度、加速度和 IMU。
- 运动畸变 LiDAR。
- 增量控制器。
- 依赖历史状态的自定义 Motion。

对此提供 `single_worker` 策略：保持一个连续 Runtime，不进行独立分段。

### 11.3 Replay From Zero

对于需要连续历史但允许低性能的任务，可提供 `replay_from_zero`：

```text
每个 Segment 从时间零开始
→ 回放至 Segment 起点
→ 再开始采集
```

该策略保证正确性但会产生按 Segment 数增长的重复模拟成本，必须在 Preflight 中明确提示。

## 12. Ledger 驱动的恢复

Resume 流程：

```text
读取 JobSpec 和 digest
→ 校验任务内容没有变化
→ 读取 Ledger
→ 校验 Ledger 声明的文件存在且非空
→ 检查并隔离未提交 staging
→ 计算首个未完成 capture group
→ 更新剩余 Segment 状态
→ 启动新的 Segment Worker
```

恢复规则：

- 已提交文件不允许覆盖。
- staging 文件不视为完成。
- Ledger 存在但目标文件丢失或为空时明确失败。
- JobSpec digest 不一致时拒绝 Resume。
- Segment 状态与 Ledger 冲突时，以 Ledger 和文件完整性为准。
- 每次 Resume 使用新的 Worker PID 和 process token。
- Resume 前后的已提交文件应保持 SHA256 一致。

## 13. Watchdog 设计

建议配置：

```json
{
  "heartbeat_timeout_seconds": 120,
  "no_progress_timeout_seconds": 600,
  "segment_start_timeout_seconds": 300,
  "graceful_stop_timeout_seconds": 30,
  "telemetry_interval_seconds": 5
}
```

检测内容：

- Worker PID 与 process token 是否仍匹配。
- Runtime heartbeat 是否按期更新。
- Ledger 是否持续增加。
- 当前 capture group 是否超过最大合理耗时。
- GPU 是否仍然可见。
- 显存是否接近设备上限。

异常处理：

```text
检测到超时或失活
→ 将状态标记为 stopping
→ 请求优雅退出
→ 等待 graceful_stop_timeout
→ 必要时按稳定进程身份强制终止
→ 标记 Segment failed/cancelled
→ 写 failure_report.json
→ Job 等待人工 Resume
```

默认不实施无限自动重试，避免 GPU page fault 或确定性配置错误形成崩溃循环。

## 14. Telemetry 设计

建议输出：

```text
output/<job_id>/telemetry/
├─ gpu.jsonl
├─ progress.jsonl
└─ segment_timing.jsonl
```

`gpu.jsonl` 记录：

- timestamp。
- GPU 名称和 driver。
- GPU utilization。
- memory used/total。
- temperature。
- Segment 和 Worker PID。

`progress.jsonl` 记录：

- 当前 Segment。
- 当前帧和变体。
- capture group 进度。
- 最近提交时间。
- 单帧耗时和移动平均。
- 预计剩余时间。

`segment_timing.jsonl` 记录：

- Worker 启动耗时。
- Stage 加载耗时。
- warmup 耗时。
- 正式采集耗时。
- 资源关闭耗时。
- Segment 总耗时。

## 15. Failure Report

失败时生成：

```text
output/<job_id>/failure_report.json
```

至少包含：

- Job、Segment 和 Worker 标识。
- JobSpec digest。
- Segment 帧范围。
- 最后一条成功 Ledger entry。
- 最后一次 heartbeat 和 commit 时间。
- 异常类型、message 和 traceback。
- exit code 和终止方式。
- GPU telemetry 摘要。
- Python executable、版本和实际 libpython。
- Render Profile 与有效 RTX readback。
- staging 内容摘要。
- 是否满足 Resume 条件。
- 建议恢复位置。

## 19. 验收标准

v04.2 完成必须同时满足：

- `segment_frames` 真正对应独立 Segment Worker。
- Segment 计划确定、完整且无重叠。
- 每段结束后 Isaac/Kit 进程完全退出。
- Job Runner 在 Studio 退出后继续运行。
- Job Runner 能可靠区分 completed、failed 和 cancelled。
- Stop 能终止当前 Worker，并且不损坏已提交文件。
- Worker 崩溃不会让 Job 错误完成。
- Resume 能从首个未提交 capture group 继续。
- 已提交文件恢复前后 SHA256 不变。
- Watchdog 能识别心跳超时和无进度。
- GPU 和进度 telemetry 持续写入。
- 失败时生成完整 failure report。
- 720p Path Tracing 长跑不存在静默停止。
- 源 USD 不被修改。
- 新代码不引用任何旧版本项目脚本文件。
- 本地测试、云端 Isaac 测试和真实渲染验证全部通过。

## 20. 风险与控制

### 20.1 分段启动开销

每段都需要启动 SimulationApp、加载 Stage 和 warmup。需要通过 telemetry 测量并选择合理的 Segment 大小，不能为了频繁释放资源而过度牺牲吞吐。

### 20.2 Path Tracing 跨段一致性

每个 Segment 必须在目标姿态重置渲染历史并执行同样的 warmup。不能继承上一个 Worker 的 RTX accumulation。

### 20.3 Motion 正确性

只有明确声明并验证过 absolute seek 的 Motion 才能快速定位。动态仿真任务必须使用 single worker 或 replay 策略。

### 20.4 进程误杀

所有终止操作必须同时校验 PID 和 process token，不能只按 PID 终止进程。

### 20.5 自动重试循环

默认失败后等待人工 Resume。后续若增加自动重试，必须设置次数上限，并区分暂时性错误和确定性配置错误。
