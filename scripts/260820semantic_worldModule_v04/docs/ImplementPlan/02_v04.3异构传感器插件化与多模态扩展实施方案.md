## 1. 文档信息

- 项目：Semantic World Module v04
- 阶段：v04.3 Heterogeneous Sensor Plugins and Multimodal Capture
- 文档日期：2026-08-25
- 当前状态：已实施并完成云端真实验证
- 前置基线：v04.2 长任务稳定性与分段执行已完成验收
- 部署模式：云电脑单机部署，轻量 Kit Studio 与 Headless Isaac Runtime 分进程运行
- 核心运行环境：Omniverse Kit、USD、Isaac Sim、Replicator、RTX

> 实施结果（2026-08-25）：72 项普通 Python 测试、Kit Studio 启动、原生鱼眼、RTX LiDAR、Realtime/Path Tracing、Schema v2、20 帧真实 Stop/Resume 和数据集校验均通过。动态 LiDAR Motion BVH 精度与完整人工 UI 视觉走查作为已记录的后续专项。详见 `docs/Validation/2026-08-25_v04.3异构传感器与多模态验证报告.md`。

## 2. 阶段定位

v04.2 解决的是“现有针孔相机任务能否长时间稳定运行”的问题。它已经建立了 Job Runner、独立 Segment Worker、Ledger 恢复、Watchdog、Telemetry、失败报告和 Path Tracing 长任务验证等稳定性基础。

v04.3 解决的是“如何在不继续修改主采集链路的情况下增加不同类型传感器和数据模态”的问题。

本阶段不能只是在 `CaptureCoordinator` 中加入鱼眼、LiDAR 的条件分支。这样虽然可以短期得到数据，却会重新形成与 v02 类似的耦合：每增加一种传感器，都要修改初始化、触发、读取、编码、输出、校验和 Studio 界面。v04.3 要做的是一次通用化改造，让后续传感器扩展主要发生在插件目录和配置文件中。

本阶段的总体目标可以概括为：

> 在完整保留 v04.2 分段、监控、停止和恢复能力的前提下，把当前“针孔相机图像采集系统”升级为“配置驱动的异构传感器与多模态采集平台”，并完成鱼眼相机、LiDAR、多针孔相机 Rig 的真实 Headless 采集闭环。

## 3. 核心目标

### 3.1 插件化目标

新增一种传感器时，允许开发者只增加：

1. 一个 Sensor Plugin。
2. 一个延迟加载的 Runtime Driver。
3. 必要的 Modality Plugin 或 Encoder。
4. 插件 Manifest、参数 Schema 和测试。

正常情况下不再修改以下模块：

- `CaptureCoordinator` 的主循环。
- Job Runner 和 Segment Planner。
- Supervisor 与 Watchdog。
- Studio 的通用传感器编辑框架。
- Ledger 的基本恢复规则。

### 3.2 真实传感器目标

本阶段计划完成以下真实插件，而不是占位插件或假数据插件：

- 针孔相机：保留现有能力，并迁移到新版统一契约。
- 鱼眼相机：从 USD Prim 读取有效参数，支持显式配置覆盖，并在云端 Isaac Runtime 中完成真实渲染。
- LiDAR：从 USD/Isaac Sensor Prim 读取配置，完成真实点云或扫描数据采集。
- 多针孔相机 Rig：多个相机作为一个同步组，在同一仿真时刻完成触发、读取和批次提交。

### 3.3 多模态目标

在现有 `rgb`、`semantic_id`、`semantic_color` 基础上，建立可以容纳不同数据形态的统一输出管线，并按远端环境的实际接口能力分批实现：

- Depth：米制深度原始数据，必要时生成可视化图。
- Surface Normal：原始法线数据和可选可视化图。
- Instance Segmentation：实例 ID 原始数据和颜色可视化图。
- LiDAR Point Cloud：结构化原始数据，并提供通用交换或可视化格式。
- 可选 Range Image：仅当所选 LiDAR 后端稳定提供时实现。

每个模态必须声明自己的数据类型、形状、坐标系、单位、编码格式和内容校验规则，不能继续假定所有输出都是二维 PNG。

### 3.4 参数来源与可审计目标

所有传感器遵守统一的参数优先级：

```text
USD Stage 已编写参数
    ↓
插件默认值（仅补全 Stage 未提供的可选参数）
    ↓
Project 中的显式 override（最高优先级）
    ↓
Runtime 启动后回读 effective parameters
```

对鱼眼相机而言，用户通常只需要选择或填写 `prim_path`。代码应自动读取 Stage 内已有的相机、投影和标定数据；只有 Stage 没有提供的必需项，或用户确实想覆盖的参数，才需要在配置中填写。系统不得静默猜测缺失的鱼眼标定参数。

LiDAR 采用相同原则：优先从选定 Prim 和其应用的 Schema/API 读取通道数、扫描范围、频率、量程、变换等数据，再合并显式覆盖。

输出必须保存参数来源和最终生效快照，使每一批数据都可以追溯到：

- 原始 Stage 值。
- 插件默认值。
- 用户覆盖值。
- Runtime 实际回读值。
- 插件和后端适配器版本。

### 3.5 稳定性继承目标

v04.3 不能以牺牲 v04.2 稳定性为代价。所有新增传感器任务继续具备：

- Headless 执行。
- 独立 Segment Worker。
- 人工停止和继续。
- 崩溃后恢复。
- 已提交文件不被覆盖。
- Watchdog 与 Telemetry。
- 结构化失败报告。
- Realtime 和 Path Tracing 能力检查。

### 4.1 包含内容

- Sensor/Modality 插件契约 v2。
- 插件 Manifest、能力描述和参数 Schema。
- 插件自动发现与注册机制。
- Project Schema 向后兼容迁移。
- 通用 Sensor Sample、Capture Context 和 Calibration Snapshot。
- 图像、数组、点云和结构化数据的统一编码与校验。
- 鱼眼相机真实 Runtime Driver。
- LiDAR 真实 Runtime Driver。
- 多相机 Rig 和同步采集批次。
- Studio 中的插件驱动传感器表单、模态选择和有效参数预览。
- 分段执行与有时间窗口传感器的兼容性检查。
- 本地纯 Python 测试和云端真实 Kit/Isaac 验证。

### 4.2 暂不包含内容

- 多台云电脑的分布式任务调度。
- 多 GPU 并行渲染。
- 实时流式传输、ROS Bridge 或消息总线。

以上内容可以使用 v04.3 的插件边界继续扩展，但不作为本阶段验收条件。

## 5. 相对于 v04.2 的核心调整

| 对比项 | v04.2 | v04.3 调整 |
|---|---|---|
| 阶段核心 | 长任务稳定、分段、恢复和诊断 | 异构传感器、同步采集和多模态扩展 |
| 传感器实现 | 真实支持针孔相机 | 真实支持针孔、鱼眼、LiDAR 和多相机 Rig |
| Registry | `build_default_registry()` 手工注册内置类 | Manifest/Loader 自动发现，内置插件也走同一注册机制 |
| Sensor Plugin | 提供匹配、参数读取、验证和 Driver 工厂 | 增加版本、能力、参数 Schema、时间模型、标定和后端需求描述 |
| Runtime Driver | 约定 `initialize/trigger/read/close`，载荷偏相机图像 | 使用统一 Capture Context 和 Sensor Sample，支持图像、数组、点云及结构化载荷 |
| 模态编码 | 主要围绕 PNG、NPY 和语义图 | Encoder 声明数据类别、单位、dtype、shape、扩展名和内容校验器 |
| 参数解析 | 针孔相机 Stage 参数加 override | 所有传感器统一 Stage/default/override/effective 四层参数来源 |
| 捕获粒度 | `(frame, sensor, variant)` 单传感器 capture group | 增加 `(frame, variant, sync_group)` 同步 Capture Batch；保留单传感器兼容视图 |
| 多相机 | 可配置多个针孔实例，共享 Replicator trigger | 增加 Rig、统一时间戳、成组触发、成组完成标记和外参快照 |
| 时间假设 | 主要是时刻采样相机，适合 absolute seek | 插件显式声明 instantaneous/exposure_window/scan_window，并参与分段策略检查 |
| Studio | 界面字段仍可能面向现有相机 | 根据插件参数 Schema 自动生成表单和模态矩阵，增加 Prim 发现、Rig 编辑和标定预览 |
| Preflight | 检查 Stage、Renderer、运动和基础插件 | 增加后端能力、投影模型、Annotator、输出格式、同步和分段兼容性检查 |
| 数据审计 | 保存相机 effective parameters | 保存统一 Calibration Snapshot、坐标系、单位、时间戳、插件与后端版本 |

这里最重要的变化是：v04.2 的插件边界已经存在，但通用程度还不足。v04.3 要进行一次受控的“主链路泛化”，之后新增传感器不再继续扩大主链路。

## 6. 核心思路

### 6.1 配置描述“采集意图”，插件解释“如何执行”

Project 只描述：

- 使用哪个传感器插件。
- 绑定哪个 Prim。
- 哪些参数来自 Stage，哪些参数被覆盖。
- 属于哪个同步组。
- 在每个场景变体中采集哪些模态。
- 使用哪个渲染和时间配置。

具体如何识别 Prim、创建 Isaac/Replicator 对象、触发、读取和释放资源，由对应插件及其 Runtime Driver 实现。

### 6.2 Studio 和 Runtime 共用纯数据契约，不共用重型对象

Studio 只加载轻量 Kit、USD 和插件的纯 Python 描述部分，用于：

- 浏览 Stage。
- 发现兼容 Prim。
- 展示传感器参数。
- 编辑 Rig 和模态矩阵。
- 预检并编译 JobSpec。

Runtime 才延迟导入 Isaac Sim、Replicator、RTX Sensor 等重型模块。插件模块顶层不得创建 GPU、Render Product、Annotator 或仿真对象。

### 6.3 能力驱动，而不是传感器类型条件分支

每个插件返回结构化 Capability Descriptor，例如：

```text
数据能力：rgb / semantic / depth / point_cloud
时间模型：instantaneous / exposure_window / scan_window
触发域：replicator / rtx_lidar / custom
渲染依赖：Realtime / PathTracing / independent
同步能力：single / shared_trigger / rig_batch
Prim 类型：Camera / Isaac Sensor Prim / custom schema
```

Compiler、Preflight、Studio 和 Runtime 根据能力组合做通用判断，不写 `if sensor.plugin == "fisheye"` 之类的业务分支。

### 6.4 原始数据和可视化数据分离

训练或算法使用的原始数据不能被颜色映射替代。例如：

- `semantic_id.npy` 是原始语义 ID。
- `semantic_color.png` 是可视化结果。
- `depth.npy` 是米制浮点深度。
- `depth_color.png` 是可选预览。
- `point_cloud.npz` 是结构化点云主数据。
- `point_cloud.ply` 是可选交换/查看格式。

两类输出由独立 Modality Plugin 表达，用户可以按场景和传感器分别选择。

### 6.5 同步是显式领域概念

“多个相机在同一循环中被调用”不等于同步。v04.3 引入 Sync Group/Rig：

- 同组传感器共享一个目标仿真时刻。
- 共享触发域的传感器只触发一次。
- 所有成员读取成功后才写入该批次的完成标记。
- 每个样本保存同一个 `capture_timestamp` 和各自的外参。
- 任一成员失败，整个批次保持未完成，恢复时重新补齐。

### 6.6 有时间窗口的传感器参与分段决策

相机通常是时刻采样；旋转 LiDAR 可能需要一段扫描时间。插件必须声明时间模型：

- `instantaneous`：可在绝对定位后直接采样。
- `exposure_window`：采样依赖曝光窗口。
- `scan_window`：采样依赖连续扫描历史。

Segment Planner 和 Preflight 根据 Motion 能否 absolute seek、传感器是否需要历史状态，选择：

- 正常 absolute seek。
- 从段前预滚一段时间。
- 从零回放到段起点。
- 限制为单 Worker。
- 对不可能保持语义正确的组合直接拒绝。

系统不能为了让任务启动而忽略时间连续性。

### 7.2 插件内部的两段式结构

每个 Sensor Plugin 分成轻量定义层和重型运行层：

```text
SensorPluginDefinition（普通 Python / 可在 Studio 中导入）
├─ manifest()
├─ parameter_schema()
├─ capabilities()
├─ matches_prim()
├─ extract_stage_parameters()
├─ validate_configuration()
├─ compile_runtime_payload()
└─ create_runtime_driver()  ──延迟导入──→ RuntimeDriver

RuntimeDriver（只在 Headless Worker 中创建）
├─ preflight()
├─ initialize()
├─ calibration_snapshot()
├─ prepare_capture()
├─ trigger_capture()
├─ read_samples()
└─ close()
```

这样 Studio 可以读取插件的配置能力，但不会加载 Isaac Runtime。

### 7.3 Runtime 通用采集链路

```text
SegmentSpec
    ↓
加载插件目录和能力描述
    ↓
打开 Stage，解析所有 Sensor Effective Config
    ↓
创建 Runtime Driver 和 Calibration Snapshot
    ↓
应用 Variant + Motion 定位/预滚
    ↓
构造 CaptureContext(frame/time/variant/segment)
    ↓
按 Sync Group 生成 CaptureBatch
    ↓
按 Trigger Domain 去重触发
    ↓
各 Driver 返回 SensorSample
    ↓
按 ModalityPlugin 编码并内容校验
    ↓
Atomic Capture Batch Writer
    ↓
Frame Ledger Entries + Batch Commit Marker
    ↓
Progress / Heartbeat / Telemetry
```

## 8. 关键数据契约

### 8.1 PluginManifest

建议至少包含：

```json
{
  "plugin_id": "fisheye_camera",
  "plugin_kind": "sensor",
  "plugin_version": "1.0.0",
  "contract_version": 2,
  "display_name": "Fisheye Camera",
  "definition_class": "semantic_world_v04.plugins.sensors.fisheye_camera:FisheyeCameraPlugin",
  "runtime_requirements": ["replicator", "rtx"],
  "supported_modalities": ["rgb", "semantic_id", "semantic_color", "depth"]
}
```

Loader 只读取 Manifest 和轻量定义类。Runtime 后端导入继续放在 `create_runtime_driver()` 或 Driver 方法内部。

### 8.2 SensorCapability

建议字段：

- `prim_matchers`
- `supported_modalities`
- `payload_kinds`
- `time_model`
- `trigger_domain`
- `synchronization_mode`
- `renderer_compatibility`
- `requires_continuous_history`
- `supports_absolute_seek`
- `supports_stage_overrides`
- `calibration_model`
- `backend_requirements`

### 8.3 EffectiveSensorConfig

编译后不再把松散字典直接交给 Driver，而是形成可审计对象：

```json
{
  "sensor_id": "front_fisheye",
  "plugin_id": "fisheye_camera",
  "plugin_version": "1.0.0",
  "prim_path": "/World/Sensors/FrontFisheye",
  "stage_parameters": {},
  "default_parameters": {},
  "override_parameters": {},
  "effective_parameters": {},
  "parameter_sources": {},
  "sync_group_id": "front_rig"
}
```

Runtime 初始化后再次回读实际值，并将差异写入元数据。必需参数缺失或回读不一致时，任务在正式采集前失败。

### 8.4 CaptureContext

每次采集都显式携带：

- `job_id`
- `segment_id`
- `frame_index`
- `simulation_step`
- `simulation_time_seconds`
- `capture_timestamp`
- `variant_id`
- `sync_group_id`
- `renderer`
- `meters_per_unit`
- `world_coordinate_convention`

### 8.5 SensorSample

Driver 返回统一容器，不直接返回依赖具体插件命名的任意字典：

```text
SensorSample
├─ sensor_id
├─ modality_payloads: modality_id → TypedPayload
├─ calibration_snapshot_id
├─ coordinate_frame
├─ timestamp
├─ sequence/scan metadata
└─ diagnostics
```

`TypedPayload` 可以是 raster、dense array、point cloud 或 structured records，但必须声明 dtype、shape、单位和坐标系。

### 8.6 RigDefinition 与 SyncGroup

建议 Project 增加可选 Rig：

```json
{
  "rig_id": "front_rig",
  "sensor_ids": ["front_left", "front_right", "front_fisheye"],
  "sync_policy": "same_simulation_step",
  "failure_policy": "all_or_retry",
  "reference_frame_prim_path": "/World/Sensors/FrontRig"
}
```

没有 Rig 的传感器自动形成单成员同步组，保持旧项目语义。

## 9. 传感器实现方案

### 9.1 针孔相机迁移

现有 `PinholeCameraPlugin` 和 `CameraRuntimeDriver` 保留真实逻辑，但迁移到 v2 契约：

- 把能力、参数 Schema 和标定快照补齐。
- 把 Replicator 触发实现移动到统一后端适配器。
- Driver 返回 `SensorSample`。
- 现有 RGB/语义结果和目录结构保持兼容。
- 原有 v04.2 Project 通过 migration/compatibility adapter 正常运行。

该迁移是后续鱼眼和 Rig 的参考实现，必须先完成且无回归。

### 9.2 鱼眼相机

#### 参数解析

1. 用户选择 `Camera` Prim 或部署环境支持的鱼眼 Camera Prim。
2. 插件读取 USD Camera 基础属性、投影类型、变换及可用的畸变/标定属性。
3. 对 Stage 中已存在的值标记为 `stage`。
4. 对可安全补全的非必需项使用插件默认值。
5. 对配置文件中显式填写的值标记为 `override`。
6. 缺少投影模型必需标定时，Preflight 报错并指出需要补充的字段。

#### Runtime 后端

实现前先在当前云端 Isaac 版本执行 Capability Probe，确认实际可用的鱼眼投影、Camera Schema 和渲染接口。后端策略为：

1. 优先使用当前 Isaac/RTX 原生支持的鱼眼投影。
2. 通过版本隔离适配器封装具体 API，避免插件定义层依赖版本细节。
3. 原生后端不支持时，不得默默退化成普通针孔相机。
4. 如后续增加“针孔渲染后畸变”的近似后端，必须使用独立 backend ID，并在元数据中明确标记，不能冒充原生鱼眼模型。

#### 验证重点

- 视场角和投影模型正确。
- RGB、语义、深度像素严格对齐。
- Stage 参数、override 和 effective snapshot 一致。
- Path Tracing 与当前后端的兼容性经过实测。

### 9.3 LiDAR

#### 参数解析

插件需要从 Prim 和应用的 Isaac/RTX Sensor Schema 中读取：

- 水平与垂直扫描范围。
- 通道/beam 配置。
- 旋转或扫描频率。
- 最小、最大量程。
- 传感器变换和坐标系。
- 可用时的噪声、回波或强度配置。

所有无法从 Stage 得到但又是后端必需的字段必须通过显式 override 提供。

#### Runtime 后端

- 在云端部署环境中探测可用的 Isaac/RTX LiDAR 接口和 Annotator。
- 使用适配器封装该版本的创建、触发、读取和释放逻辑。
- 输出至少包含 XYZ；只有后端真实提供时才声明 intensity、ring、azimuth、distance、timestamp 等字段。
- 不得用随机点云或从深度图伪造点云作为“LiDAR 已实现”的验收结果。

#### 时间与分段

- 单帧快照式 LiDAR 可声明 `instantaneous`。
- 旋转扫描式 LiDAR 声明 `scan_window`。
- `scan_window` 必须配置预滚或连续回放策略，不能在每段起点无历史地直接读取并声称连续扫描。

#### 输出建议

- 主数据：压缩 NPZ，保存具名数组及元数据。
- 可选交换格式：PLY。
- 元数据：单位、坐标系、传感器到世界变换、扫描起止时间、有效点数、字段列表。

### 9.4 多针孔相机 Rig

现有 v04.2 已能配置多个针孔相机，但 v04.3 增加正式 Rig 语义：

- 一组 Driver 在一个仿真时刻准备。
- 相同 Replicator trigger domain 只执行一次 orchestrator step。
- 读取每个相机的样本和标定。
- 所有成员数据均通过校验后再写批次完成标记。
- 输出保存 Rig reference frame 和每个传感器相对外参。

Rig 不新建专用渲染主链路，它只是对通用传感器实例进行分组和同步编排。

## 10. 多模态与输出方案

### 10.1 Modality Plugin v2

每个 Modality Plugin 至少声明：

- `plugin_id`
- `plugin_version`
- `accepted_payload_kinds`
- `output_artifacts`
- `media_type`
- `dtype/shape/field` 约束
- `unit` 和 `coordinate_frame` 约束
- `validate_options()`
- `encode_runtime()`
- `validate_encoded_artifact()`

### 10.2 建议首批格式

| 模态 | 主数据格式 | 可视化/交换格式 | 说明 |
|---|---|---|---|
| RGB | PNG | PNG | 保持现有格式 |
| Semantic ID | NPY | 无 | 原始 ID |
| Semantic Color | PNG | PNG | 稳定调色板 |
| Depth Linear | NPY float32 | PNG 可选 | 单位固定为米 |
| Surface Normal | NPY float32 | PNG 可选 | 明确相机或世界坐标系 |
| Instance ID | NPY integer | PNG 可选 | 保存实例映射表 |
| Point Cloud | NPZ | PLY 可选 | 具名字段、单位和坐标系 |

如需 EXR，应作为显式编码选项，在远端环境完成读写兼容性验证后再启用。

### 10.3 Atomic Capture Batch

现有单传感器 Ledger key 继续保留：

```text
(frame_index, sensor_id, variant_id)
```

v04.3 额外增加批次完成标记：

```text
(frame_index, variant_id, sync_group_id)
```

写入顺序建议为：

1. 将该批次全部传感器产物写入 staging。
2. 对每个编码产物执行内容校验。
3. 发布各传感器文件并追加兼容 Frame Ledger entry。
4. 最后追加 Batch Commit Marker。
5. 只有 Batch Marker 存在且成员文件完整，Rig 批次才算完成。

Worker 异常退出造成的未完成批次在 Resume 时重新核对；已拥有有效 Frame Ledger 的成员不应被无条件覆盖，但整个批次必须补齐并最终生成一致的 Batch Marker。

### 10.4 标定与元数据

建议新增：

```text
output/
├─ sensor_effective_parameters.json
├─ calibrations/
│  ├─ <sensor_id>.json
│  └─ rigs/<rig_id>.json
├─ ledger.jsonl
├─ batch_ledger.jsonl
└─ sensors/<sensor>/<variant>/<modality>/...
```

相机标定至少包含投影模型、内参或等价投影参数、分辨率、畸变参数、裁剪范围和外参；LiDAR 标定至少包含 beam/scan 配置、量程、单位和外参。

## 11. Studio 实现方案

Studio 仍是轻量 USD 任务编辑器，不承担正式数据采集。

### 11.1 Sensor Catalog

- 行为传感器或 Rig 成员。
- 列为当前插件实际支持的模态。
- 每个场景变体独立选择采集内容。
- 不兼容组合直接禁用，并显示原因。

### 11.4 Rig Editor

- 新建、删除和重命名 Rig。
- 添加或移除传感器成员。
- 选择 reference frame。
- 展示同步策略、触发域和时间模型冲突。

### 11.5 Effective Config Preview

在编译 JobSpec 前展示：

- Stage 参数快照。
- override 差异。
- 最终配置预估值。
- Runtime 后端要求。
- 模态输出格式。
- 分段与时间模型兼容性。

Runtime 实际回读值只有正式 Worker 初始化后才能确定，界面应明确区分“编译预估”和“Runtime 实际值”。

## 12. Compiler、Preflight 与分段策略

### 12.1 编译期检查

- 插件 ID、版本和 Contract Version 是否可用。
- Prim 是否存在且类型匹配。
- 必需参数是否齐全。
- override 是否属于插件允许字段。
- 传感器与模态是否兼容。
- Rig 成员、reference frame 和 sync policy 是否有效。
- Renderer 与传感器后端是否兼容。
- 时间模型与 Segment/Motion 策略是否兼容。

### 12.2 Runtime Capability Probe

由于 Isaac/RTX 传感器接口与部署版本密切相关，v04.3 第一阶段必须在当前云端环境生成机器可读的 Capability Report，至少记录：

- Isaac Sim/Kit/Replicator 版本。
- 可用扩展和 Annotator。
- 鱼眼投影后端。
- LiDAR 创建和输出接口。
- Renderer 兼容性。
- GPU 和驱动信息。

编译时可以做静态预检，Worker 启动后还必须做动态预检。二者都通过后才进入正式采集。

### 12.3 Segment Policy Resolver

根据所有启用传感器中最严格的时间要求生成策略：

```text
全部 instantaneous + Motion 可 absolute seek
    → direct_absolute_seek

存在 exposure_window/scan_window，后端支持有限预滚
    → absolute_seek_with_preroll

需要连续历史且无法恢复历史
    → replay_from_zero 或 single_worker

无法保证语义正确
    → preflight error
```

该策略写入 JobSpec/SegmentSpec，不能由 Worker 临时猜测。

## 13. Project Schema 与兼容策略

v04.3 会增加 Rig、插件版本、能力和编码配置等字段。实现时应采用显式版本迁移，不静默改变旧字段含义。

建议策略：

1. 引入 Project Schema v2。
2. Repository 能读取 v04.2 Schema v1，并迁移成内存中的 v2 模型。
3. 老项目中每个传感器自动成为单成员同步组。
4. 旧 `pinhole_camera`、`rgb`、`semantic_id`、`semantic_color` ID 保持不变。
5. 已经编译的 v1 JobSpec 通过兼容加载器继续可读；不在原文件上原地改写。
6. Studio 保存迁移后的项目时，先生成备份或新版本文件，并在界面明确提示。
7. Ledger 的 v1 单传感器记录继续有效；Batch Ledger 是向后兼容的新增层。

Migration 必须具备固定输入/固定输出的单元测试和 golden files。

## 17. 主要风险与控制方式

### 17.1 Isaac/RTX API 版本差异

风险：鱼眼和 LiDAR 接口随 Isaac 版本变化。

控制：先做 Capability Probe；具体 API 收敛在 backend adapter；Manifest 声明版本要求；Runtime 动态预检。

### 17.2 LiDAR 时间连续性

风险：分段 absolute seek 破坏旋转扫描历史。

控制：显式 time model；预滚/回放策略；不能保证时直接阻止任务。

### 17.3 Rig 的部分提交

风险：部分相机文件已经发布，但批次未完整。

控制：staging、成员内容校验、Frame Ledger 兼容记录、最终 Batch Marker 和恢复核对。

### 17.4 插件配置自由度过高

风险：任意字典导致拼写错误或运行期才失败。

控制：严格参数 Schema、未知字段拒绝、单位和取值范围验证、编译期有效配置预览。

### 17.5 多传感器性能下降

风险：每个传感器重复触发或重复加载资源。

控制：按 trigger domain 去重；共享 Render/Replicator step；分传感器统计耗时；按能力决定是否允许并行读回。

### 17.6 用近似结果冒充真实传感器

风险：后处理畸变或深度反投影被误认为原生鱼眼/LiDAR。

控制：不同 backend ID；输出保存生成方式；验收只认可用户选择并明确记录的真实后端。

## 19. 模块化链路总结

v04.3 的模块化链路是：

```text
USD Stage
  → Stage Adapter 只读索引
  → Plugin Loader 发现传感器能力
  → Sensor Plugin 解析 Stage 参数与 override
  → Compiler 生成 Effective Config、Rig 和 Segment Policy
  → Studio/CLI 提交不可变 JobSpec
  → v04.2 Job Runner 分段启动 Headless Worker
  → Runtime 按 Sync Group 通用编排 Sensor Driver
  → Driver 返回带时间、坐标和标定信息的 SensorSample
  → Modality Plugin 编码原始/可视化产物
  → Atomic Batch Writer + Ledger 提交
  → Validator、Telemetry 和 Failure Report 完成验证与诊断
```

其中，Studio 负责轻量配置，Compiler 负责把配置变成确定性执行计划，插件负责传感器差异，Runtime 只负责通用时序和批次编排，Output Plane 负责格式与原子提交，v04.2 Execution Plane 继续负责长任务稳定运行。

这套架构完成后，增加 Event Camera、Radar 或其他传感器时，主要新增对应插件、Driver、Encoder 和测试，不再为每一种传感器复制或修改整条主渲染链路。
