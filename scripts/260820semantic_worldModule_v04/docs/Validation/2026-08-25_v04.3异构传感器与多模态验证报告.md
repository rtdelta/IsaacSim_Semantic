## LiDAR 连续历史诊断

当 `capture_on_play=False` 时，即使时间线推进 180 次，点云仍为 0 点。启用连续 Replicator 调度并使用 Isaac 6 的 300×300 RTX sensor scheduling surface 后，第 5 次更新、仿真时间约 0.0833 秒获得 `254993×3 float32` 点云。

据此实现独立 `SensorCaptureClock`：只要某个 Driver 声明 `requires_continuous_history=True`，Worker 就在时间线播放期间保持 Replicator sensor tick；关闭 Worker 时统一恢复为 False。Coordinator 中没有 LiDAR 类型判断。

## 数据与原子性检查

`scripts/validate_dataset.py` 已检查：

- Job digest、Renderer readback 和 Segment 完成状态。
- Frame Ledger 对应的全部文件。
- Batch Ledger 的同步组成员完整性。
- PNG/NPY/NPZ/PLY 文件头与内容结构。
- 图像分辨率、数组 dtype/shape/finite value。
- 点云为有限 `N×3` float points 且 N 大于零。
- 每个启用传感器的标定快照。

相机 Rig 的两个成员共享同一 Batch 时间戳和仿真步；LiDAR 作为独立同步组拥有自己的 Batch marker。源 USD 未由 Runtime 保存，传感器 override 和可见性只存在于匿名 Session Layer。

## 已知限制

- RTX LiDAR 连续扫描会使混合 Worker 比纯相机 Worker 更慢，这是生成真实扫描历史的必要成本。
- 云端静态 smoke 日志提示 Motion BVH 未启用；静态点云有效，但动态运动畸变精度必须在启用 Motion BVH 后另行验收。
- Rig 当前实现同仿真步/all-or-retry 语义，不等同于外部硬件纳秒级触发模型。
- Kit 窗口已自动化启动验证，尚未完成所有控件的人工视觉/交互走查。

## 结论

v04.3 的主要技术闭环已通过真实部署验证：配置驱动的异构传感器、原生鱼眼、RTX LiDAR、通用 Sample/Encoder、Rig 同步批次、Realtime/Path Tracing、Schema v2 和 v1 兼容均可工作。新增传感器差异已经收敛在 Plugin/Driver/Modality 边界，Coordinator 不包含具体传感器业务分支。
