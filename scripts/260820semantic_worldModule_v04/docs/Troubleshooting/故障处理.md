# 故障处理

## 启动时在 `_asyncio` 或 `PyObject_Hash` 原生崩溃

原因通常是系统 `libpython` 和 Isaac bundle 的扩展混装。不要直接复用任意 shell 环境启动 worker。正式任务使用 `scripts/launch_job_runner.sh`，Runner 再用 `scripts/launch_runtime.sh` 启动 Worker；wrapper 会把 `/root/isaacsim/kit/python/lib` 放在最前，并把实际加载路径写入预检查快照。

如果 Segment 的 `host_preflight_snapshot.json` 不存在，查看 `segments/<segment_id>/runtime.log` 的启动阶段。如果快照显示 `/usr/lib/.../libpython3.12.so`，启动方式不正确。

## Path Tracing 比 Realtime 慢

这是预期行为。耗时受 SPP、subframes、warmup、分辨率、bounce 和变体数量共同影响。先用 320×180、1 SPP、1 帧做 smoke，再逐步提高质量。Runtime 在打开 Stage 后回读设置，`runtime_snapshot.json` 可确认有效配置。

## LiDAR 报 `returned no finite points`

先确认使用的是 Isaac 6 当前接口：`OmniLidar`、`isaacsim.sensors.rtx.nodes` 和 `IsaacExtractRTXSensorPointCloud`。运行：

```bash
./scripts/launch_capability_probe.sh --output /tmp/v04_capability.json
./scripts/launch_isaac_python.sh scripts/probe_rtx_lidar_capture.py \
  --stage /path/to/scene.usd --prim-path /World/Sensors/Lidar \
  --report /tmp/v04_lidar_probe.json
```

旋转 RTX LiDAR 是 `scan_window` 传感器。若关闭 Replicator 的 `capture_on_play`，时间线虽然推进，扫描历史仍为空。v04.3 由 `SensorCaptureClock` 自动识别连续历史需求；不要在某个 Driver 或外部脚本中再次覆盖该全局开关。探针中 `data` 应最终为 `N×3`，并且 N 大于零。

如果仍为空，检查 Prim 的引用资源是否加载成功、`tickRate`/扫描频率、量程、传感器姿态和场景中是否存在可命中几何体。Warp device array 必须先调用 `.numpy()` 再编码。

## 加入 LiDAR 后相机任务变慢

这是连续扫描的真实成本：LiDAR 必须在时间线播放阶段获得 Replicator tick，不能只在最终相机帧瞬时触发。当前同一 Worker 中的相机 Render Product 也会参与 Replicator 调度，因此混合任务会比纯相机任务慢。可通过降低物理/扫描频率、减少 LiDAR 字段、减少点云可视化格式或把不要求同步的任务拆开来控制成本；不要关闭连续历史来换取看似更快但错误的点云。

日志中的 Motion BVH 警告意味着运动场景的 LiDAR 运动效应可能不准确。静态场景点云仍可用；需要真实运动畸变时必须启用并验证部署版本对应的 Motion BVH 设置。

## v1 项目打开后显示 Schema v2 migration

这是预期迁移。Repository 会先按 v1 内容验证 revision digest，再在内存中补充单成员同步组等 v2 字段。首次保存会写新 v2 revision，并在项目根保留 `project.schema_v1.backup.json`。不要手工把旧 JSON 的版本数字改成 2；应由 Repository 完成迁移。

## 输出目录暂时没有图片

每个采集组先写 `.staging`，全部模态成功后才发布正式文件并追加 ledger。SimulationApp 启动、Stage 加载、warmup 或首个 capture group 尚未提交时，正式目录为空是正常的。查看任务 `status.json`、当前 `segments/<segment_id>/status.json`、该段 `runtime.log` 和 `.staging`。

## Job failed 并生成 `failure_report.json`

先读取 `failure_code`、`runtime_log_tail`、GPU 快照和 `recommended_resume_segment`。CLI 可执行：

```bash
python3 -m semantic_world_v04.cli.supervisor_cli failure-report JOB_ID --output-root OUTPUT_ROOT
python3 -m semantic_world_v04.cli.supervisor_cli segments JOB_ID --output-root OUTPUT_ROOT
```

修复确定性配置错误后不要篡改原 JobSpec；应修改 `.swproject` 并编译新 Job。若报告标记 `resume_allowed: true` 且 JobSpec 未变，可执行 `resume`，Runner 会从 Ledger 的首个未提交 capture group 继续。

## 心跳或无进度超时

`heartbeat_timeout_seconds` 用于判断 Worker 是否仍在更新状态；`no_progress_timeout_seconds` 用于识别进程存活但 Ledger 长时间不增加。Path Tracing 的单组耗时可能较长，生产配置应高于实测最慢 capture group；不应通过关闭看门狗掩盖卡死。

## Articulation 初始化提示 `create_articulation_view` 为 None

这表示 Motion 初始化时 Physics Simulation View 尚未建立。v04.2 已让 `CsvArticulationMotion` 声明 `requires_physics`，Runtime 会先创建并 reset `SimulationContext`，再初始化 `SingleArticulation`。更新代码后可对同一不可变 Job 执行 Resume；静态 `none` Motion 不会创建该 Context。

若仍失败，检查 `articulation_prim_path` 是否指向真正的 articulation root，以及 `joint_columns` 中的 DOF 名称是否能由 `get_dof_index` 解析。失败 Job 的 `failure_report.json` 会保留原始 traceback，Job 最终恢复完成后该报告仍作为历史审计证据存在。

## Resume 报 committed output missing or empty

Ledger 声明的某个正式文件缺失或为空。v04 会停止而不是覆盖。根据 ledger 的 `files` 检查对应文件，从备份恢复或把损坏任务复制到新的测试输出后进行受控修复；不要直接删除整份输出。

## GPU lock 获取失败

已有另一个 Runtime 正在使用同一 GPU 锁。先查询现有 JobStatus 和进程身份。不要直接删除锁文件；锁的有效性由 OS 文件锁而不是文件是否存在决定。

## Studio 影响采集性能

使用 `Run headless & exit`。`Run + monitor` 会同时保留 Kit Viewport，只适合短调试。Studio 退出不影响已启动 Runtime，可用 CLI 查询状态和日志。

## Include Paths 隐藏错误内容

把需要保留的环境或灯光 Prim 放入 `include_paths` 或 `protected_paths`。传感器 Prim 及祖先会自动保护。所有意见都在 Session Layer，重新打开 Stage 可回到源文件状态。
