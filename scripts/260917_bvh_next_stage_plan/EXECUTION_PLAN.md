# 下一阶段：Gaussian 普通 BVH 与场景 Motion BVH 共存的因果实验

日期：2026-09-17。
状态：仅制定方案，未启动新仿真、未修改远端环境。
本方案建立在当前 Isaac Sim 6.0.1-rc.7 / Kit 110.1.2 的实测与反汇编之上。
所有实验只创建新文件。旧 USD/USDA、业务代码、安装库、既有实验脚本和旧报告都不修改。

## 核心目标

解释原项目必须关闭 Motion BVH 的实现原因，并确定这个限制的最小适用范围：

场景开启 Motion BVH 时，Gaussian 自己保留普通 TLAS 是否能够被正确查询？
如果不能，失败发生在资源构建、资源绑定、空间变换、射线时间还是 LiDAR 探测处理中？

成功标准不是消除错误日志，而是建立“输入模式 → 实际资源 → 查询行为 → 最终返回”的可复核因果链。
本轮不以重建整个业务项目、提高点云精度或寻找 Mesh 替代方案为主目标。

## 已有证据与缺口

已确认：
- 静态 Gaussian + 相机独立输出也会触发，活动 LiDAR 不是必要条件。
- Mesh 支持本次测试的运动模式，Gaussian buildTlas 收到模式 1 会主动退出。
- Gaussian 初始化 TLAS 的已观察代码路径使用模式 0。
- Gaussian 实例记录步长为 64 字节，创建前有 Ray Query 能力检查。
- 原生 NZ3 Instant 也受影响。

未确认：
- Gaussian 普通局部 TLAS 是否可以在运动场景查询中继续使用。
- 运动信息能否由 Gaussian 外层实例承担。
- GPU 查询着色器使用的具体遍历方式、时间参数与资源绑定。
- Gaussian 交互结果转为 LiDAR 距离的具体规则。
- NVIDIA 设定限制的设计动机，以及其他版本是否支持。

所有下述假设均针对已观察路径，不把字段步长或错误字符串当作完整算法证明。

## 阶段 0：建立可追踪的资源与时间基线

只用新目录复制、改写此前 worker、runner 与 GDB wrapper；不直接在旧目录运行会写输出的脚本。

首先做以下检查：
1. 记录当前版本、GPU、驱动、目标库 SHA256、ELF Build ID。
2. 对旧项目、引用资产、旧实验脚本/报告及目标库生成本轮保护清单。
3. 使用真实牙齿 Gaussian 与 Mesh 室内壁面，复核 Gaussian Motion OFF 基线有可靠返回。
4. 校验独立输出：相机 case 无活动 OmniLidar；LiDAR case 只有一个活动 LiDAR RenderProduct，均无活动视口。
5. 记录实际引擎创建标志；不能只记录全局 setting。
6. 所有组使用同一种 GDB 运行方式，以控制调试开销与启动条件。
7. 追踪 Gaussian 初始化、TLAS 创建和 buildTlas，关联对象、设备、模式、资源槽与调用栈。

资源检查优先从已确认偏移出发：
- createInstanceBuffer: 0x183030。
- Gaussian 创建与 Ray Query 检查入口: 0x184810。
- GPU 初始化路径: 0x183bb0；调用共用 TLAS helper 的位置: 0x183e68。
- 共用 helper: 0x185110；描述字段 +0x48 控制模式。
- Gaussian buildTlas: 0x184990。
- 构建任务调用点: 0x1eba39。

这些偏移仅适用于目标 SHA256：
3fc6bb790d164decaf40aa52c5c76a6401e67e210f395e40cea9ea20ac6c57f0

若库版本或哈希变化，停止使用旧偏移，重新定位。
资源指针非空不等于有效 BVH；还需观察构建命令、后续使用与输出。
初始化 helper 会被其他对象使用，日志必须依据已验证的调用者 / 对象关联筛选，禁止把所有 helper 调用都认作 Gaussian。

## 阶段 1：唯一关键干预——只改变 Gaussian 局部构建模式

保持整个引擎 Motion BVH 开启。
在新诊断进程中，GDB 到达 PreprocessedGaussians::buildTlas 入口时：
- 确认当前库哈希、对象、调用点、设备以及 bool 参数均符合预期。
- 记录原始模式。
- 仅当模式为 1 时，将该函数的 mode 实参改为 0。
- 读取并记录修改后的实参，然后继续执行原有普通构建代码。

这是临时运行时诊断干预，不修改磁盘二进制，不关闭整个引擎 Motion BVH，也不跳过构建函数。
x86-64 当前入口上的该参数位于 ecx；设置后必须读回验证。
不改变 bool 参数、对象数据、材质、光束配置、输出解析或其他函数的参数。
遇到未知模式、非预期调用者或结构布局时终止该 case，结果归为干预无效。

旧 trace_hook.py 在 seen 达到 12 后会关闭断点：新干预脚本不得沿用这个行为。
所有相关调用都必须持续接受干预；可压缩重复日志，但需保存总调用次数、1→0 修改次数、原始模式分布和异常。
不能在首帧修改后就假定后续帧也保持该模式。

对照矩阵，每种输出分别执行：

| 组 | 几何 | 场景 Motion | Gaussian 局部处理 | 目的 |
|---|---|---:|---|---|
| A | 真实 Gaussian + Mesh 壁面 | 0 | 只观察 | 有效输出基线 |
| B | 同 A | 1 | 只观察 | 复现原失败 |
| C | 同 A | 1 | buildTlas 的 1 改为 0 | 检验普通 Gaussian TLAS 能否共存 |
| D | 同 A | 0 | 启用同一个干预 hook，但不应改参数 | 控制 hook 本身影响 |
| E | 只有 Mesh 壁面 | 1 | 只观察 | 确认 Mesh 运动路径可运行 |
| F | 只有 Mesh 壁面 | 1 | 启用 Gaussian hook，预期命中 0 次 | 确认干预范围 |

输出两类：
- 相机独立输出。
- 原生 NZ3 Instant 独立输出，使用此前有效的 46,080 发射器配置。

首轮 12 个 case，各独立冷启动、单进程占用 GPU。初始预热 60 次更新，采集 120 次更新，并单独记录实际完整输出数。
有恢复迹象时，才对 A/B/C/D 的相关组补到 3 次独立启动，估计基线波动与重复性；不无条件扩大全部矩阵。
可补单 Gaussian 相机 A/B/C 以简化资源关联；之前单 Gaussian LiDAR OFF 没有近处返回，因此不能用作 LiDAR 恢复基线。

测量与有效性：
- 实际引擎标志、所有 buildTlas 调用的原始/有效模式、初始化资源模式。
- 构建路径是否走到正常命令提交；相关资源如何进入后续场景查询。
- 相机目标 ROI 是否恢复，与 A 的背景、轮廓、图像差异对照。
- LiDAR 完整扫描、有效数量、目标返回覆盖、距离、强度、时间戳。
- 按 emitterId、channelId、echo/return 序号和采样时间匹配，不按数组索引比较。
- 固定静态场景可继续使用“目标位于 8 m 内、壁面在约 10 m”隔离返回；同时保存 ROI 与可用的对象标识，避免只凭总点数。
- 非空返回只是“恢复迹象”；必须检查返回确实来自目标、距离没有被背景替代、没有 NaN/Inf。
- C 与 A 的分布差异需同 A 的独立重复波动比较，逐项报告，不编造通用毫米阈值。
- 静态输出恢复只证明这个条件能共存，不能证明运动时间正确或生产可用。

## 阶段 1 的结果分流

| 结果 | 可支持的解释 | 下一步 |
|---|---|---|
| C 相机与 LiDAR 都恢复，并且资源/模式证据完整 | 普通 Gaussian TLAS 至少能参与该静态运动引擎路径；统一模式传递/能力分派是直接障碍 | 进入阶段 2，测试时间和外层运动 |
| C 相机恢复，LiDAR 未恢复 | 共享场景路径部分可用；LiDAR 消费路径或探测条件仍有差异 | 比较 LiDAR 查询资源、命中属性、距离/强度处理；先验证 A 的返回基线 |
| C 两者都未恢复，但正常构建已完成 | 构建之后可能仍存在绑定、查询或变换缺口 | 进入阶段 3，寻找最早发生差异的资源使用点 |
| C 尚未完成正常构建、干预漏命中、资源关联失败或 GPU 出错 | 暂时不能判定上述假设 | 先定位干预有效性、资源状态和故障位置，不能直接归因于硬件 |
| D 或 F 与对应控制不一致 | 调试/干预污染或实验设置问题 | 修正实验，再作因果判断 |

不得把“B 报错、C 不报错”直接写成修复成功。
C 若失败，也不自动证明普通 Gaussian BVH 与 Motion BVH 无法共存；仅否定这个具体干预足以解决。

## 阶段 2：如果静态恢复，区分运动发生在哪一层

按以下顺序开展，先解决一个再扩展：

1. 传感器移动，Gaussian 与场景静止。
2. 传感器静止，Gaussian 的外层 Xform 刚体移动。
3. 只有前两项通过且与根因有关时，才增加 Gaussian 内部中心/尺度变化。
4. 只有平移通过后才增加旋转，不同时叠加多个运动因素。

初始轨迹：
- 固定物理步长 1/60 s。
- 选取约 1 s 的稳定测量窗，单轴匀速 2 m/s，使帧内差异可分辨；轨迹在新场景中设置。
- 用此前有效的 8 通道、10 Hz 定时扫描配置检验扫描内时间。
- NZ3 Instant 继续用于项目配置兼容性验证；不把 Instant 的通过当作扫描内时间插值通过。
- 不沿用此前 NZ3 非 Instant 每缓冲区仅 1 点的无效配置。

时间校准：
旧 probe_v5.py 的运动代码用 frame/60 驱动，下一阶段不直接复用。
新脚本以实测物理步进时间驱动轨迹，同时记录 timeline/Hydra 时间、渲染更新和传感器发射/输出时间。
先用有解析交点的 Mesh 平面校准传感器时序；确认 Motion ON 的结果与实际逐射线姿态相符。
不得仅替换时间变量就宣称同步完成，也不得沿用此前 33.3 ms 偏移为所有 case 的常数。

Gaussian 运动参照：
- 不把另一份 Mesh 模型当作 Gaussian 的精确几何真值。
- 对有限代表射线，在其实际发射时刻冻结同一 Gaussian 和传感器姿态，生成普通模式静态参考返回。
- 比较运动扫描与这些同表示、同姿态、同方向的参考。
- 对匹配失败、仅一方返回、多回波对应不清的射线分别统计，不隐藏在距离 P95 中。
- 报告返回覆盖、绝对距离差 P50/P95/max、时间偏差和帧间稳定性。
- 这仍是内部一致性实验，不是对真实激光雷达的物理标定。

运动阶段通过意味着已观察范围内的运动查询可用；若刚体通过、内部形变失败，结论必须限定于外层刚体运动。

## 阶段 3：追踪剩余的实现缺口

这是按阶段 1/2 结果触发的定位工作，不预设已取得所有内部源码：

A. 资源建立：
- 实例数据在哪里生成，模式 0 / 1 的资源槽如何分配。
- Mesh 与 Gaussian 分别何时提交构建，谁更新与引用结果。
- 是否存在构建了普通槽但运动消费者读取其他槽的情况。

B. 资源绑定与遍历：
- 区分整个场景 TLAS 与 Gaussian 自己的 TLAS。
- 追踪 Gaussian 资源地址/句柄进入场景数据或着色器参数的位置。
- 有条件时观察实际图形 API 的构建描述和查询相关 shader 信息。
- 仅有指针、符号或 Ray Query 检查，不足以证明具体 GPU 指令和时间语义。

C. 时间与坐标：
- 运动信息放在外层实例还是 Gaussian 内部。
- 射线时间是否传到需要使用它的层。
- 世界空间到对象空间的变换是否与射线发射时刻一致。

D. LiDAR 特有结果处理：
只在相机/场景可用但 LiDAR 仍异常时，追踪命中距离、遮挡、透明度/材质属性与返回筛选。
不预设距离取 Gaussian 中心、包围体边界或某个 opacity 阈值。
必要时仅在新场景中单独改变一个 Gaussian 属性，区分其对命中与探测的影响。

到达闭源/符号边界时，输出：
已证实的调用与数据流、最小复现、精确缺失的源码/符号/厂商问题。
不以猜测填补结论，也不向外部论坛或他人发送资料。

## 实现文件规划

以下为执行时要在新目录创建的文件，目前尚未实现：
- probe_static.py：两类独立输出、静态几何和结果采集。
- trace_resources.py：初始化、构建、资源关联的只读跟踪。
- intervene_gaussian_mode.py：Gaussian buildTlas 参数 1→0 的受控干预。
- runner.py / debug_python.py：独立进程、环境隔离、超时与退出管理。
- probe_motion.py：校准后的时间驱动与分层运动。
- analyze_returns.py：逐发射器匹配、有效返回、深度与强度统计。
- protect_sources.py：保护清单与前后哈希核验。
- cases/<unique_case_name>/：新层、参数、原始数据、日志、原生跟踪与快照。

禁止使用 queue.py 等会遮蔽 Python 标准库的文件名。
新 wrapper 配置新的脚本路径；不得继续引用旧 trace_hook 作为干预入口。

## 文件保护与执行约束

- 执行时创建 /root/gpufree-data/diagnostics/bvh_local_mode_<新时间戳>/。
- 本轮 runtime/cache/log/tmp 均指向该新目录。
- 若复制缓存，仅从旧缓存读取并复制到新目录；不把新进程写入路径指向旧实验。
- 旧资产只读引用，新增属性和 RenderProduct 位于新根层/覆盖层，禁止保存源层。
- GDB 干预仅限本轮新启动进程的函数实参，磁盘库保持原样。
- 单 GPU 串行执行，每个 case 使用唯一目录；普通 case 默认 240 s 超时，超时只标记未完成。
- 只结束本轮创建的进程组，不操作其他业务进程。
- 收尾核验所有受保护文件；如有差异，停止扩展实验，报告具体路径和差异。
- 不修改原项目“三项开关”的配置或 guard；何时能调整它必须由后续兼容范围证据决定。

## 交付物与完成标准

每阶段提供：
1. 简洁结论：已证明什么，尚未证明什么。
2. 对照表和必要的相机图 / 点云叠图。
3. 原生模式、资源与输出之间的证据关联。
4. 新建的可复现脚本与完整 case 清单，保留失败和无效尝试。
5. 文件保护核验、实验进程退出状态。

首要交付是阶段 1 的“能否共存”判断及其证据。
后续逐步缩小到构建分派、资源使用或时间/探测处理的具体环节。
如果拿不到原始源码，最终明确称为二进制与运行时机制分析；不称为已经阅读了 NVIDIA 原始实现源码。
