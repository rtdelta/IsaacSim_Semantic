# 01 项目全景与核心概念

## 1. 项目解决的问题

上游仿真采集得到的是：

- 一张 RGB 图片；
- 一张与 RGB 像素完全对齐的二维 semantic ID 数组；
- 一份“semantic label ↔ semantic ID”的 mapping。

模型训练通常需要的是 YOLO 检测数据：

- 图片；
- 与图片同名的 `.txt` 标签；
- 类别列表。

本项目负责把前一种数据转换成后一种数据。当前业务目标分两层：

1. 从 `tooth_1` 到 `tooth_5` 的语义像素中，为每个斗齿标签生成一个独立框；
2. 从上一步的斗齿框中选择两个端部框，生成一个 `tooth_group` 集合框。

它是独立的后处理项目，不启动 Isaac Sim，也不回放关节轨迹。仿真、相机、关节和材质问题属于上游；本项目只消费已经落盘的数据。

## 2. 项目刻意不做什么

理解边界能避免把错误排查到错误的位置：

- 不从 RGB 图片做视觉识别；
- 不读取彩色语义预览图 `semantic_color_*.png`；
- 不把 semantic ID 自动猜成标签；
- 不做连通域或实例分割；
- 不负责拆分 train/val/test；
- 不生成 Ultralytics 的 `data.yaml`；
- 不直接训练 YOLO；
- 不递归搜索任意目录结构。

当前算法信任 semantic ID 数组和 mapping。如果上游标签错误，本项目只能忠实地产生错误框。

## 3. 三层结构

```text
run_pipeline.py
    │
    ▼
pipeline/
    ├─ 读取总配置、校验依赖、创建模块
    ├─ 发现并配对帧
    ├─ 多进程调度
    └─ 汇总运行状态
    │
    ├──────────────┐
    ▼              ▼
common/          modules/
数据模型与通用 I/O  业务算法与模块配置
```

依赖方向是：

```text
run_pipeline -> pipeline
pipeline     -> common
modules      -> pipeline 的模块协议 + common
```

业务模块之间不直接导入。`tooth_group_yolo` 不导入
`semantic_yolo_boxes`，而是通过 `FrameArtifactStore` 读取上游发布的
`SemanticBoxSet`。这样模块算法彼此隔离，依赖关系由 JSON 描述。

## 4. 关键目录

```text
260724PostProcessChain/
├─ run_pipeline.py
├─ requirements.txt
├─ configs/
│  ├─ orchestrator.json
│  └─ orchestrator.example.json
├─ postprocess_chain/
│  ├─ common/
│  ├─ pipeline/
│  └─ modules/
│     ├─ semantic_yolo_boxes/
│     └─ tooth_group_yolo/
├─ tests/
└─ docs/tutorials01/
```

各区域的职责：

- `run_pipeline.py`：唯一命令行入口，只接受 `--config`；
- `configs`：定义输入、输出、并行参数、模块启停和依赖；
- `common`：帧模型、像素框、semantic I/O、YOLO 格式和原子写出；
- `pipeline`：模块协议、注册、拓扑排序、多进程和总调度；
- `modules`：严格隔离的业务实现和各自 JSON；
- `tests`：几何、模块和端到端行为测试。

## 5. 必须先理解的六个概念

### 5.1 帧

同一个 frame ID 的两个文件组成一帧：

```text
rgb_0007.png
semantic_id_0007.npy
```

项目按文件名提取 `0007`，而不是读取文件中的元数据。两边 ID 集合必须完全一致。

### 5.2 semantic ID 与 semantic label

`.npy` 中存的是整数，例如 `5`；mapping 说明 `5` 对应 `tooth_1`。模块配置使用 label，运行开始时才解析成 ID。

### 5.3 semantic label 与 YOLO class

五个 semantic label 可以映射到同一个 YOLO class：

```text
tooth_1 ─┐
tooth_2  │
tooth_3  ├──> YOLO class 0: tooth
tooth_4  │
tooth_5 ─┘
```

这会产生五个 class ID 都是 `0` 的检测框，而不是把五个标签合成一个框。

### 5.4 帧内中间产物

模块除了写 YOLO 标注，还能返回只存在于当前 worker 内存中的 artifact。上游发布：

```text
tooth_boxes.semantic_boxes
```

其中 `tooth_boxes` 是总配置中的模块 ID，`semantic_boxes` 是模块发布的局部名。

### 5.5 依赖图

```text
tooth_boxes ──> tooth_group
```

总配置中的 `depends_on` 决定顺序。项目会检查未知依赖、禁用依赖、自依赖和循环依赖，并做稳定拓扑排序。

### 5.6 帧级多进程

一个 worker 完成一整帧的模块链：

```text
worker A: frame 0000 -> 模块 1 -> 模块 2
worker B: frame 0001 -> 模块 1 -> 模块 2
```

不是“模块 1 一个进程、模块 2 一个进程”。因此同一帧的 semantic 数组只加载一次，各模块共享。

## 6. 一次运行的主路径

```text
读取并严格校验 JSON
  -> 检查输入路径
  -> 按文件名发现并配对帧
  -> 加载 mapping
  -> 按依赖顺序创建并校验模块
  -> 计算配置指纹并准备输出
  -> 多进程处理每一帧
  -> 原子写出标签/图片
  -> 写 summary 与最终 manifest
  -> 返回退出码
```

启动阶段的问题会直接使入口返回退出码 `2`。帧处理阶段如果出现失败，流水线仍可按配置继续，但最终返回 `1`。完全成功返回 `0`。

## 7. 推荐的源码阅读入口

第一次阅读不要从工具函数开始。按以下顺序建立主线：

1. `run_pipeline.py`
2. `pipeline/orchestrator_config.py`
3. `pipeline/orchestrator.py`
4. `pipeline/executor.py`
5. `pipeline/module_base.py`
6. 两个模块的 `module.py`
7. 最后再查 `common` 中被调用的函数

这样读到每个工具函数时，你已经知道它在总流程中的位置。

## 本章验收

请在不看上文的情况下回答：

1. 为什么 `tooth_group_yolo` 不应直接导入另一个业务模块？
2. 五个 semantic label 映射到一个 YOLO class 时，会得到几个框？
3. 多进程并行的是模块还是帧？
4. 为什么本项目不能修复错误的上游 semantic 标签？

答案要点：通过帧内 artifact 解耦；每个可见且达阈值的 label 一个框；并行帧；算法完全依赖 semantic 数据。
