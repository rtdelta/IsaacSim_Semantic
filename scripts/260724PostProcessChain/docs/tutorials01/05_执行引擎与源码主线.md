# 05 执行引擎与源码主线

本章从 `python run_pipeline.py` 开始，沿着一次运行的真实调用顺序阅读源码。

## 1. 命令行入口

`run_pipeline.py` 只做三件事：

```python
args = parse_args()
config = load_orchestrator_config(args.config)
return Orchestrator(config).run()
```

唯一参数是 `--config`。默认值是项目根目录下的
`configs/orchestrator.json`。这个默认文件当前含 `YOUR_DATASET` 占位符，必须先改路径或指定另一份配置。

入口还负责：

- Windows 多进程的 `freeze_support()`；
- Windows 终端 UTF-8；
- `KeyboardInterrupt` 返回 130；
- 未处理的启动/全局异常返回 2；
- 帧级失败由 orchestrator 汇总后返回 1；
- 完全成功返回 0。

## 2. 配置先变成不可变数据对象

`pipeline/orchestrator_config.py` 把 JSON 解析为：

```text
OrchestratorConfig
├─ InputConfig
├─ output_root
├─ ExecutionConfig
├─ OutputConfig
└─ tuple[ModuleSpec, ...]
```

这些 dataclass 都是 `frozen=True`。配置一旦加载，执行期间不会被业务模块悄悄修改。

加载阶段已经完成：

- JSON 类型和未知字段校验；
- 路径绝对化；
- 输入文件存在性检查；
- 并行参数约束；
- 依赖合法性与环检查；
- 输入输出隔离检查。

因此“配置错误”通常在任何输出创建前就能暴露。

## 3. 稳定拓扑排序

模块不简单按 JSON 数组顺序执行，而是按 `depends_on` 建图。

示例：

```text
A ──> C
B ──> C
```

如果 A、B 同时可执行，项目保留它们在配置数组中的相对顺序；这叫稳定拓扑排序。若没有任何入度为 0 的剩余模块，说明存在环，启动失败。

当前链：

```text
tooth_boxes ──> tooth_group
```

## 4. 模块怎样被找到

注册表位于 `pipeline/module_registry.py`：

```python
@register_module("semantic_yolo_boxes")
class SemanticYoloBoxesModule(PipelineModule):
    ...
```

装饰器把：

```text
"semantic_yolo_boxes" -> SemanticYoloBoxesModule
```

保存到进程内字典。

注册依赖 import 副作用。`Orchestrator._create_modules()` 会导入
`postprocess_chain.modules`，而 `modules/__init__.py` 显式导入两个内置模块，从而执行装饰器。

这解释了新增模块时的一个常见错误：只写 `@register_module` 不够，还必须让
`modules/__init__.py` 导入该模块。

## 5. `PipelineModule` 生命周期

所有模块遵守：

```text
from_config()
    -> validate()
    -> prepare()
    -> process_frame()  重复 N 帧
    -> finalize()
```

### `from_config`

从 `ModuleSpec` 和只读 `RunContext` 创建模块实例。业务 JSON 在这里解析。

### `validate`

做跨字段或跨模块约束。基类要求 `class_names` 非空；集合模块还检查 artifact 来源在 `depends_on` 中。

### `prepare`

基类创建模块输出目录并写 `classes.txt`。所有模块都通过验证后才准备输出。

### `process_frame`

纯粹的逐帧业务核心：

```python
result = module.process_frame(frame, artifacts)
```

返回 `ModuleResult`。

### `finalize`

所有帧结束后的钩子，当前两个模块没有额外操作。

## 6. Orchestrator 的完整顺序

`Orchestrator.run()` 的真实顺序：

1. 读取 semantic mapping；
2. 发现并配对所有帧；
3. 创建 `output_root`；
4. 创建 `RunContext`；
5. 按拓扑顺序实例化、校验模块；
6. 计算配置指纹；
7. 检查已有 manifest；
8. 调用所有模块的 `prepare()`；
9. 写状态为 `running` 的 manifest；
10. 执行帧任务并汇总错误/统计；
11. 调用所有模块的 `finalize()`；
12. 写 `summary.json`；
13. 把 manifest 更新为 `completed` 或 `failed`；
14. 打印摘要并返回退出码。

如果进程在步骤 9 后意外中断，manifest 可能停留在 `running`，且没有最终 summary。看到这种状态不能把该输出目录当成完整运行。

## 7. 一帧怎样执行

worker 中的 `process_frame_task()`：

```text
加载 FrameContext
  -> 新建本帧 FrameArtifactStore
  -> 按拓扑顺序遍历模块
       -> 检查计算依赖是否 ready
       -> process_frame
       -> 发布 artifact
       -> 标记 computationally_ready
       -> 根据 disposition/annotation 写出
  -> 返回本帧状态、各模块状态和错误列表
```

`FrameContext` 包含：

```text
task.frame_id
task.rgb_path
task.semantic_path
semantic ndarray
image_width
image_height
```

同一帧的所有模块共享这个对象，避免重复加载 semantic。

## 8. `FrameArtifactStore`

发布：

```python
artifacts.publish("tooth_boxes", {"semantic_boxes": value})
```

内部完整键为：

```text
tooth_boxes.semantic_boxes
```

规则：

- 局部 artifact 名不能为空；
- 局部名不能包含 `.`；
- 同一个完整键不能重复发布；
- 读取不存在的键会报错；
- store 每帧新建，不跨帧、不跨进程，也不落盘。

因此 artifact 适合传递计算中间结果，不适合做跨帧统计或断点持久化。

## 9. `ModuleResult` 的四个维度

```python
ModuleResult(
    artifacts={...},
    annotation=...,
    disposition="write",
    metrics={...},
)
```

### `artifacts`

供当前帧下游消费。

### `annotation`

- 有 detections：写普通 YOLO 标签；
- 空 `YoloAnnotationSet(())`：写空标签；
- `None`：成功但不写标签。

### `disposition`

- `write`：按 annotation 处理；
- `exclude`：排除该模块的这帧。

### `metrics`

模块自定义整数计数，在主进程中累加到 summary。

## 10. 依赖 ready 与输出成功不是一回事

执行器先：

1. 成功执行 `process_frame()`；
2. 发布 artifact；
3. 把模块标记为 `computationally_ready`；
4. 再尝试写 YOLO 输出。

因此：

- `process_frame` 抛错：模块为 `error`，依赖它的下游为 `blocked`；
- `process_frame` 成功但写文件失败：本模块仍记为 `error`，但下游仍可消费已发布 artifact 并继续计算；
- 模块返回 `exclude`：计算仍成功，下游依赖也可继续；
- 模块输出被 `skipped`：计算仍已发生，artifact 正常存在。

“依赖”表达的是计算数据依赖，不等价于“上游文件必须已成功落盘”。

## 11. 帧级并行

`workers=1` 时在主进程顺序执行，最适合断点调试。

`workers>1` 时使用 `ProcessPoolExecutor`：

- 每个 future 对应一帧；
- 每个 worker 持有完整的有序模块列表；
- `max_in_flight` 限制 pending future 数；
- 主进程按完成顺序收集结果，不保证 frame ID 顺序；
- 最终每个输出文件以 frame ID 命名，因此完成顺序不影响数据内容。

模块实例作为 worker 初始化参数传递，所以新增模块必须可 pickle。不要把已打开文件句柄、线程锁、局部函数或不可序列化的第三方对象长期保存在模块实例字段中。

## 12. `continue` 与 `fail_fast`

`continue`：

- 一帧失败不阻止其他帧；
- 最后仍写 summary；
- 有任何失败则退出码 1。

`fail_fast`：

- 单进程：第一帧错误后停止；
- 多进程：停止提交新帧，但已在 pending 中的帧仍会完成；
- `summary.stopped_early` 用于判断是否提前停止。

它不是事务回滚，已经写出的帧不会撤销。

## 13. 建议断点位置

按问题选择：

| 问题 | 建议位置 |
| --- | --- |
| 路径或字段报错 | `load_orchestrator_config()` |
| 帧配对错误 | `discover_frame_tasks()` |
| dtype/尺寸错误 | `load_frame_resources()` |
| 模块没有框 | 对应模块的 `process_frame()` |
| YOLO 数值异常 | `format_annotation_set()` |
| 下游 blocked | `process_frame_task()` 依赖检查处 |
| 续跑行为异常 | `_prepare_manifest()`、`write_yolo_frame()` |

调试时先把 `workers/max_in_flight` 设为 `1/1`，否则断点可能落在子进程。
