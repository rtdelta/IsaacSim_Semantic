# 09 测试、调试与性能优化

正确的顺序是：先证明代码环境正常，再证明输入契约正常，再验证算法质量，最后才调性能。

## 1. 当前测试体系

从项目根目录运行全部测试：

```powershell
python -m unittest discover -s . -p "test_*.py" -v
```

当前版本共 10 项测试，已在本工作区 Python 3.9.18 上通过。

### 分层运行

几何：

```powershell
python -m unittest tests.test_box_geometry -v
```

单标签框模块：

```powershell

```

集合框模块：

```powershell

```

端到端：

```powershell

```

## 3. 排错阶梯

遇到问题时按这一顺序，不要同时改多项参数。

### 第一级：环境

```powershell
python --version
python -c "import numpy, PIL; print(numpy.__version__, PIL.__version__)"
python -m unittest discover -s . -p "test_*.py" -v
```

测试失败先修环境或代码，不要继续怀疑业务数据。

### 第二级：配置加载

把并行设为 `1/1`，运行：

```powershell
python run_pipeline.py --config <你的配置>
$LASTEXITCODE
```

退出码 2 通常表示：

- JSON 语法或字段错误；
- 路径不存在；
- mapping/模块配置非法；
- 依赖图错误；
- 旧 manifest 指纹冲突。

### 第三级：输入帧

抽查：

- RGB 与 NPY 文件名是否成对；
- semantic 是二维；
- shape 与 RGB 一致；
- dtype 与 mapping 一致；
- mapping label 与模块配置一致。

### 第四级：逐帧算法

若产生 `errors.jsonl`：

- `load_frame`：先查 NPY/RGB；
- `process_frame`：查当前模块输入和 artifact；
- `write_output`：查框边界、class ID/name、权限和磁盘。

### 第五级：业务质量

即使退出码 0，也要检查：

- `missing_masks` 是否异常；
- `small_masks` 是否因阈值过大而激增；
- `missing_endpoints` 是否符合遮挡情况；
- 随机可视化框；
- 分场景统计，而不只看总数。

## 4. 常见报错速查

### `RGB directory does not exist`

总配置路径基准错误或还保留 `YOUR_DATASET`。

### `RGB and semantic frames do not match`

两侧 frame ID 集合不同。项目不忽略缺对帧。

### `no semantic_id_*.npy files found`

目录错、文件名大小写错、后缀错，或文件在子目录中。发现逻辑不递归。

### `semantic array must be 2D`

NPY 是 `(H, W, 1)`、RGB 数组或其他非二维数据。

### `semantic dtype=..., mapping declares ...`

mapping 的 `dataset_dtype` 与 NPY dtype 不同。不要只修改声明来绕过；先确认哪个才是数据真实契约。

### `semantic shape ... does not match RGB size`

宽高颠倒、裁剪不同步或拿错帧。

### `semantic label ... is absent from mapping`

模块配置与 mapping 命名不一致，例如 `tooth_1` 对 `tooth_01`。

### `unknown module type`

type 拼错，或新增模块没有在 `modules/__init__.py` 中导入注册。

### `required frame artifact is unavailable`

`source_artifact` 名写错、上游未发布，或当前分支没有该 artifact。

### `output_root contains results from a different configuration`

换新输出目录，或明确使用 `overwrite=true`。

### `PermissionError` / 写出失败

检查：

- 输出目录权限；
- 文件是否被其他程序占用；
- 磁盘空间；
- 防病毒或同步软件锁定；
- 网络盘是否支持 replace/硬链接。

## 5. 为什么调试先用单进程

`workers=1` 的优势：

- 异常堆栈来自当前进程；
- IDE 断点直接命中；
- 日志顺序稳定；
- 不涉及 pickle 和子进程导入；
- 可确定具体是第几帧触发。

算法和数据通过后，再切换到多进程验证。新增模块必须同时测试 `workers=2`，否则可能隐藏序列化问题。

## 6. 设计一个最小失败实验

不要在 500 帧正式数据上调一个字段。复制一帧到小目录：

```text
debug_input/
├─ rgb/rgb_0000.png
├─ semantic_id/semantic_id_0000.npy
└─ semantic_mapping.json
```

然后用：

```json
"workers": 1,
"max_in_flight": 1,
"image_mode": "none",
"on_frame_error": "fail_fast"
```

快速复现。修复后再跑两帧：一帧正常、一帧故意触发边界。

## 7. 新增测试的三层方法

### 纯函数测试

对 `PixelBox`、归一化、选择器等无 I/O 函数给定输入并断言输出。

### 模块测试

直接构造：

```text
RunContext
ModuleSpec
FrameContext
FrameArtifactStore
```

调用 `module.process_frame()`，断言：

- annotation；
- artifacts；
- disposition；
- metrics。

这层不需要真实图片落盘。

### 端到端测试

在 `TemporaryDirectory` 中创建：

- RGB；
- NPY；
- mapping；
- 两份模块配置；
- 总配置。

运行 `Orchestrator(config).run()`，断言输出文件和 summary。再至少测一次多进程和一次续跑。

## 8. 性能成本来自哪里

大致分为：

```text
磁盘读取 NPY/RGB 元数据
  + NumPy 扫描 semantic
  + 进程调度/序列化
  + 图片硬链接或复制
  + 标签和 JSON 写出
```

当前 RGB 只打开读取尺寸，不把完整像素解码成 NumPy。主要计算通常在 semantic 扫描，主要 I/O 风险通常在大量 NPY 和图片复制。

## 9. 调整 `workers`

建议逐级测试：

```text
1 -> 2 -> 4 -> 8
```

每档用同一数据、全新输出目录，记录：

- `elapsed_seconds`；
- `frames_per_second`；
- CPU 利用率；
- 内存；
- 磁盘活动时间。

不要假设 worker 越多越快：

- 多进程会增加同时读取 NPY 的压力；
- `np.isin` 本身有内存带宽成本；
- HDD/网络盘可能先饱和；
- 每个进程都有临时数组和 Python 开销。

如果从 4 到 8 几乎不加速，通常应停在 4。

## 10. 调整 `max_in_flight`

默认 `workers * 2` 是合理起点。

太小：

- worker 完成后可能短暂等不到新任务。

太大：

- 主进程保留更多 future；
- fail_fast 时已有更多任务无法立即取消；
- 不会让 worker 数本身增加。

一般先固定为 `2 × workers`，只有测量显示提交饥饿时再调整。

## 11. 图片模式与磁盘

性能验证阶段：

```json
"image_mode": "none"
```

可把算法耗时与图片物化耗时分开。

正式输出：

- 同一磁盘：优先 `hardlink_or_copy`；
- 跨磁盘/网络盘且要独立副本：`copy`；
- 训练流程共享原图：评估能否保留 `none`，并另做数据清单。

硬链接目录的“文件大小总和”看起来可能很大，但实际磁盘占用不等于简单相加。

## 12. 跨平台和远端

本项目是普通 CPython 后处理器：

- 不需要 Isaac Sim；
- 不需要 CUDA；
- 不需要 GUI；
- 不依赖 pytest；
- 没有专用 Docker/SSH/部署脚本。

Linux 典型命令：

```bash
cd scripts/260724PostProcessChain
python3 -m venv .venv
source .venv/bin/activate
python -m pip install -r requirements.txt
python run_pipeline.py --config configs/my_run.json
```

跨平台注意：

- JSON 路径推荐使用 `/`；
- Windows JSON 中的 `\` 必须写成 `\\`；
- Linux 文件名大小写敏感；
- 相对路径仍以配置文件目录为基准；
- 在数据所在机器处理大型 NPY，通常比来回传输更合理。

## 13. 可重复性注意

不同 worker 完成顺序可能不同，所以：

- 终端进度顺序不应作为结果顺序；
- `errors.jsonl` 行顺序可能随并行完成顺序变化；
- 输出文件名和内容由 frame ID 决定，业务结果应一致；
- 性能比较必须使用同一数据和独立输出目录。
