# 08 输出、断点续跑与错误处理

可靠的数据流水线不仅要“能跑”，还要能证明输出对应哪份配置、哪些帧失败、哪些帧被有意排除。

## 1. 输出目录

```text
output_root/
├─ manifest.json
├─ summary.json
├─ errors.jsonl
└─ modules/
   ├─ tooth_boxes/
   │  ├─ classes.txt
   │  ├─ rgb_0000.png
   │  └─ rgb_0000.txt
   └─ tooth_group/
      ├─ classes.txt
      ├─ rgb_0000.png
      └─ rgb_0000.txt
```

`errors.jsonl` 仅在本次运行记录到错误时存在。

每个模块是独立 YOLO 数据集：

- 独立 `classes.txt`；
- 独立逐帧 `.txt`；
- 按 `image_mode` 决定是否有图片。

标签名使用 RGB stem。例如输入 `rgb_cameraA_0042.png`，标签为
`rgb_cameraA_0042.txt`。

## 2. 图片物化模式

### `hardlink_or_copy`

先用 `os.link` 创建硬链接，失败再 `copy2`。

特点：

- 同一磁盘/文件系统通常不额外占一份图片数据块；
- 删除输出硬链接不会删除原始 RGB；
- 跨磁盘、网络盘或权限不支持时自动复制。

### `copy`

总是复制。空间占用更大，但行为最直观，适合网络文件系统或需要完全独立交付的目录。

### `none`

不在模块目录创建图片，只写标签。适合快速验证和已有统一图片管理的训练流程。

## 3. 原子写出

文本和 JSON 的写法：

```text
写同目录临时文件
  -> flush
  -> fsync
  -> os.replace 到正式文件
```

图片也先写临时路径，再 replace。这样能减少进程中断时出现“正式文件只写了一半”的风险。

原子写并不等于整个运行是事务：已经成功完成的其他帧不会因后一帧失败而回滚。

## 4. `classes.txt`

每次运行的 `prepare()` 都根据模块的 `class_names` 写出它。YOLO detection 写出时还会检查：

- class ID 没有越界；
- detection 的 class name 与 `classes.txt` 相同位置的名称一致。

因此新增模块时，不能只让 ID 正确而 name 不一致。

## 5. `manifest.json`

运行开始时：

```json
{
  "schema_version": 1,
  "status": "running",
  "started_at": "...",
  "config_path": "...",
  "config_fingerprint": "...",
  "inputs": {...},
  "modules": ["tooth_boxes", "tooth_group"]
}
```

成功结束后增加：

```json
{
  "status": "completed",
  "finished_at": "...",
  "summary": {...}
}
```

有帧失败时最终 status 为 `failed`。

### 指纹精确包含什么

当前实现的 SHA-256 指纹包含：

- RGB 输入目录的解析后路径；
- semantic 输入目录的解析后路径；
- 启用模块按执行顺序的 `id`、`type`、`depends_on`；
- semantic mapping 的文件路径和文件内容；
- 每个启用模块配置的文件路径和文件内容。

当前不包含：

- 输入 RGB/NPY 文件内容；
- `workers`、`max_in_flight`、`on_frame_error`；
- `image_mode`、`write_manifest`；
- `output_root` 本身。

所以不要把它理解为“所有数据和所有总配置的完整内容哈希”。它主要防止在同一输出目录中误混不同 mapping/模块业务配置。

## 6. `summary.json`

关键字段：

```json
{
  "discovered_frames": 100,
  "completed_frames": 100,
  "failed_frames": 0,
  "stopped_early": false,
  "elapsed_seconds": 1.23,
  "frames_per_second": 81.3,
  "modules": {
    "tooth_boxes": {
      "written": 100,
      "skipped": 0,
      "excluded": 0,
      "success": 0,
      "error": 0,
      "blocked": 0,
      "boxes": 470,
      "small_masks": 8,
      "missing_masks": 22
    }
  }
}
```

状态含义：

| 状态 | 含义 |
| --- | --- |
| `written` | 本次写出标签 |
| `skipped` | 标签已存在且 overwrite=false |
| `excluded` | 模块主动排除 |
| `success` | 计算成功，但 annotation 为 None |
| `error` | 计算或写出失败 |
| `blocked` | 计算依赖未 ready |
| `boxes` | 返回 annotation 中 detection 数之和 |

模块自定义 metrics 也会被累加进入同一对象。

`completed_frames` 是已从执行器收到结果的帧数，不等于成功帧数；必须同时看 `failed_frames`。

## 7. `errors.jsonl`

一行一个 JSON 对象，便于大数据集流式读取：

```json
{"frame_id":"0042","module_id":"tooth_boxes","stage":"process_frame","message":"ValueError: ...","rgb_path":"...","semantic_path":"..."}
```

错误阶段：

| `module_id` / `stage` | 含义 |
| --- | --- |
| `__frame__` / `load_frame` | NPY、dtype、维度、RGB 尺寸等加载问题 |
| 具体模块 / `process_frame` | 业务计算或 artifact 问题 |
| 具体模块 / `write_output` | YOLO 校验或文件写出问题 |
| `__worker__` / `worker` | future/worker 外层异常 |

`blocked` 本身通常没有额外错误行，应向前找同帧上游的 `process_frame` 错误。

快速查看：

```powershell
Get-Content tutorial_work\output\run_001\errors.jsonl
```

按阶段统计：

```powershell
@'
import json
from collections import Counter
from pathlib import Path

path = Path("tutorial_work/output/run_001/errors.jsonl")
counter = Counter()
for line in path.read_text(encoding="utf-8").splitlines():
    item = json.loads(line)
    counter[(item["module_id"], item["stage"])] += 1
print(counter)
'@ | python -
```

## 8. 断点续跑的真实机制

`overwrite=false` 时，若模块目标标签文件已存在：

1. 模块仍执行 `process_frame()`；
2. artifact 仍发布；
3. 输出 writer 发现 `.txt` 已存在；
4. 确保图片按模式物化；
5. 返回 `skipped`，不重写标签。

为什么不跳过整个上游模块？因为下游可能依赖它的内存 artifact，而 artifact 不持久化。

## 9. 指纹不匹配

已有 manifest 且 `overwrite=false` 时，如果指纹不同，启动失败：

```text
output_root contains results from a different configuration
```

处理方式：

- 推荐：使用新的 `output_root`；
- 明确确认要替换旧结果时：`overwrite=true`。

新的输出目录更利于对比实验和审计。

## 10. 输入内容变化的高级风险

指纹不包含输入帧内容。若你原地修改某个 `.npy`，输入目录路径不变，指纹也不会变化。

此时 `overwrite=false` 会跳过已有标签，造成“标签来自旧 NPY，输入目录却已更新”的不一致。

安全规则：

```text
输入 RGB/NPY 内容有变化
  -> 使用全新 output_root
  或
  -> 明确设置 overwrite=true
```

不要把指纹当作输入数据完整性校验。

## 11. exclude 的陈旧文件风险

当前帧现在被排除，但输出目录里可能有过去生成的同名文件：

- `overwrite=true`：执行器会删除旧 `.txt` 和对应图片；
- `overwrite=false`：不会清理。

当输入或策略改变时，继续复用旧目录可能残留本不该存在的样本。这也是业务变更使用新输出目录的理由。

## 12. 错误策略

### `continue`

适合批量处理：

- 收集尽可能多的结果；
- 所有错误落入 journal；
- summary 反映失败数；
- 最终退出码 1，提醒自动化流程不能当作完全成功。

### `fail_fast`

适合严格验证或调试：

- 尽早停止提交；
- 多进程已有 pending 任务可能继续；
- summary 的 `stopped_early=true` 表明并非全部帧都处理。

## 13. 运行结果审计清单

一次正式结果至少检查：

```text
[ ] 进程退出码为 0
[ ] manifest.status == "completed"
[ ] summary.discovered_frames == 预期帧数
[ ] summary.completed_frames == discovered_frames
[ ] summary.failed_frames == 0
[ ] summary.stopped_early == false
[ ] 没有 errors.jsonl
[ ] 各模块 written + skipped + excluded 等状态符合预期
[ ] boxes、missing_masks、missing_endpoints 的数量合理
[ ] 随机可视化若干 YOLO 框
[ ] 保存总配置、模块配置和 mapping
```

仅看到终端最后一行 `post-process chain completed` 不足以证明业务结果正确。
