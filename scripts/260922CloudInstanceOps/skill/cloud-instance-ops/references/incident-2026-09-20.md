# 事件参考：读取被过滤导致桌面依赖加载失败

本文件是 2026-09-20 一次 Linux 云实例事故的脱敏复盘。只在调查读取矛盾、异常预加载、进程隐藏等现象时参考；不是每次部署必做检查，也不是通用恶意软件签名库。

## 已确认的机制

- 旧实例 `/etc/ld.so.preload` 指向异常 `.libproc.so`；其代码替换 `read`、`readdir` 等接口，并过滤文件、进程及网络记录。
- 系统 psutil 字节码磁盘原始内容为 91,544 字节，与工作正常的对照实例一致；普通读取仅得到 91,465 字节，反序列化失败。
- 隐藏配置包含回环地址的编码。psutil 文档字符串中恰好包含相同编码的一整行被删去，共 79 字节；读取编译后的字节码也发生同样删减。
- 静态代码、配置解码和实际字节差异相互吻合。本地重建过滤结果后，与普通读取结果逐字节一致；没有执行可疑库来验证。
- 同时存在隐藏进程、接近 CPU 配额的异常占用和持久化启动项。普通进程列表不足以反映实际负载。
- 桌面主程序后来退出，共同默认配置 `autorestart=false` 使其未重启。历史中另有停止桌面 PID 的命令，但缺少逐条时间和操作者信息，未确认是谁触发退出。

## 必须保留的结论边界

- 字节码读取破坏的机制已复现；原桌面环境中那份失败缓存后来已消失，不能声称重放了该原副本。
- 入侵入口、操作者和最早入侵时间未确定。文件 mtime/ctime、相邻时间的 Hydra 安装记录以及外联地址，不能单独证明来源或责任。
- 两边 Jupyter 都关闭自身认证，同账号实例间存在无应用凭据读取元数据的内网路径；公网网关和跨租户隔离尚未核实，不能据此认定入侵来自 Jupyter。
- 对照实例能正常运行、受检哈希一致，不等于官方离线可信镜像或完整安全验收。
- 新实例有合法的平台预加载库；不能把“预加载文件非空”视为感染，也不能自动清空它。

## 遇到类似情况如何选择下一步

1. 保留报错原文和相关文件，再比较原始内容与应用读取结果；不要先删缓存，使原始证据消失。
2. 以身份明确、版本可比较的实例或可信副本交叉核对；区分共同配置、正常用户状态和异常独有变化。
3. 同时参考平台资源统计、实例配额和进程信息；有明显矛盾才扩大调查，不普遍执行底层取证。
4. 原始系统调用或内存映射只能绕过部分已知用户态过滤，不能证明没有内核或其他层干预。它们不是通用“安全读取模式”。
5. 在线采集依旧可能触发既有加载器或后台程序。严格保全场景应使用授权的快照/离线或平台救援方式，不能擅自停机取证。
6. 普通依赖报错未显示异常注入证据时，仍按正常版本、路径和缓存问题排查；不能把本次特殊事故泛化到所有 Python 错误。
